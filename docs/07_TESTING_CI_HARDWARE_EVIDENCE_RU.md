# NekoFlash — Testing, CI & Hardware Evidence

## 1. Тесты строятся по слоям

### Pure unit
- codecs/parsers;
- state machines;
- byte accounting;
- advisory classification;
- artifact logic;
- correlation logic.

### Protocol simulation
Fake peer/transport должен уметь моделировать:
- short reads/writes;
- packet fragmentation;
- delayed responses;
- duplicate/out-of-order relevant events;
- stream concurrency;
- malformed frames;
- `INFO/TEXT/FAIL` sequences;
- DATA length mismatch;
- disconnect at every interesting byte/state boundary.

### Integration
- Android USB permission/session ownership;
- foreground operation service;
- persistence/process recreation;
- SAF seekable/non-seekable providers where testable.

### Hardware
Нужен matrix реальных устройств/режимов, потому что USB host stacks и Recoveries имеют vendor quirks.

## 2. Hardware evidence policy

Hardware-sensitive change не считается proven только по unit tests.

Evidence bundle должен содержать:
- app commit/build identity;
- host device identity;
- target identity;
- mode;
- timestamps;
- relevant structured logs/transcript;
- exact byte counts;
- screenshots только как дополнительное подтверждение, не вместо logs;
- PASS criteria.

## 3. Reference devices

### `vayu`
Стабильный reference target для A2 evidence. Доказаны Native USBFS Fastboot DATA transfer/flash, cancel/drain semantics и финальный ADB inbound framing gate — **PASS**.

Frozen A2 archive не содержит финальный diagnostics bundle этого framing gate; статус PASS зафиксирован как project evidence по подтверждению владельца и должен учитываться отдельно от наличия самого bundle.

### `onyx` / POCO F7 / Redmi Turbo 4 Pro
USB-unstable stress patient. Не использовать как единственный reference gate. Quirk должен стать explicit observed capability/advisory, а не глобальным hard-block устройства.

## 4. Regression matrix нового проекта

Минимум постепенно покрыть:
- ADB Android mode;
- ADB Recovery mode;
- concurrent ADB streams;
- shell_v2 и legacy fallback;
- push/pull крупного файла;
- install;
- bootloader Fastboot;
- fastbootd;
- DATA OUT крупного image;
- DATA IN/fetch;
- physical detach during read-only operation;
- detach before and after mutation boundary;
- Sideload normal flow;
- Sideload duplicate requests;
- Sideload verifier reconnect/correlation;
- Mi Unlock staging на безопасных этапах и отдельно destructive/server-sensitive gate.

## 5. Localization quality gate

English и Russian являются first-class UI locales. Для каждого changeset, меняющего пользовательский интерфейс:
- default English resources и `values-ru` должны оставаться согласованными;
- Android Lint `MissingTranslation`/resource format failures являются блокирующими;
- user-facing Compose strings не должны возвращаться в hardcoded literals;
- protocol/raw/evidence data не переводятся на уровне core;
- при существенном UI изменении проверяется, что русский текст не ломает adaptive layout.

## 6. CI minimum

**Authoritative build/test environment нового NekoFlash — GitHub Actions.** Termux используется как Git/worktree environment и не обязан быть полноценной Android/Gradle build machine.

Каждый merge в main:
- compile;
- unit/protocol tests;
- static analysis/lint;
- formatting;
- repository hygiene scan;
- Kotlin style/complexity/module-boundary scan;
- no generated binary drift where relevant;
- test report artifact;
- build identity embedded/exportable in diagnostics;
- canonical documentation updated in the same changeset when behavior, architecture, gates or project status changes.

## 6.3. usb:api — 2026-08-30

Первый модуль Phase 2. Чистый JVM-контракт без Android: дескрипторы USB, классификация интерфейсов и выведение идентичности target.

Классификация перенесена из двух независимых источников, сошедшихся на одном и том же — Legacy `UsbDeviceInspector.kt` и A2 `usb/discovery/UsbInterfaceSelector.kt`: класс `0xFF`, подкласс `0x42`, протокол `0x01` для ADB и `0x03` для Fastboot, четыре уровня уверенности с подавлением низших, обязательная пара bulk-эндпоинтов.

Выведение идентичности спроектировано заново: в A2 его не было. `TargetId` строится по серийному номеру, когда он доступен, и по имени USB-подключения, когда нет; источник хранится рядом с идентичностью, потому что второй вариант не переживает re-enumeration и не должен выдавать себя за первый.

Владение сессиями и `SessionGeneration` спроектированы заново по `02_CORE_ARCHITECTURE_RU.md`: generation монотонна в пределах процесса, каждое подключение получает новую, завершённая сессия необратима. Обращение по устаревшей generation отклоняется с указанием причины завершения, а не generic-ошибкой: реестр помнит ограниченное число недавно закрытых сессий именно ради честного ответа «устройство отключено».

Политика разрешений перенесена из A2 (`UsbPermissionPolicy`), но опирается на сессии, а не на отдельный реестр ожидающих запросов: два источника истины о том же самом рано или поздно расходятся. Сохранены проверенные детали — приоритет точного совпадения идентификатора подключения над именем, повторная привязка выбранного интерфейса к свежему дескриптору, таймаут 30 секунд и отказ подключаться неявно по разрешению, о котором система не сообщила.

57 unit-тестов модуля закрепляют перенесённые инварианты. Проверка границ модулей расширена на `usb/api`: Android-импорты в него запрещены машинно.

## 6.4. usb:android и декларации манифеста — 2026-08-30

Первый Android-модуль. Содержит только перекладку дескрипторов `android.hardware.usb.*` в модель `usb:api`: разбор сырых значений направления и типа передачи вынесен в `usb:api` и покрыт тестами, поэтому в непроверяемом на телефоне коде не осталось ни одного решения.

Attach-фильтр перенесён из Legacy как есть — один wildcard `class="255"` вместо списка производителей. Список конкретных vendorId был бы ровно тем запретом, который запрещает продуктовый устав: устройство отсеивалось бы за отсутствие в нашем списке, а не за собственный отказ. Wildcard покрывает канонические ADB и Fastboot, OEM Fastboot с нестандартными subclass/protocol и новые vendorId без правки списка.

`uses-feature android.hardware.usb.host` объявлен обязательным так же, как в Legacy и A2. На установку это не влияет: `uses-feature` используется магазином приложений, а не установщиком, а NekoFlash распространяется вне магазина.

Проверка границ модулей расширена на `usb/android`: зависимости на protocol, feature, vendor, UI и Compose запрещены машинно.

Владение USB на стороне Android добавлено следом: перечисление устройств, приёмники подключения и отключения, запрос разрешения. Хост не принимает решений — он сообщает факты и выполняет запрошенное, а классификация, идентичность, владение сессиями и разбор ответа остаются в `usb:api`.

Уникальность имени действия для ответа системы вынесена в `usb:api` и покрыта тестами: идентичность отложенного намерения не учитывает дополнительные данные, поэтому активации приходится различать самим именем действия, а токен процесса не даёт ответу, созданному до гибели процесса, совпасть с приёмником в новом.

Наблюдение на стороне Android построено на слушателе: приёмники платформы работают по колбэкам, и оборачивать их в `Flow` следует уровнем выше, а не внутри владельца USB.

`kotlinx.coroutines` введён отдельным изменением вместе с первым настоящим использованием: `UsbSessionRegistry` публикует незавершённые сессии как `StateFlow`. Прежняя функция-снимок удалена — два способа получить одно и то же расходятся. Зависимость проверена сборкой в том же изменении, которым введена.

Связывание добавлено следом. Платформенная часть вынесена за интерфейс `UsbHost` в `usb:api`, поэтому `UsbSessionCoordinator` остался чистым и покрыт тестами на подставном хосте: полный цикл подключения, выдача и отказ в разрешении, таймаут, отключение, уточнение идентичности серийным номером после разрешения.

Границы координатора намеренно узкие. В A2 ровно эта склейка разрослась до 2495 строк, потому что туда же попали запуск и остановка транспортов, оркестрация прошивки и Sideload, экспорт диагностики. Здесь координатор умеет только превращать события USB в состояние сессий.

Планирование времени координатору не принадлежит: стартовое сканирование, повторные попытки и таймаут ожидания разрешения запускает платформенный слой, вызывая его методы. Планирование нельзя выполнить детерминированно в тесте, а всё остальное — можно.

Экран добавлен последним. Владение USB живёт в `NekoFlashApplication`, а не на экране: подключённое устройство не должно теряться при повороте. Таймаут ожидания разрешения планируется там же, в области с `Dispatchers.Default` — главный диспетчер потребовал бы отдельного артефакта корутин, а реестр сессий и наблюдаемое состояние потокобезопасны, доставку на экран берёт на себя Compose.

Экран показывает только то, что действительно известно: идентичность target вместе с её источником, транспортный вид интерфейса, уверенность классификации, состояние сессии и generation. Протокольный режим не показывается вовсе, и вместо него выводится прямое объяснение, что до handshake он неизвестен: дескриптор отличает интерфейс класса ADB от класса Fastboot, но не Android от Recovery, а bootloader Fastboot от fastbootd. Подставлять правдоподобное вместо неизвестного значило бы обманывать оператора.

Ресурсы прежнего статичного макета, ставшие ненужными, удалены вместе с ним, а не оставлены про запас.

Сборщик evidence-пакета добавлен в `core:diagnostics` отдельно от платформы, потому что `java.util.zip` доступен и без Android — а значит формат архива проверяется тестами, а не наблюдением. Архив детерминирован: одинаковый набор разделов и одна отметка экспорта дают побайтово одинаковый файл, поэтому два прогона можно сравнить напрямую и расхождение будет означать расхождение данных, а не времени файловой системы. Время записей в архиве обнуляется намеренно.

Записывается только то, что передал вызывающий: каталог целиком не упаковывается, чтобы посторонний файл рядом не попал в evidence. Поток остаётся за вызывающим и не закрывается сборщиком.

Событие превращается в одну строку, пригодную и для чтения человеком, и для `grep`; переносы внутри значений заменяются пробелом, чтобы одно событие не распалось на несколько строк.

Запись событий подключена следом. `UsbSessionCoordinator` сообщает в приёмник каждый значимый переход: открытие сессии с параметрами подключения и выбранного интерфейса, запрос и исход разрешения, уточнение идентичности после его выдачи, таймаут с принятым решением, закрытие при отключении. Реестр по-прежнему ничего не пишет сам — он возвращает достаточно подробные результаты, а решает, что из этого событие, координатор.

Приёмник событий ограничен по объёму: владелец USB живёт всё время работы приложения, и неограниченный список рос бы часами. Число вытесненных событий сохраняется и попадает в evidence — молча потерять начало журнала значит выдать неполный отчёт за полный.

Выгрузка завершает диагностику. Архив содержит три раздела помимо описи: `host.txt` с идентичностью сборки и устройства-хоста, `sessions.txt` со снимком сессий на момент выгрузки, `events.txt` с журналом. Файл создаёт пользователь через системный диалог сохранения — приложение не заводит собственного хранилища отчётов.

Состав отчёта ничем не урезан. Он собирается оператором о собственном устройстве, и вырезать из него сведения «на всякий случай» означало бы ровно тот host-side запрет, который запрещает `01_PRODUCT_CHARTER_RU.md`. Поле, которого платформа не даёт, записывается с причиной отказа, а не пропускается: серийный номер хоста требует `READ_PRIVILEGED_PHONE_STATE`, разрешения системного уровня, которое обычному приложению не выдаётся ни при каких действиях пользователя. Вызов не делается вовсе — он не может завершиться успешно, — а в отчёт идёт причина. Это отказ платформы, который по классу Device authority показывается как есть.

Протокольный режим в отчёт не подставляется и записан как `unknown_until_handshake`. Пустое место и правдоподобная догадка одинаково портят evidence.

## 6.6. Первый аппаратный прогон — 2026-08-31

Хост: POCO `25053PC47G` (`onyx`), Android 16, SDK 36, патч 2026-07-01. Сборка `0.1.0-dev`, versionCode 1.

Цель: `serial:eff4927c`, vendorId `0x18D1`.

**Подтверждено на устройстве:**

- пять generation подряд, 1→5, монотонно, ни одна не переиспользована;
- уточнение идентичности `USB_ATTACHMENT → SERIAL` сработало при каждой выдаче разрешения;
- **идентичность пережила смену режима**: один и тот же серийный номер при `productId` `0x4EE7` (ADB), `0xD00D` (Fastboot) и `0x4E11` (ADB в другой конфигурации USB). Это прямое подтверждение решения не включать `vendorId`/`productId` в ключ при наличии серийного номера;
- Fastboot-интерфейс классифицирован как `FASTBOOT` с уровнем `CANONICAL`;
- отказ в разрешении закрыл сессию, повторное подключение открыло новую;
- таймаут, пришедший после ответа, дал `IGNORE` и ничего не изменил;
- потерь событий нет: `droppedEvents=0`.

**Найдено и исправлено по итогам прогона:**

- события сообщали состояние **до** перехода: `permission_requested` писал `DISCOVERED`, `permission_granted` — `PERMISSION_PENDING`. Отчёт называл прошлое настоящим. Снимок теперь берётся из результата самого перехода;
- снимок сессий оказался пустым, потому что устройство отключают перед выгрузкой. В отчёт добавлены недавно завершённые сессии — реестр их и так помнит;
- `MainActivity` не имела `launchMode="singleTop"`, и подтверждение attach-намерения пересоздавало экран. Атрибут есть и в Legacy, и в A2 — он был пропущен при переносе манифеста. Владение USB при этом не пострадало: оно живёт в `Application`, и в журнале нет ни дублирующих сессий, ни лишних generation.

## 6.7. Второй аппаратный прогон — 2026-08-31

Тот же хост и та же цель. Все три исправления подтверждены на устройстве:

Автоматического перезапроса после отказа нет: пользователь ответил «нет», и повторять вопрос без его действия было бы навязчивостью, а не свободой возможностей.

## 6.9. Claim / release

Захват интерфейса реализован как возможность, но **не выполняется автоматически**.

В Legacy и A2 захват живёт внутри протокольного транспорта (`AdbUsbTransport.open`, `FastbootUsbTransport.open`) и происходит сам собой при успешном обнаружении и разрешении. У нас протокольных движков ещё нет, поэтому автоматический захват удерживал бы исключительный ресурс, ничего с ним не делая, и мешал бы другим владельцам USB на этом хосте.

Поэтому захват и освобождение выполняются действием оператора. С появлением протокольных движков захват станет частью открытия транспорта, как в архивах, а явное освобождение сохранится: удерживать устройство без способа отпустить — само по себе ограничение.

`claimInterface` вызывается с принудительным отбором, единогласно с обоими архивами: вендорный интерфейс на некоторых хостах занят ядерным драйвером, и без этого ADB и Fastboot не работают. Это отбор у драйвера, который по этим протоколам всё равно не говорит.

Отказ платформы возвращается как есть — `DEVICE_GONE`, `OPEN_REFUSED`, `INTERFACE_REFUSED` — и попадает в журнал с причиной, а не подменяется собственным умолчанием.

## 6.15. Почему диалог авторизации появился повторно — 2026-09-03

В прогоне §6.14 устройство снова спросило подтверждение, хотя тот же хост был
авторизован двумя часами раньше. Разрешения отладки при этом не отзывались.

**Что видно в журнале.** Подпись была отправлена и **не принята**: следом ушёл
публичный ключ. Значит ключ хоста отличался от того, который устройство
запомнило. Между `auth_required` и `auth_signature_sent` прошло 120 мс — для
чтения ключа с диска долго, для генерации RSA-2048 правдоподобно.

**Причина, подтверждённая владельцем устройства.** Приложение при каждой новой
сборке удаляется и ставится заново, а не обновляется. Удаление уносит приватный
каталог вместе с ключом. Обновление же было невозможно по своей причине:
у сборки не было `signingConfig`, поэтому
`assembleDebug` на чистом раннере GitHub Actions создаёт новый
`debug.keystore` при каждом запуске. Каждая сборка подписана другим ключом,
установка поверх прежней невозможна, и приложение приходится удалять. Удаление
уносит приватный каталог вместе с `adbkey.pk8`, а новый ключ для устройства —
новый хост.

**Почему это не доказано.** Отпечаток ключа нигде не записывался, и отличить
«хост потерял ключ» от «устройство забыло хост» было нечем. Поэтому вместе с
этим разделом добавлено событие `host_key` с происхождением ключа
(`GENERATED` или `LOADED`) и его отпечатком.

**Как проверить в следующий раз.** Установить сборку, подключиться, посмотреть
`host_key`. `GENERATED` при уже авторизованном устройстве означает потерю
каталога, `LOADED` с прежним отпечатком и повторным диалогом — что забыло
устройство.

**Что сделано.** Сборка научилась брать отладочный ключ из переменной
`NEKOFLASH_DEBUG_KEYSTORE`, а CI — раскладывать его из секрета
`NEKOFLASH_DEBUG_KEYSTORE_BASE64` во временный каталог раннера. Файл в дерево
не кладётся: гейт гигиены запрещает `*.keystore` среди отслеживаемых файлов, и
запрещает правильно. Пока секрет не задан, поведение прежнее — сборка подписана
одноразовым ключом.

Секрет создаётся один раз на стороне владельца репозитория:

```
keytool -genkeypair -v -keystore ~/nekoflash-debug.keystore \
  -storepass android -keypass android -alias androiddebugkey \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -dname "CN=NekoFlash Debug,O=NekoFlash,C=US"
base64 -w0 ~/nekoflash-debug.keystore | gh secret set NEKOFLASH_DEBUG_KEYSTORE_BASE64
```

## 6.16. Разбор «приложение не видит устройство» — 2026-09-04

Два выгруженных evidence подряд оказались пустыми: `no events were recorded`,
`no sessions at export time`, `droppedEvents=0`.

**Что из этого следует.** Координатор пишет `device_ignored_no_usable_interface`
всякий раз, когда устройство видно, но подходящего интерфейса в нём нет. Этой
записи тоже нет, значит `getDeviceList` вернул пустой список: приложению не для

**Чего не хватило для ответа.** Ровно ничего в журнале не отличало «система не
отдала ни одного устройства» от «приложение не работает». Разбираться пришлось
по отсутствию записей — то есть по умолчанию, а не по свидетельству. Это дефект
самой диагностики, и он важнее конкретной причины.

**Что исправлено.**

- Скан пишет `scan_completed` всегда, включая случай нуля устройств, и
  сообщает, сколько система отдала, сколько разобрано впервые и сколько уже
  известно.
- `host.usbHostFeature` попадает в `host.txt`: сообщает ли платформа о
  поддержке host-режима USB вообще.
- Экран при пустом списке говорит, чего именно нет: host-режима, устройств или
  подходящего интерфейса.
- В манифест добавлено `<uses-feature android:name="android.hardware.usb.host">`.
  Его там не было ни разу за всю историю нового ядра, хотя платформа требует
  объявления от приложений, работающих с USB Host API, и часть систем без него
  не доставляет `USB_DEVICE_ATTACHED`. `required="false"` намеренно: `true`
  заблокировал бы установку на аппаратах, которые о фиче не сообщают.

**Что это не доказывает.** Отсутствие объявления не объявляется причиной: до
2026-09-03 на том же хосте всё работало. Причина станет видна из следующего
evidence — по `host.usbHostFeature` и `scan_completed`.

**Про роль `onyx` — исправлено.** В первой редакции этого раздела запись из
`KNOWN_USB_DEVICE_QUIRKS.md` была отнесена к хосту. Это неверное чтение: весь
материал того документа описывает `onyx` **в роли пациента**, то есть цели, и

владельца: как хост `onyx` работает нормально, проблемным он был именно как
цель.

`scan_completed` и `host.usbHostFeature` не скажут обратного.

## 6.24. Recovery на устройстве — 2026-09-05, PASS частичный

Другая цель: `serial:cc16218c`, `productId=0xD001`, интерфейс `ADB · CANONICAL`.

| Что наблюдалось | Результат |
|---|---|
| Режим peer'а | `RECOVERY` — определён из баннера, а не угадан |

| Возможности | 17 против 23 у обычной системы |
| Переподключение | второе поколение открылось и подключилось так же |

**Почему это важно.** До сих пор все прогоны шли против обычной системы, где
`adbd` требует подтверждения. Recovery подтверждает вторую ветку: соединение
устанавливается сразу, и предположение «диалог будет всегда» неверно. В
Recovery подтверждать его было бы некому — там нет экрана блокировки и
пользователя, который нажимает «Разрешить».

**Команды в Recovery — прогон 2026-09-05 20:48.** `id` вернул 272 байта,
`getprop ro.build.version.release` — 14, обе через `shell,v2,raw:`. Список
возможностей теперь виден в журнале, и `shell_v2` в нём есть: **Recovery
объявляет его наравне с обычной системой**. Ожидание, что откат сработает
именно здесь, не оправдалось.

**Откат на `shell:` по-прежнему не выполнялся на железе.** Сработает он на
peer'е без `shell_v2` — это Android 6 и старше либо Sideload. До такого прогона
ветка остаётся покрытой только тестами, и в `09` она отмечена частичной.

**Чего не хватило журналу.** Событие `connected` записывало **число**
возможностей, а не их список. По числу нельзя сказать, объявлен ли `shell_v2`, и
разбор упёрся в это сразу же. Исправлено: теперь записывается список.

**Что нашлось попутно.** Тест на новую запись упал и вскрыл настоящее
ограничение разбора: `features=` искались только среди частей, разделённых
точкой с запятой. Для баннера обычной системы это одно и то же — там перед
списком всегда есть свойства. Но `recovery::features=cmd` без единого свойства
был бы разобран как «возможностей нет», и команда ушла бы устаревшей веткой при
живом `shell_v2`. Разбор расширен, случай покрыт тестом.

и есть его след. До сих пор ветка была покрыта только тестами: обычная система
и Recovery объявляют `shell_v2` и предоставляют его, поэтому откат не
выполнялся ни разу.

**Главное, что здесь выяснилось.** Sideload **объявляет `shell_v2` в баннере, но
сервиса не предоставляет**. Объявленная возможность не является обещанием, что
сервис откроется. Именно поэтому откат делается не только когда `shell_v2` не
объявлен, но и когда объявлен, а поток не открылся — решение перенесено из
Legacy и теперь подтверждено наблюдением.

Обе команды в Sideload закончились отказом, и это правильный результат:
оболочки там нет вовсе, а отказ вернулся как отказ, а не как пустой вывод или
зависание.

## 6.30. Разбор AUTH без диалога — закрыт новым evidence

Предыдущие попытки с `vayu` на разных host-install состояниях доходили до
`auth_public_key_sent`, после чего на экране долго не было RSA-диалога.
Инструментирование `auth_response` было добавлено, чтобы отличить повторный
`AUTH TOKEN` от полного отсутствия ответа.

**Уточнение прежней интерпретации.** Отсутствие `auth_response` сразу после
`AUTH RSAPUBLICKEY` само по себе **не доказывает**, что ключ не дошёл до
`adbd`. После принятия публичного ключа daemon может ждать решение Android
framework/пользователя и не посылать новый ADB-пакет до подтверждения. Поэтому
старое чтение «тишина = пакет не дошёл или отвергнут» было слишком сильным и
здесь отменяется.

Фактический успешный прогон 2026-09-07:

| Момент | Что наблюдалось |
|---|---|
| 19:10:34.351 | `cnxn_sent` |
| 19:10:34.354 | `auth_required` |
| 19:10:34.383 | `auth_signature_sent` |
| 19:10:34.402 | `auth_response type=1`, через 19 мс |
| 19:10:34.403 | `auth_public_key_sent payload=719` |
| 19:10:47.693 | после подтверждения RSA-диалога пришёл `CNXN`, через 13 289 мс |
| 19:10:47.696 | `connected peerMode=DEVICE`, 23 capabilities |

Повторное подключение тем же сохранённым host key прошло без отправки public
key: `auth_signature_sent` → `CNXN` за **14 мс**. Это аппаратно доказывает и
первичную авторизацию, и сохранение/узнавание ключа устройством. Старый blocker
«authorization dialog не появляется» закрыт.

**Как теперь читать AUTH evidence.**

| Что в журнале | Что можно утверждать |
|---|---|
| `auth_public_key_sent`, затем тишина | только то, что хост успешно записал пакет и ждёт; из одной тишины нельзя вывести, дошёл ли framework до UI |
| повторный `AUTH TOKEN type=1` | peer продолжает требовать авторизацию; причина UI/отказа отдельно не доказана |
| `CNXN` после public key | авторизация подтверждена |
| следующий connect: signature → `CNXN` без public key | сохранённый ключ узнан |

## 6.31. Аудит согласованности и Terminal correctness — 2026-09-07

Это **software/static audit changeset**, а не новый аппаратный PASS. Он приводит
код и каноническую документацию в соответствие с уже действующим правилом:
NekoFlash — инструмент для профессионалов; correctness-защита обязательна, но
валидные возможности протокола не должны скрываться за product-level gate.

Исправлено по результатам полного прохода дерева:

- `README.md`, `docs/README.md`, roadmap и recovery handoff синхронизированы с
  фактической текущей **Phase 4**;
- нумерация evidence §6.x восстановлена: `6.5` снова стоит после `6.4`, а
  пропущенный номер перед интерактивной оболочкой устранён;
- `push` и `pull` больше не объединены одним статусом: read-only `RECV` существует
  в production-пути, `SEND` остаётся не начатой мутацией;
- блокирующий USB I/O Terminal больше не запускается из Compose callback/UI
  thread: чтение и запись имеют отдельные executors, при этом физический reader
  по-прежнему один;
- Terminal не принимает ввод до реального ADB `OKAY`: событие открытия потока
  проходит от `AdbStreamRouter` до UI как отдельное состояние `ready`;
- stdout/stderr/legacy shell декодируются потоковым UTF-8 decoder, поэтому
  многобайтовый символ не портится, если граница символа совпала с границей
  ADB-пакета или `shell,v2` frame;
- выгрузка diagnostics перенесена на `Dispatchers.IO`;
- добавлены unit-тесты для controller-level очередности Terminal и для чистой
  части `usb:android`; protocol-тестами закреплены `OKAY`, разрезанный UTF-8 и
  сохранение прежней очистки NUL в `shell,v2`;
- закрытие Terminal удерживает reader ownership до отправки корректного
  `CLSE` и выхода reader loop; если `OKAY` ещё не пришёл, закрытие сначала
  дожидается remoteId и не удаляет opening-stream преждевременно;
- стилевой detekt-run теперь охватывает production Kotlin всех семи модулей, а
  не только `app/src` и `core`; единственное явно зафиксированное rule-level
  исключение — `MagicNumber` для production source `protocol:adb`, где числа
  являются wire-format command words/masks/offsets/shifts; остальные правила
  detekt этот модуль продолжают проверять;
- крупный `NekoFlashApp.kt` разделён по ответственности, ADB UI/state вынесены
  из монолитного файла;
- добавлен CI-гейт `check_docs_consistency.py`: он сверяет current Phase между
  четырьмя входными документами, непрерывность нумерации evidence и фактическое

Текущий production-путь всё ещё **не является полноценным concurrent service
multiplexer**: постоянный physical reader/dispatcher, который одновременно
обслуживает несколько logical streams, остаётся отдельным пунктом Phase 4. Пока
он не построен и не подтверждён, одноразовые shell/file/service calls при живом
Terminal намеренно не запускаются параллельно. Это временное ограничение
реализации, а не продуктовый запрет capability.

## 6.32. AUTH, большой RECV и late `CLSE` — 2026-09-07

Этот прогон выполнялся уже после зелёного GitHub Actions для
`c1478aa932c485c1179108e5897c88d20f0e05e3`. Он закрыл два аппаратных вопроса
Phase 4 и одновременно обнаружил один protocol-correctness defect.

**AUTH — PASS.** Первичная авторизация прошла через `AUTH TOKEN` → signature →
повторный token → `AUTH RSAPUBLICKEY` → системный RSA-диалог → `CNXN`. После
подтверждения устройство подключилось, а повторное подключение тем же ключом
дало `CNXN` через 14 мс без повторной отправки public key. Полная последовательность
и исправленная трактовка тишины после public key записаны в §6.30.

**Read-only Sync / RECV — PASS по критерию целостности.** Малый файл дал
`STAT size=10` и `RECV bytes=10`. Файл 2 MiB дал `STAT size=2097152`,
`RECV bytes=2097152`; SHA-256 на экране NekoFlash совпал с эталоном:
`5647f05ec18958947d32874eeb788fa396a05d0bab7c1b71f112ceb7e9b31eee`.
Подробности — §6.29.

**Найден late `CLSE`.** После освобождения и нового захвата интерфейса одна
попытка отправила новый `CNXN`, но первым входящим пакетом оказался
`command=0x45534c43` (`CLSE`) от logical stream предыдущего соединения. Старый
handshake трактовал любой пакет кроме `CNXN/AUTH` как фатальный и завершился
`UNEXPECTED_COMMAND`; следующая попытка через 10 секунд подключилась нормально.

Это не причина скрывать повторное подключение. `CLSE` с stream IDs до ответа
на новый `CNXN` не может быть ответом handshake и является поздним закрытием
старого logical stream. Исправление узкое: до первого `CNXN/AUTH` handshake
пропускает ограниченное число именно `CLSE`, записывая
`handshake_stale_close` с remote/local IDs. Другие неожиданные команды
по-прежнему фатальны; framing errors не игнорируются.

**UI AUTH.** Состояние «ждём авторизацию» раньше выставлялось до вызова
`connection.connect()`, то есть UI мог предлагать подтвердить RSA ещё до
фактического `AUTH RSAPUBLICKEY`. Теперь оно появляется только после успешной
записи public key. Текст также описывает факт протокола и лишь условно сообщает,
что обычный Android может показать RSA-диалог.

**Diagnostics.** Успешный `sync_received` теперь содержит `path`, `bytes` и
`sha256`. Следующий hardware bundle сможет сам доказать целостность RECV без
отдельного скриншота.

Аудит без нового кода и без аппаратного прогона: проверка того, что документы
говорят то же, что делает код. Проверено на `b3a6642`.

**Подтверждено независимо от гейтов.** 372 `@Test` — ровно столько, сколько
заявляет `99_RECOVERY_HANDOFF_RU.md`. Три архива сходятся с

300–449. Направление зависимостей и `api()` вместо `implementation()`
соблюдены во всех семи модулях. В production нет ни `TODO/FIXME/HACK`, ни
`NotImplemented`, ни `.orig`. Продуктовый закон держится и в коде: ни

`AdbServiceCall` принимает произвольное имя сервиса, а его пределы — ресурсные

заголовок добирается циклом до 24 байт, payload читается одной операцией,
короткий результат даёт `SHORT_PAYLOAD` fail-closed.

**Найдено три расхождения, все документационные. Дефектов корректности нет.**

- `09_IMPLEMENTATION_ROADMAP_RU.md` утверждал, что `CNXN` ещё не объявляет
  `maxdata`. Объявляет: `AdbConnection` считает значение один раз и отдаёт его

  над свойством `peerFeatures`, а сама `connect()` осталась без документации.
  Kotlin привязывает только последний блок, поэтому ни компилятор, ни detekt
  этого не видят. Проход по всему дереву показал, что случай единственный;

провода, а не production stub: значения принадлежат протоколу целиком, и
объявлять их по одному вместе с командами значило бы разносить один формат по
разным changeset'ам. `emptyStateReason` в `:app` содержит выбор из четырёх

покрывается; это отступление от принципа §6.4 и кандидат на вынос чистой части,
но не нарушение контракта.

## 6.34. Аппаратный гейт записи файла — план; закрыт прогонами §6.36 и §6.38

Раздел написан **до** прогона. `SEND` — первая мутация в проекте, и критерий,
придуманный после того, как результат виден, критерием не является.

**Что проверяется.** `AdbSyncSession.send`: спецификация назначения, поток
блоков `DATA`, `DONE` со временем изменения и вердикт устройства. Отдельно —
что о состоянии файла назначения сообщается ровно то, что доказано.

**Почему гейт нельзя пропустить.** Ни один тест здесь не отвечает на главный
вопрос: в какой момент `adbd` создаёт и обрезает файл. Подставной транспорт
знает только то, что заложил автор. До прогона граница мутации остаётся
консервативным предположением, а не измеренным фактом.

| Сценарий | Что должно наблюдаться |
|---|---|
| Запись малого файла в `/sdcard` | `OKAY`; `sync_sent` с `bytes` и `sha256`; `sha256sum` на устройстве совпадает с отпечатком на экране |
| Запись файла больше 2 MiB | то же; блоки идут по 64 КиБ, память приложения не растёт пропорционально файлу |
| Запись в `/system` без прав | `FAIL` с настоящим текстом устройства; исход `DEVICE_REFUSED`, назначение `UNKNOWN` |
| Перезапись существующего файла | `OKAY`; отпечаток совпадает с новым содержимым, а не со старым |
| Отключение кабеля посреди `DATA` | назначение `UNKNOWN`, автоматического повтора нет |
| Режим созданного файла | вне `/sdcard`: `ls -l` показывает переданный режим. На `/sdcard` строка непроверяема — эмулированное хранилище навязывает свои права (§6.38), и это ответ устройства, а не наш дефект |

**Критерий PASS.** Наблюдаются первые пять сценариев плюс режим созданного
файла, evidence выгружен приложением, `droppedEvents=0`, отпечатки совпадают.

**Строка про границу мутации в критерий PASS не входит и входить не может.**
Она не проверяет реализацию, а измеряет предположение, на котором реализация
построена. Формулировка этой строки в первой редакции была негодной, и прогон
§6.36 это показал: «посмотреть, существует ли файл» **не различает две
гипотезы**. «Файл не создавался» и «файл создан, а при обрыве `adbd` его
удалил» дают одинаковый ответ `STAT` с нулевым режимом. Разница же
принципиальная: во втором случае назначение было мутировано, и лежавший там
раньше файл уничтожен.

Решающий сценарий — §6.37: писать поверх **существующего** файла с известным
отпечатком и оборвать передачу. Уцелевшее старое содержимое доказывает, что
`SEND` назначения не тронул; изменившееся или исчезнувшее — что тронул.

**Чем нажимать.** В секции «Файлы устройства» появились кнопки «Записать
4 КиБ» и «Записать 16 МиБ». Содержимое порождает само приложение: выбор
пользовательского файла требует artifact source из Phase 8, а для этого гейта
он и не нужен — проверяется протокольный путь, а не сценарий push. Узор
детерминирован, поэтому прогон воспроизводим, и его период — простое число,
чтобы перепутанные местами блоки не дали тот же отпечаток.

Малый размер проходит одним блоком, большой — двумястами пятьюдесятью шестью;
шестнадцати мегабайт хватает и на требование «больше 2 MiB», и на то, чтобы
успеть выдернуть кабель посреди передачи.

**Чего гейт не закрывает.** Пользовательский push: выбрать свой файл всё ещё
нельзя. Гейт проверяет протокольный путь.

## 6.37. Аппаратный гейт границы мутации — план; закрыт прогоном §6.38

Раздел написан до прогона. Гейт измеряет предположение, на котором построен
`AdbSyncSendOutcome`: что запрос `SEND` уже меняет назначение.

**Почему §6.36 не ответил.** Там писали в несуществующий путь, и отсутствие
файла после обрыва одинаково объясняется двумя противоположными гипотезами.
Различить их можно только по судьбе **уже лежащего** там содержимого.

| Шаг | Что сделать |
|---|---|
| 1 | Записать 4 КиБ в `/sdcard/nf-b.bin`, запомнить отпечаток |
| 2 | Сверить `sha256sum /sdcard/nf-b.bin` — исходное состояние зафиксировано |
| 3 | Записать в **тот же** путь 16 МиБ и выдернуть кабель через 1–2 с |
| 4 | Переподключиться, `Проверить` путь — записать режим и размер |
| 5 | `sha256sum /sdcard/nf-b.bin` и `ls -l /sdcard/nf-b.bin` |

**Как читать результат.**

- отпечаток шага 5 равен отпечатку шага 2 → `SEND` назначения **не тронул**,
  и граница мутации может быть ослаблена до первого блока `DATA` — отдельным
  решением, потому что это меняет, когда операция вправе отвечать `Cancelled`;
- отпечаток изменился, размер другой или файл исчез → `SEND` тронул
  назначение, и текущая консервативная граница **доказана**;
- результат плавает от прогона к прогону → граница остаётся консервативной,
  и это записывается как свойство устройства, а не как неудача.

Повторить не менее трёх раз: одиночный результат здесь ничего не значит.

**Чего гейт не решает.** Ответ верен для этой версии `adbd` и этой файловой
системы. Переносить его на другие устройства без своего прогона нельзя —
`16_AGENT_OPERATING_PROMPT_RU.md` §3 про квирки в роли.

## 6.39. Аппаратный гейт одновременных потоков — план, прогон не проведён

Раздел написан **до** прогона. `docs/adr/0004_CONCURRENT_ADB_DISPATCHER_RU.md`
принят не будет, пока эти строки не отработают на устройстве: одновременность
не проверяется ни сборкой, ни подставным транспортом. 407 локальных тестов
показывают раскладку по ящикам и остановку цикла — но подставной транспорт
отдаёт записанные ответы, а не гоняет два настоящих потока по одному проводу.

**Что изменилось.** Читающий цикл переехал в `AdbConnection` и стал один на
соединение; потребители ждут каждый на своём ящике; `busy()` снят, и экран
больше не гасит кнопки при живой оболочке; операции идут на пуле потоков, а не
в одной очереди.

**Сборка.** Записать здесь коммит, на котором шёл прогон, и `droppedEvents`
из архива. Без этого прогон не считается.

**Подготовка.** Шаг 9 требует **большого** файла, и это не придирка к размеру.
Два мебибайта читаются меньше секунды: по §6.36 скорость около 14 МБ/с, и попасть
выдёргиванием кабеля в такое окно нельзя. Первая редакция гейта этого не учла и
предписывала невыполнимый шаг. Нужен отдельный файл, чтение которого длится
секунды:

    dd if=/dev/zero of=/sdcard/nekoflash-big.bin bs=1M count=128

128 МиБ на этой скорости читаются около десяти секунд — окна хватает. Файл шага 5
для этого не годится: он служит сверке отпечатка и должен остаться нетронутым.

**Подготовка.** Шаг 5 сверяется с §6.29, поэтому нужен тот же файл —
`/sdcard/nekoflash-2m.bin`, два мебибайта нулей. Если его на устройстве не
осталось, он воспроизводится точно: `dd if=/dev/zero of=/sdcard/nekoflash-2m.bin
bs=1M count=2`. Содержимое детерминировано, поэтому отпечаток §6.29
`5647f05ec18958947d32874eeb788fa396a05d0bab7c1b71f112ceb7e9b31eee` остаётся
годным для сверки — это проверено арифметически, а не предположено.

## 6.44. Аппаратный гейт перезагрузки — план, прогон не проведён

Раздел написан **до** прогона. `reboot:` — односторонний сервис, и проверить
его подставным транспортом нельзя по той же причине, по которой он и особенный:
успех здесь выглядит как обрыв, а обрыв подставного транспорта устраивает не
устройство, а тест.

**Что проверяется.** Что успешная перезагрузка отличается от неудачной. Обе
кончаются потерей соединения, и если приложение не умеет их различать, оно
будет сообщать успех всегда — в том числе когда устройство отказало.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Подключиться, оставить поле цели **пустым**, нажать «Перезагрузить» | `reboot_requested service=reboot:`, затем `reboot_accepted`; устройство уходит в перезагрузку |
| 2 | Дождаться загрузки, подключиться снова | `reboot_accepted` не помешал следующему поколению: generation растёт, рукопожатие проходит |
| 3 | Цель `bootloader`, нажать «Перезагрузить» | `reboot_accepted service=reboot:bootloader`; устройство ушло в загрузчик |
| 4 | Вернуть устройство в систему, подключиться | подключение проходит |
| 5 | Цель `нетакойцели`, нажать «Перезагрузить» | **вот здесь главное**: что ответит устройство. Записать `reboot_failed` целиком — `reason`, `device`, `detail` |
| 6 | Открыть оболочку, не закрывая её — нажать «Перезагрузить» с пустой целью | перезагрузка уходит своим потоком; в журнале виден её `stream=`, отличный от `stream=` оболочки |

**Как читать результат.**

- шаги 1–4 прошли → протокольный путь верен, и пункт чеклиста можно закрывать;
- ~~шаг 5 дал `reboot_accepted` → это дефект~~ — **критерий был неверен, и это
  исправлено после прогона §6.46**. Он опирался на предположение, что `adbd`
  отвергнет незнакомую цель. Железо показало обратное: причина перезагрузки —
  произвольная строка, и устройство перезагружается с любой. Ошибка была в
  представлении автора гейта об устройстве, а не в коде;
- шаг 5 дал `reboot_failed` с `device=UNTOUCHED` → верно: устройство отказало
  словами, ничего не тронуто, повтор безопасен;
- шаг 5 дал `NO_TRANSITION` с `device=UNKNOWN` → устройство промолчало и не
  ушло с шины. Тоже верно, но записать отдельно: значит, эта версия `adbd` на
  неизвестную цель не отвечает вовсе, и это свойство устройства.

**Чего гейт не проверяет.** Оборванную отправку самого запроса: попасть
выдёргиванием кабеля в 24 байта заголовка нельзя. Ветки `SEND_FAILED` и
`FRAMING_LOST` остаются на тестах, и это записано честно, а не выдано за
проверенное.

**Отдельно про шаг 5.** Цель не ограничивается списком (`01` §3), поэтому
«нетакойцели» — не диверсия, а обычный ввод, на который у устройства есть свой
ответ. Гейт проверяет, что мы этот ответ передаём, а не подменяем своим.
## 6.45. Аппаратный гейт произвольного сервиса — план, прогон не проведён

Раздел написан **до** прогона. Проверяется не «сервис вызвался», а три вещи,
которые подставным транспортом не проверяются: что имя уходит как набрано, что
ответ не текстового сервиса не выдаётся за текст и что односторонний сервис
узнаётся **по имени**, откуда бы его ни набрали.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Вызвать `shell:id` | `service_completed`; на экране размер в байтах и текст `uid=…` |
| 2 | Вызвать `sync:` | ожидается `TIMED_OUT` примерно через 30 с: сервис открылся, но ждёт бинарных запросов, которых поле ввода не шлёт. Важно, что вызов **кончается сам** и не роняет соединение |
| 3 | Вызвать `exec:id` | ответ без рамок `shell,v2`: сравнить с шагом 1 и записать разницу |
| 4 | Вызвать `нетакогосервиса:` | `service_failed reason=REJECTED`; соединение живо, следующий вызов проходит |
| 5 | Вызвать `reboot:` **из этого поля** | **главная строка**: `reboot_requested` и `reboot_accepted` в журнале, на экране «принят, устройство ушло с шины» — а не отказ |
| 6 | После перезагрузки подключиться и вызвать `shell:id` | соединение восстановилось, вызовы идут |

**Как читать результат.**

- шаг 5 показал отказ → дефект: одностороннюю политику применили не по имени
  сервиса, и экран соврал про то, что произошло на самом деле;
- шаг 4 оборвал соединение → дефект: отказ в сервисе не должен ронять
  транспорт, это подтверждалось ещё в §6.29 для `RECV`;
- шаг 2 повис навсегда или оборвал соединение → дефект; `TIMED_OUT` через
  отведённое время — верный исход, а не неудача гейта.

**Про нетекстовый ответ.** Ни один шаг выше его не даёт: у `sync:` ответа не
будет вовсе, а `shell:` и `exec:` отвечают текстом. Показ размера отдельно от
текста поэтому остаётся проверенным только тестами, и записать это надо прямо,
а не считать проверенным заодно. Сервис, который отдаёт байты и сам закрывает
поток, на подопытном устройстве ещё предстоит найти.

**Чего гейт не проверяет.** Сервисы, которых нет на подопытном устройстве, и
поведение при выводе больше 64 КиБ — потолок вызова обрезает раньше, и это
свойство `AdbServiceCall`, а не произвольного сервиса.
## 6.46. Перезагрузка и произвольный сервис — 2026-09-10, PASS и найденный дефект

Гейты §6.44 и §6.45 отработали за один прогон. Сборка `584c505`,
`droppedEvents=0`. Всё, что гейты просили, прошло, и сверх того нашёлся
**дефект в моём коде**, который не мог найтись иначе.

**Произвольный сервис — PASS по всем строкам.**

| Сервис | Итог |
|---|---|
| `shell:id` | `service_completed bytes=263` |
| `sync:` | `TIMED_OUT` ровно через 30 с; соединение живо, следующий вызов прошёл |
| `exec:id` | `service_completed bytes=263` — **тот же размер**, что у `shell:id` |
| `нетакогосервиса:` | `REJECTED`, `closed before OKAY`; соединение живо |
| `reboot:` из поля сервиса | `reboot_requested` → `reboot_accepted` |

Последняя строка была главной, и она прошла: односторонняя политика применилась
**по имени сервиса**, а не по нажатой кнопке.

Совпадение размеров у `shell:id` и `exec:id` стоит записать: гейт ожидал
разницы в рамках, а её нет, потому что `shell:` без `,v2` рамок и не имеет.
Разница появилась бы при сравнении с `shell,v2,raw:`, а не с `shell:`.

**Перезагрузка — PASS, и один результат решающий.**

| Цель | Что наблюдалось |
|---|---|
| пустая | `accepted evidence=transport closed`, generation 1 закрыта `DETACHED`, устройство вернулось |
| `нетакойцели` | `accepted`, устройство **перезагрузилось** и вернулось как ADB |
| `bootloader` | `accepted`, generation 4 поднялась с интерфейсом **FASTBOOT** |
| `recovery` | `accepted`, устройство вернулось как ADB в recovery |

Строка `bootloader` — самая убедительная: смена роли интерфейса на `FASTBOOT`
это наблюдение, а не толкование. Устройство действительно ушло в загрузчик.

**Критерий гейта §6.44 про несуществующую цель был написан неверно, и это моя
ошибка.** Гейт говорил: `reboot_accepted` на цель `нетакойцели` — дефект.
Железо показало обратное: `adbd` принимает любую строку как причину
перезагрузки и перезагружается. Ошибка не в коде, а в предположении автора
гейта о том, как устроено устройство. Строка исправлена — но исправлена **после**
прогона и потому помечена как исправленная, а не переписана молча.

### Найденный дефект: `UNTOUCHED` после границы мутации

Пятый запрос ушёл, когда устройство было **в recovery**. Ответ:

    19:10:52.624  reboot_failed reason=DEVICE_REFUSED device=UNTOUCHED detail=reboot.
    19:10:52.960  usb session_closed_detached generation=6
    19:11:08      generation 7 — устройство вернулось

Мы сказали оператору «устройство не тронуто» — и **через 336 мс** устройство
ушло в перезагрузку. Recovery ответила словом `reboot.` и перезагрузилась.

Дефект не в том, что мы не угадали смысл слова `reboot.`. Дефект в том, что
ветка ответа текстом стоит **после границы мутации** — `OPEN` к тому моменту
записан целиком, — а отвечала `UNTOUCHED`. Правило про границу записано в KDoc
того же класса с самого начала: до границы устройство не тронуто, после —
доказать это нечем. Ветка его нарушала.

Исправлено тем же changeset: причина переименована в `DEVICE_ANSWERED`,
состояние — `UNKNOWN`. Слово устройства передаётся оператору дословно и не
переводится в вердикт: что оно значит, знает устройство, а приписывать ему
решение, которого оно не выносило, — то же самое враньё, только вежливое.

**Что это стоит помнить.** Тесты этот случай пропустили не по невнимательности:
они проверяли то же самое утверждение, которое было неверным. Проверка
называлась `textFromTheDeviceIsARefusalAndNotATransition` и добросовестно
закрепляла ошибку. Такое ловится только устройством.

**Возможное улучшение, у которого пока нет гейта.** Если после ответа текстом
подождать смерти транспорта, случай recovery превратился бы из `UNKNOWN` в
честный `Accepted`. Это изменение поведения, и делать его без своего гейта
нельзя — гейт пишется первым; он записан как §6.47.

**Поправка к этому абзацу, сделанная при подготовке §6.47.** Сначала здесь
было сказано, что такое окно «держал Legacy», со ссылкой на
`EXPECTED_REBOOT_DISCONNECT_WINDOW_NS`. Это неверно, и ошибка моя: константа
была найдена грепом, а её использование не открыто. Пятнадцать секунд в Legacy
нужны **читающему циклу** — чтобы последующий обрыв транспорта не
эскалировался как ошибка операции (`AdbProtocol.kt:2540`); исход же сервиса
Legacy решает на `A_CLSE` и возвращает успех независимо от того, сказало
устройство что-нибудь или нет. Идея «подождать смерти транспорта после ответа
текстом» — наша, а не архивная, и приписывать её Legacy нельзя. Ровно от этого
предостерегает `16` §3, и предостережение сработало не зря.
## 6.47. Гейт ожидания разрыва после ответа текстом — план, прогон не проведён

Раздел написан **до** кода и до прогона. Закрывает то, что осталось от §6.46:
recovery отвечает словом и уходит в перезагрузку, а мы отвечаем `UNKNOWN`.

**Что меняется.** После ответа текстом решение не принимается сразу. Мы ждём —
не дольше отдельного небольшого окна, — умрёт ли транспорт. Умер: устройство
ушло с шины, значит перешло, и это `Accepted`; слова устройства при этом
переносятся в evidence целиком. Не умер: устройство ответило и осталось, и
состояние остаётся `UNKNOWN`.

**Почему не проще.** Рассматривались три варианта, и два отвергнуты.

| Вариант | Почему нет |
|---|---|
| Считать закрытие потока успехом, как Legacy | Настоящий отказ «not permitted» стал бы `Accepted`. Это ложь в сторону, где оператор поверит, что устройство перезагружается, и уйдёт ждать |
| Оставить `UNKNOWN` навсегда | Не врёт, но в частом случае даёт худший ответ, чем позволяет наблюдение |
| **Ждать смерти транспорта** | Различает случаи **наблюдением**, а не толкованием текста устройства |

Толковать текст мы по-прежнему не будем: `reboot.` и `not permitted` для нас
одинаково непрозрачны, и решает не их смысл, а ушло ли устройство с шины.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Перевести устройство в recovery (`reboot:recovery`) и дождаться подключения | generation поднялась, ADB отвечает |
| 2 | В recovery нажать «Перезагрузить» с пустой целью | `reboot_accepted`, и в `evidence` видны **и слова устройства, и уход с шины** |
| 3 | Дождаться загрузки, подключиться | устройство вернулось; `reboot_failed` в журнале за этот запрос нет |
| 4 | В обычной системе повторить пустую цель | `reboot_accepted` как в §6.46 — поведение без текста не изменилось |
| 5 | Повторить `bootloader` | `accepted`, интерфейс поднимается как `FASTBOOT` — прежний результат не сломан |

**Как читать результат.**

- шаг 2 дал `accepted` со словами устройства в evidence → улучшение работает,
  и §6.46 закрыт;
- шаг 2 дал `accepted` **без** слов в evidence → мы потеряли то, что сказало
  устройство. Не катастрофа, но дефект: слова оператору нужны;
- шаг 2 дал `DEVICE_ANSWERED`/`UNKNOWN` → сравнить измеренную паузу из журнала
  (`reboot_failed` и соседний `session_closed_detached`) с окном. Пауза **больше**
  окна — окно мало, менять по измеренному числу. Пауза **меньше** — дело не в
  окне, а в сигнале: смотреть, откуда узнаётся уход с шины. Второй случай
  и произошёл, см. §6.48; в первой редакции этой строки он предусмотрен не был;
- шаги 4 и 5 изменились по сравнению с §6.46 → регрессия: улучшение задело
  путь, которого не должно было касаться.

**Чего гейт не проверяет, и это важно.** Случай «устройство ответило текстом и
осталось на шине» на подопытном устройстве вызвать нечем: отказать в
перезагрузке `vayu` не отказывается. Ветка «окно истекло, транспорт жив»
остаётся на тестах, и записать это надо прямо, а не считать проверенным
заодно. Именно в этой ветке живёт `UNKNOWN`, ради которого всё и затевалось.

**Мера предосторожности.** Ожидание добавляется **после** ответа и потому может
увеличить общее время вызова сверх запрошенного таймаута. Это осознанно: цена —
несколько секунд ожидания, выигрыш — верный ответ вместо «не знаю».
## 6.48. Ожидание разрыва не сработало — 2026-09-10, дефект найден и исправлен

Гейт §6.47 отработал и **провалил** улучшение. Сборка `905abb7`,
`droppedEvents=0`. Провал полезнее, чем прошёл бы успех: он показал, что
неверен был не размер окна, а сам сигнал.

**Что наблюдалось.** Второй запрос ушёл из recovery:

    19:42:23.246  reboot_requested service=reboot:bootloader
    19:42:23.552  usb session_closed_detached generation=2
    19:42:25.288  reboot_failed reason=DEVICE_ANSWERED device=UNKNOWN detail=reboot-bootloader.
    19:42:27.217  usb session_opened generation=3 interfaceKind=FASTBOOT

Устройство ответило словом `reboot-bootloader.` и ушло с шины через **306 мс**
— то есть глубоко **внутри** двухсекундного окна. Мы всё равно ответили «не
знаю», а ещё через две секунды устройство поднялось загрузчиком.

**Диагноз гейта не подошёл, и это надо сказать прямо.** §6.47 предусматривал
единственную причину такого исхода: «окно короче, чем пауза устройства», и
предписывал измерить паузу. Пауза измерена — 306 мс, — и она в шесть раз
меньше окна. Причина оказалась другой, гейтом не предусмотренной.

**Настоящая причина.** `transportEnd` смотрел только на цикл раскладки, а цикл
знает лишь те беды, которые принёс сам: обрыв чтения и потерю кадра. В
production об отпадении устройства первым узнаёт USB-слой — он закрывает
сессию, владелец закрывает соединение, и цикл кончается **по просьбе**. Его
поле в этом случае пусто, что видно и по evidence успешных перезагрузок:
`dispatch loop stopped`, а не `transport closed`.

Я исключил остановку по просьбе намеренно и написал в KDoc, что путать её со
смертью транспорта нельзя. Рассуждение верное, вывод неверный: смерть
транспорта эту остановку и **вызывает**.

**Исправление.** Спрашивать надо у транспорта, а не выводить из цикла:
интерфейс больше не удерживается — значит устройства нет. Причина, названная
самим циклом, остаётся весомее: она точнее. Решение вынесено в
`AdbTransportEnd.of(loopEnd, held)` и покрыто тремя проверками, среди которых
ровно та комбинация, что провалилась здесь: цикл молчит, интерфейс отпущен.

**Чего этот прогон не отменяет.** Первый запрос (`reboot:recovery` из системы)
прошёл как `accepted`, и `bootloader` поднял FASTBOOT-интерфейс — прежние
результаты §6.46 не сломаны. Улучшение не сломало ничего; оно просто не
работало.

**Что осталось непроверенным.** Само улучшение на железе так и не
подтверждено: прогон показал, что его не было. Гейт §6.47 остаётся открытым и
повторяется на исправленной сборке — шаги те же.

## 6.49. Сборка упала на гонке в тесте — 2026-09-10, разбор и исправление

**Сначала о своей ошибке.** Я отчитался об исправлении §6.48, не дождавшись
сборки. Сборка упала, и заметил это не я. Отчёт до зелёного CI — это не отчёт,
и правило простое: сначала прогон, потом слова.

**Что упало.** Run 97, `dd2d4d5`:

    AdbServiceCallTest > closedStreamIsAcknowledgedBack FAILED
        java.lang.AssertionError at AdbServiceCallTest.kt:60
    289 tests completed, 1 failed

**Это не тот коммит.** Ни `dd2d4d5`, ни `905abb7` не трогают ни
`AdbServiceCall`, ни его сюиту, а `1cd2816` и `905abb7` прошли зелёными.
Коммит не сломал тест — он изменил раскладку по времени ровно настолько, чтобы
уже существующая гонка сработала. Списывать такое на «флаки» нельзя: причина
находится и оказывается настоящей.

**Причина.** Проверка наблюдала **чужой** поток. Ответное `CLSE` на закрытие
устройства пишет цикл раскладки, и пишет он его **после** `dispatcher.dispatch`
— а разбудил вызов `dispatch` уже внутри себя, закрыв ящик. Между «вызов
вернул `Completed`» и «подтверждение ушло на провод» порядка нет, и снимок
`sentFrames()` сразу после `run` показывал последним кадром `OPEN`.

**Порядок остаётся таким намеренно.** Отправлять подтверждение под замком
диспетчера значило бы держать замок всё время передачи — до пяти секунд по
`AdbPacketWriter.DEFAULT_SEND_TIMEOUT_MS` — и блокировать этим `open`, `write`
и `close` чужих потоков, то есть ровно ту одновременность, ради которой
затевался ADR-0004. Неверна была проверка, а не код: она утверждала
последовательность, которой система не обещает и обещать не должна.

**Гейт записан до исправления.** Воспроизведение — одно ядро, `taskset -c 0`:
на нём планировщик отдаёт потоки крупными кусками, и окно гонки становится
широким. Критерий: до исправления класс падает, после — не падает ни разу за
30 прогонов на тех же условиях.

Замер до исправления: `AdbServiceCallTest` в одиночку — **20 падений из 45**.
Вся сюита на том же ядре — 0 из 6: полная сюита прогревает JIT и окно
закрывается, поэтому одиночный класс здесь показательнее.

**Исправление.** В подставном транспорте появилось ожидание
`awaitSentFrames(count)`: «мы отправили X» проверяется дождавшись, а не
снимком. Заодно `sentFrames()` научилась отбрасывать незаконченный хвост —
снимок, взятый между заголовком и payload чужого потока, раньше падал по
выходу за границу списка, и выглядело бы это как поломка писателя.

**Тот же класс нашёлся ещё дважды.**

- `outputBeyondTheCapStopsTheCall`: `OKAY` за второй блок пишет цикл, а `CLSE`
  — сам вызов. «Последний кадр» здесь не был свойством никогда; проверяется то,
  что и требуется: поток закрыт ровно один раз.
- `AdbInteractiveShellTest.pumpingAfterExitDoesNothing`: сравнивал два снимка
  недоделанной работы, и потому обычно проходил. Ожидание показало, что кадров
  на самом деле три (`OPEN` и `CLSE` от сессии, `OKAY` от цикла), а не два, как
  я предположил при исправлении — предположение проверил тест, а не я.

**Результат.** На одном ядре по 30 прогонов: `AdbServiceCallTest`,
`AdbInteractiveShellTest`, `AdbRebootTest`, `AdbConcurrentStreamsTest`,
`AdbSyncSessionTest`, `AdbSyncSendTest`, `AdbConnectionTest`,
`AdbHandshakeTest`, `AdbStreamDispatcherTest` — 0 падений у каждого.

**Чего это не доказывает.** Одно ядро — модель планировщика CI, а не сам CI.
Подтверждением остаётся зелёный прогон.
