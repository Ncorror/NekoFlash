# ADR-0003 — Технический базис Phase 2

Статус: **ACCEPTED**
Дата: **2026-08-30**
Вводит: D032, D033

## Контекст

Phase 2 (USB + Target/Session) — первый слайс с реальным асинхронным вводом-выводом, владением ресурсами и временем жизни. Три решения до сих пор существовали неявно. Их надо зафиксировать до кода, а не после: в Legacy отсутствие такого решения дало цепочки `Handler.postDelayed` (`scheduleUsbPermissionTimeout`, `scheduleStartupUsbDiscovery`), а отсутствие анализатора размера/сложности позволило вырасти файлам на 2000–4000 строк никем не остановленными.

## Решение

### 1. Направление зависимостей выражается через `api`, а не `implementation`

Модуль, чей публичный API раскрывает типы другого модуля, объявляет эту зависимость как `api(...)`.

Текущее состояние нарушало это правило: `OperationContext.targetId: TargetId` и `DiagnosticEvent.targetId: TargetId?` — публичные члены, но `:core:model` объявлен как `implementation`. Проверено экспериментально: потребитель, видящий только `core:operation`, не компилируется — `cannot access class TargetId`. Сейчас это скрыто тем, что `:app` объявляет `:core:model` напрямую; `usb:api` и `protocol:*` из Phase 2 упрутся в это сразу.

Для получения семантики `api` в Kotlin JVM модулях применяется плагин `java-library`.

### 2. Конкурентная модель — `kotlinx.coroutines` + `Flow`

- structured concurrency; каждый запуск принадлежит явному scope;
- `CoroutineScope` привязан ко времени жизни `SessionGeneration`: detach/re-enumeration отменяет scope, старые задачи не переживают generation;
- никаких голых `Thread`, `Handler.postDelayed` и callback-цепочек в новом коде;
- наблюдаемое состояние — `Flow`/`StateFlow`, а не мутируемые поля с колбэками, как в Legacy `AdbProtocol`, державшем `onLog`/`onProgress` прямо в протокольном классе;
- ожидаемые протокольные исходы моделируются `OperationOutcome`/sealed-типами, исключения — только для программистских ошибок и невозможных состояний.

### 3. Dependency injection — ручной, пока это оправдано

DI-библиотека не вводится. На текущем масштабе явная сборка графа в `:app` читаема, не требует кодогенерации и не добавляет времени сборки в CI, который является единственной авторитетной средой сборки. Решение пересматривается отдельным ADR, когда ручной граф станет трудно поддерживать.

### 4. Статический анализ — обязательный CI-гейт

Вводится анализатор стиля и сложности Kotlin (ktlint или detekt) как обязательный шаг GitHub Actions, включая правила на размер файла/класса и на нежелательные импорты между модулями — чтобы направление зависимостей раздела 1 проверялось машиной, а не только на ревью.

Ориентиры размера (сигнал для ревью, не отказ компилятора): файл/класс свыше ~300–400 строк или ~15–20 публичных членов — пауза «точно ли это одна ответственность»; свыше ~800 строк без обоснования в ADR — блокирующее замечание.

Гейт настраивается **отдельным проверяемым changeset**, а не вместе с этим решением: включение анализатора меняет конфигурацию Gradle и может потребовать правок существующего кода, что должно быть видно в CI изолированно.

## Последствия

- `core:operation` и `core:diagnostics` получают `java-library` и `api(project(":core:model"))`; `usb:api` и `protocol:*` смогут зависеть только от нужного модуля.
- `kotlinx.coroutines` появляется в version catalog при первом использовании в Phase 2, а не заранее пустой зависимостью.
- Отсутствие DI-библиотеки — осознанный выбор, а не упущение; его не нужно «исправлять» без нового решения.
- Статический анализ станет причиной отдельного красного CI при внедрении; это ожидаемо и лучше, чем обнаружить накопленный долг позже.
- Алиас плагина `android-library` в `build.gradle.kts` и version catalog объявлен `apply false` и пока не используется ни одним модулем. Это не заброшенный артефакт: он нужен модулю `usb:android` этой же фазы. Правило «модули не создаются пустыми» из ADR-0001 относится к Gradle-модулям, а не к объявлению плагина.
