# NekoFlash — Testing, CI & Hardware Evidence

## 1. Тесты строятся по слоям

### Pure unit
- codecs/parsers;
- state machines;
- byte accounting;
- advisory classification;
- artifact logic;
- correlation logic.

### Protocol simulation
Fake peer/transport должен уметь моделировать:
- short reads/writes;
- packet fragmentation;
- delayed responses;
- duplicate/out-of-order relevant events;
- stream concurrency;
- malformed frames;
- `INFO/TEXT/FAIL` sequences;
- DATA length mismatch;
- disconnect at every interesting byte/state boundary.

### Integration
- Android USB permission/session ownership;
- foreground operation service;
- persistence/process recreation;
- SAF seekable/non-seekable providers where testable.

### Hardware
Нужен matrix реальных устройств/режимов, потому что USB host stacks и Recoveries имеют vendor quirks.

## 2. Hardware evidence policy

Hardware-sensitive change не считается proven только по unit tests.

Evidence bundle должен содержать:
- app commit/build identity;
- host device identity;
- target identity;
- mode;
- timestamps;
- relevant structured logs/transcript;
- exact byte counts;
- screenshots только как дополнительное подтверждение, не вместо logs;
- PASS criteria.

## 3. Reference devices

### `vayu`
Стабильный reference target для A2 evidence. Доказаны Native USBFS Fastboot DATA transfer/flash, cancel/drain semantics и финальный ADB inbound framing gate — **PASS**.

Frozen A2 archive не содержит финальный diagnostics bundle этого framing gate; статус PASS зафиксирован как project evidence по подтверждению владельца и должен учитываться отдельно от наличия самого bundle.

### `onyx` / POCO F7 / Redmi Turbo 4 Pro
USB-unstable stress patient. Не использовать как единственный reference gate. Quirk должен стать explicit observed capability/advisory, а не глобальным hard-block устройства.

## 4. Regression matrix нового проекта

Минимум постепенно покрыть:
- ADB Android mode;
- ADB Recovery mode;
- concurrent ADB streams;
- shell_v2 и legacy fallback;
- push/pull крупного файла;
- install;
- bootloader Fastboot;
- fastbootd;
- DATA OUT крупного image;
- DATA IN/fetch;
- physical detach during read-only operation;
- detach before and after mutation boundary;
- Sideload normal flow;
- Sideload duplicate requests;
- Sideload verifier reconnect/correlation;
- Mi Unlock staging на безопасных этапах и отдельно destructive/server-sensitive gate.

## 5. Localization quality gate

English и Russian являются first-class UI locales. Для каждого changeset, меняющего пользовательский интерфейс:
- default English resources и `values-ru` должны оставаться согласованными;
- Android Lint `MissingTranslation`/resource format failures являются блокирующими;
- user-facing Compose strings не должны возвращаться в hardcoded literals;
- protocol/raw/evidence data не переводятся на уровне core;
- при существенном UI изменении проверяется, что русский текст не ломает adaptive layout.

## 6. CI minimum

**Authoritative build/test environment нового NekoFlash — GitHub Actions.** Termux используется как Git/worktree environment и не обязан быть полноценной Android/Gradle build machine.

Каждый merge в main:
- compile;
- unit/protocol tests;
- static analysis/lint;
- formatting;
- repository hygiene scan;
- Kotlin style/complexity/module-boundary scan;
- no generated binary drift where relevant;
- test report artifact;
- build identity embedded/exportable in diagnostics;
- canonical documentation updated in the same changeset when behavior, architecture, gates or project status changes.

## 6.3. usb:api — 2026-08-30

Первый модуль Phase 2. Чистый JVM-контракт без Android: дескрипторы USB, классификация интерфейсов и выведение идентичности target.

Классификация перенесена из двух независимых источников, сошедшихся на одном и том же — Legacy `UsbDeviceInspector.kt` и A2 `usb/discovery/UsbInterfaceSelector.kt`: класс `0xFF`, подкласс `0x42`, протокол `0x01` для ADB и `0x03` для Fastboot, четыре уровня уверенности с подавлением низших, обязательная пара bulk-эндпоинтов.

Выведение идентичности спроектировано заново: в A2 его не было. `TargetId` строится по серийному номеру, когда он доступен, и по имени USB-подключения, когда нет; источник хранится рядом с идентичностью, потому что второй вариант не переживает re-enumeration и не должен выдавать себя за первый.

Владение сессиями и `SessionGeneration` спроектированы заново по `02_CORE_ARCHITECTURE_RU.md`: generation монотонна в пределах процесса, каждое подключение получает новую, завершённая сессия необратима. Обращение по устаревшей generation отклоняется с указанием причины завершения, а не generic-ошибкой: реестр помнит ограниченное число недавно закрытых сессий именно ради честного ответа «устройство отключено».

Политика разрешений перенесена из A2 (`UsbPermissionPolicy`), но опирается на сессии, а не на отдельный реестр ожидающих запросов: два источника истины о том же самом рано или поздно расходятся. Сохранены проверенные детали — приоритет точного совпадения идентификатора подключения над именем, повторная привязка выбранного интерфейса к свежему дескриптору, таймаут 30 секунд и отказ подключаться неявно по разрешению, о котором система не сообщила.

57 unit-тестов модуля закрепляют перенесённые инварианты. Проверка границ модулей расширена на `usb/api`: Android-импорты в него запрещены машинно.

## 6.4. usb:android и декларации манифеста — 2026-08-30

Первый Android-модуль. Содержит только перекладку дескрипторов `android.hardware.usb.*` в модель `usb:api`: разбор сырых значений направления и типа передачи вынесен в `usb:api` и покрыт тестами, поэтому в непроверяемом на телефоне коде не осталось ни одного решения.

Attach-фильтр перенесён из Legacy как есть — один wildcard `class="255"` вместо списка производителей. Список конкретных vendorId был бы ровно тем запретом, который запрещает продуктовый устав: устройство отсеивалось бы за отсутствие в нашем списке, а не за собственный отказ. Wildcard покрывает канонические ADB и Fastboot, OEM Fastboot с нестандартными subclass/protocol и новые vendorId без правки списка.

`uses-feature android.hardware.usb.host` объявлен обязательным так же, как в Legacy и A2. На установку это не влияет: `uses-feature` используется магазином приложений, а не установщиком, а NekoFlash распространяется вне магазина.

Проверка границ модулей расширена на `usb/android`: зависимости на protocol, feature, vendor, UI и Compose запрещены машинно.

Владение USB на стороне Android добавлено следом: перечисление устройств, приёмники подключения и отключения, запрос разрешения. Хост не принимает решений — он сообщает факты и выполняет запрошенное, а классификация, идентичность, владение сессиями и разбор ответа остаются в `usb:api`.

Уникальность имени действия для ответа системы вынесена в `usb:api` и покрыта тестами: идентичность отложенного намерения не учитывает дополнительные данные, поэтому активации приходится различать самим именем действия, а токен процесса не даёт ответу, созданному до гибели процесса, совпасть с приёмником в новом.

Наблюдение на стороне Android построено на слушателе: приёмники платформы работают по колбэкам, и оборачивать их в `Flow` следует уровнем выше, а не внутри владельца USB.

`kotlinx.coroutines` введён отдельным изменением вместе с первым настоящим использованием: `UsbSessionRegistry` публикует незавершённые сессии как `StateFlow`. Прежняя функция-снимок удалена — два способа получить одно и то же расходятся. Зависимость проверена сборкой в том же изменении, которым введена.

Связывание добавлено следом. Платформенная часть вынесена за интерфейс `UsbHost` в `usb:api`, поэтому `UsbSessionCoordinator` остался чистым и покрыт тестами на подставном хосте: полный цикл подключения, выдача и отказ в разрешении, таймаут, отключение, уточнение идентичности серийным номером после разрешения.

Границы координатора намеренно узкие. В A2 ровно эта склейка разрослась до 2495 строк, потому что туда же попали запуск и остановка транспортов, оркестрация прошивки и Sideload, экспорт диагностики. Здесь координатор умеет только превращать события USB в состояние сессий.

Планирование времени координатору не принадлежит: стартовое сканирование, повторные попытки и таймаут ожидания разрешения запускает платформенный слой, вызывая его методы. Планирование нельзя выполнить детерминированно в тесте, а всё остальное — можно.

Экран добавлен последним. Владение USB живёт в `NekoFlashApplication`, а не на экране: подключённое устройство не должно теряться при повороте. Таймаут ожидания разрешения планируется там же, в области с `Dispatchers.Default` — главный диспетчер потребовал бы отдельного артефакта корутин, а реестр сессий и наблюдаемое состояние потокобезопасны, доставку на экран берёт на себя Compose.

Экран показывает только то, что действительно известно: идентичность target вместе с её источником, транспортный вид интерфейса, уверенность классификации, состояние сессии и generation. Протокольный режим не показывается вовсе, и вместо него выводится прямое объяснение, что до handshake он неизвестен: дескриптор отличает интерфейс класса ADB от класса Fastboot, но не Android от Recovery, а bootloader Fastboot от fastbootd. Подставлять правдоподобное вместо неизвестного значило бы обманывать оператора.

Ресурсы прежнего статичного макета, ставшие ненужными, удалены вместе с ним, а не оставлены про запас.

Сборщик evidence-пакета добавлен в `core:diagnostics` отдельно от платформы, потому что `java.util.zip` доступен и без Android — а значит формат архива проверяется тестами, а не наблюдением. Архив детерминирован: одинаковый набор разделов и одна отметка экспорта дают побайтово одинаковый файл, поэтому два прогона можно сравнить напрямую и расхождение будет означать расхождение данных, а не времени файловой системы. Время записей в архиве обнуляется намеренно.

Записывается только то, что передал вызывающий: каталог целиком не упаковывается, чтобы посторонний файл рядом не попал в evidence. Поток остаётся за вызывающим и не закрывается сборщиком.

Событие превращается в одну строку, пригодную и для чтения человеком, и для `grep`; переносы внутри значений заменяются пробелом, чтобы одно событие не распалось на несколько строк.

Запись событий подключена следом. `UsbSessionCoordinator` сообщает в приёмник каждый значимый переход: открытие сессии с параметрами подключения и выбранного интерфейса, запрос и исход разрешения, уточнение идентичности после его выдачи, таймаут с принятым решением, закрытие при отключении. Реестр по-прежнему ничего не пишет сам — он возвращает достаточно подробные результаты, а решает, что из этого событие, координатор.

Приёмник событий ограничен по объёму: владелец USB живёт всё время работы приложения, и неограниченный список рос бы часами. Число вытесненных событий сохраняется и попадает в evidence — молча потерять начало журнала значит выдать неполный отчёт за полный.

Выгрузка завершает диагностику. Архив содержит три раздела помимо описи: `host.txt` с идентичностью сборки и устройства-хоста, `sessions.txt` со снимком сессий на момент выгрузки, `events.txt` с журналом. Файл создаёт пользователь через системный диалог сохранения — приложение не заводит собственного хранилища отчётов.

Состав отчёта ничем не урезан. Он собирается оператором о собственном устройстве, и вырезать из него сведения «на всякий случай» означало бы ровно тот host-side запрет, который запрещает `01_PRODUCT_CHARTER_RU.md`. Поле, которого платформа не даёт, записывается с причиной отказа, а не пропускается: серийный номер хоста требует `READ_PRIVILEGED_PHONE_STATE`, разрешения системного уровня, которое обычному приложению не выдаётся ни при каких действиях пользователя. Вызов не делается вовсе — он не может завершиться успешно, — а в отчёт идёт причина. Это отказ платформы, который по классу Device authority показывается как есть.

Протокольный режим в отчёт не подставляется и записан как `unknown_until_handshake`. Пустое место и правдоподобная догадка одинаково портят evidence.

## 6.9. Claim / release

Захват интерфейса реализован как возможность, но **не выполняется автоматически**.

В Legacy и A2 захват живёт внутри протокольного транспорта (`AdbUsbTransport.open`, `FastbootUsbTransport.open`) и происходит сам собой при успешном обнаружении и разрешении. У нас протокольных движков ещё нет, поэтому автоматический захват удерживал бы исключительный ресурс, ничего с ним не делая, и мешал бы другим владельцам USB на этом хосте.

Поэтому захват и освобождение выполняются действием оператора. С появлением протокольных движков захват станет частью открытия транспорта, как в архивах, а явное освобождение сохранится: удерживать устройство без способа отпустить — само по себе ограничение.

`claimInterface` вызывается с принудительным отбором, единогласно с обоими архивами: вендорный интерфейс на некоторых хостах занят ядерным драйвером, и без этого ADB и Fastboot не работают. Это отбор у драйвера, который по этим протоколам всё равно не говорит.

Отказ платформы возвращается как есть — `DEVICE_GONE`, `OPEN_REFUSED`, `INTERFACE_REFUSED` — и попадает в журнал с причиной, а не подменяется собственным умолчанием.

## 6.15. Почему диалог авторизации появился повторно — 2026-09-03

В прогоне §6.14 устройство снова спросило подтверждение, хотя тот же хост был
авторизован двумя часами раньше. Разрешения отладки при этом не отзывались.

**Что видно в журнале.** Подпись была отправлена и **не принята**: следом ушёл
публичный ключ. Значит ключ хоста отличался от того, который устройство
запомнило. Между `auth_required` и `auth_signature_sent` прошло 120 мс — для
чтения ключа с диска долго, для генерации RSA-2048 правдоподобно.

**Причина, подтверждённая владельцем устройства.** Приложение при каждой новой
сборке удаляется и ставится заново, а не обновляется. Удаление уносит приватный
каталог вместе с ключом. Обновление же было невозможно по своей причине:
у сборки не было `signingConfig`, поэтому
`assembleDebug` на чистом раннере GitHub Actions создаёт новый
`debug.keystore` при каждом запуске. Каждая сборка подписана другим ключом,
установка поверх прежней невозможна, и приложение приходится удалять. Удаление
уносит приватный каталог вместе с `adbkey.pk8`, а новый ключ для устройства —
новый хост.

**Почему это не доказано.** Отпечаток ключа нигде не записывался, и отличить
«хост потерял ключ» от «устройство забыло хост» было нечем. Поэтому вместе с
этим разделом добавлено событие `host_key` с происхождением ключа
(`GENERATED` или `LOADED`) и его отпечатком.

**Как проверить в следующий раз.** Установить сборку, подключиться, посмотреть
`host_key`. `GENERATED` при уже авторизованном устройстве означает потерю
каталога, `LOADED` с прежним отпечатком и повторным диалогом — что забыло
устройство.

**Что сделано.** Сборка научилась брать отладочный ключ из переменной
`NEKOFLASH_DEBUG_KEYSTORE`, а CI — раскладывать его из секрета
`NEKOFLASH_DEBUG_KEYSTORE_BASE64` во временный каталог раннера. Файл в дерево
не кладётся: гейт гигиены запрещает `*.keystore` среди отслеживаемых файлов, и
запрещает правильно. Пока секрет не задан, поведение прежнее — сборка подписана
одноразовым ключом.

Секрет создаётся один раз на стороне владельца репозитория:

```
keytool -genkeypair -v -keystore ~/nekoflash-debug.keystore \
  -storepass android -keypass android -alias androiddebugkey \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -dname "CN=NekoFlash Debug,O=NekoFlash,C=US"
base64 -w0 ~/nekoflash-debug.keystore | gh secret set NEKOFLASH_DEBUG_KEYSTORE_BASE64
```

После этого сборки подписаны одним ключом и ставятся поверх прежних. Приватный
каталог переживает установку, ключ хоста ADB сохраняется, и устройство не
спрашивает подтверждения заново. Пароли `android` и `androiddebugkey` — принятое
соглашение отладочных хранилищ; секретом они не являются и ничего не защищают.

## 6.16. Разбор «приложение не видит устройство» — 2026-09-04

Два выгруженных evidence подряд оказались пустыми: `no events were recorded`,
`no sessions at export time`, `droppedEvents=0`.

**Что из этого следует.** Координатор пишет `device_ignored_no_usable_interface`
всякий раз, когда устройство видно, но подходящего интерфейса в нём нет. Этой
записи тоже нет, значит `getDeviceList` вернул пустой список: приложению не для
чего было запрашивать разрешение.

**Чего не хватило для ответа.** Ровно ничего в журнале не отличало «система не
отдала ни одного устройства» от «приложение не работает». Разбираться пришлось
по отсутствию записей — то есть по умолчанию, а не по свидетельству. Это дефект
самой диагностики, и он важнее конкретной причины.

**Что исправлено.**

- Скан пишет `scan_completed` всегда, включая случай нуля устройств, и
  сообщает, сколько система отдала, сколько разобрано впервые и сколько уже
  известно.
- `host.usbHostFeature` попадает в `host.txt`: сообщает ли платформа о
  поддержке host-режима USB вообще.
- Экран при пустом списке говорит, чего именно нет: host-режима, устройств или
  подходящего интерфейса.
- В манифест добавлено `<uses-feature android:name="android.hardware.usb.host">`.
  Его там не было ни разу за всю историю нового ядра, хотя платформа требует
  объявления от приложений, работающих с USB Host API, и часть систем без него
  не доставляет `USB_DEVICE_ATTACHED`. `required="false"` намеренно: `true`
  заблокировал бы установку на аппаратах, которые о фиче не сообщают.

**Что это не доказывает.** Отсутствие объявления не объявляется причиной: до
2026-09-03 на том же хосте всё работало. Причина станет видна из следующего
evidence — по `host.usbHostFeature` и `scan_completed`.

**Про роль `onyx` — исправлено.** В первой редакции этого раздела запись из
`KNOWN_USB_DEVICE_QUIRKS.md` была отнесена к хосту. Это неверное чтение: весь
материал того документа описывает `onyx` **в роли пациента**, то есть цели, и
про его поведение в роли хоста там не сказано ничего. Полевое наблюдение
владельца: как хост `onyx` работает нормально, проблемным он был именно как
цель.

К разбору 2026-09-04 та запись к тому же не относится вовсе: целью был
POCO X3 Pro (`vayu`), а не `onyx`. Хост из числа подозреваемых исключается, пока
`scan_completed` и `host.usbHostFeature` не скажут обратного.

именно здесь, не оправдалось.

критерий побайтной целостности: один размер такого доказательства не давал бы.

**Отрицательный путь.** Отсутствующий путь дал нулевой `STAT`, а попытка
`RECV` несуществующего имени вернула `DEVICE_REFUSED` с сообщением устройства
`open failed: No such file or directory`. После отказа ADB-соединение осталось
живым и следующие Sync-операции прошли.

**Evidence.** В журнале есть `sync_open`, `sync_opened`, `sync_stat`,
`sync_received`, `sync_failed`, `sync_closed`; `droppedEvents=0`. В сборке
этого прогона `sync_received` записывал размер, но не SHA-256, поэтому
совпадение отпечатка подтверждено экраном. Следующий changeset добавляет
`sha256` прямо в `sync_received`, чтобы дальнейшее hardware evidence не
зависело от скриншота.

**Не перепроверено в этом прогоне.** Отдельный `STAT` каталога `/sdcard` и
permission-denied на `/data/system`. Они не входят в критерий целостности
`RECV`; соответствующие protocol outcomes покрыты unit-тестами. `SEND` не
реализован и этим гейтом не проверяется.

## 6.30. Разбор AUTH без диалога — закрыт новым evidence

Предыдущие попытки с `vayu` на разных host-install состояниях доходили до
`auth_public_key_sent`, после чего на экране долго не было RSA-диалога.
Инструментирование `auth_response` было добавлено, чтобы отличить повторный
`AUTH TOKEN` от полного отсутствия ответа.

**Уточнение прежней интерпретации.** Отсутствие `auth_response` сразу после
`AUTH RSAPUBLICKEY` само по себе **не доказывает**, что ключ не дошёл до
`adbd`. После принятия публичного ключа daemon может ждать решение Android
framework/пользователя и не посылать новый ADB-пакет до подтверждения. Поэтому
старое чтение «тишина = пакет не дошёл или отвергнут» было слишком сильным и
здесь отменяется.

Фактический успешный прогон 2026-09-07:

| Момент | Что наблюдалось |
|---|---|
| 19:10:34.351 | `cnxn_sent` |
| 19:10:34.354 | `auth_required` |
| 19:10:34.383 | `auth_signature_sent` |
| 19:10:34.402 | `auth_response type=1`, через 19 мс |
| 19:10:34.403 | `auth_public_key_sent payload=719` |
| 19:10:47.693 | после подтверждения RSA-диалога пришёл `CNXN`, через 13 289 мс |
| 19:10:47.696 | `connected peerMode=DEVICE`, 23 capabilities |

Повторное подключение тем же сохранённым host key прошло без отправки public
key: `auth_signature_sent` → `CNXN` за **14 мс**. Это аппаратно доказывает и
первичную авторизацию, и сохранение/узнавание ключа устройством. Старый blocker
«authorization dialog не появляется» закрыт.

**Как теперь читать AUTH evidence.**

| Что в журнале | Что можно утверждать |
|---|---|
| `auth_public_key_sent`, затем тишина | только то, что хост успешно записал пакет и ждёт; из одной тишины нельзя вывести, дошёл ли framework до UI |
| повторный `AUTH TOKEN type=1` | peer продолжает требовать авторизацию; причина UI/отказа отдельно не доказана |
| `CNXN` после public key | авторизация подтверждена |
| следующий connect: signature → `CNXN` без public key | сохранённый ключ узнан |

## 6.31. Аудит согласованности и Terminal correctness — 2026-09-07

Это **software/static audit changeset**, а не новый аппаратный PASS. Он приводит
код и каноническую документацию в соответствие с уже действующим правилом:
NekoFlash — инструмент для профессионалов; correctness-защита обязательна, но
валидные возможности протокола не должны скрываться за product-level gate.

Исправлено по результатам полного прохода дерева:

- `README.md`, `docs/README.md`, roadmap и recovery handoff синхронизированы с
  фактической текущей **Phase 4**;
- нумерация evidence §6.x восстановлена: `6.5` снова стоит после `6.4`, а
  пропущенный номер перед интерактивной оболочкой устранён;
- `push` и `pull` больше не объединены одним статусом: read-only `RECV` существует
  в production-пути, `SEND` остаётся не начатой мутацией;
- блокирующий USB I/O Terminal больше не запускается из Compose callback/UI
  thread: чтение и запись имеют отдельные executors, при этом физический reader
  по-прежнему один;
- Terminal не принимает ввод до реального ADB `OKAY`: событие открытия потока
  проходит от `AdbStreamRouter` до UI как отдельное состояние `ready`;
- stdout/stderr/legacy shell декодируются потоковым UTF-8 decoder, поэтому
  многобайтовый символ не портится, если граница символа совпала с границей
  ADB-пакета или `shell,v2` frame;
- выгрузка diagnostics перенесена на `Dispatchers.IO`;
- добавлены unit-тесты для controller-level очередности Terminal и для чистой
  части `usb:android`; protocol-тестами закреплены `OKAY`, разрезанный UTF-8 и
  сохранение прежней очистки NUL в `shell,v2`;
- закрытие Terminal удерживает reader ownership до отправки корректного
  `CLSE` и выхода reader loop; если `OKAY` ещё не пришёл, закрытие сначала
  дожидается remoteId и не удаляет opening-stream преждевременно;
- стилевой detekt-run теперь охватывает production Kotlin всех семи модулей, а
  не только `app/src` и `core`; единственное явно зафиксированное rule-level
  исключение — `MagicNumber` для production source `protocol:adb`, где числа
  являются wire-format command words/masks/offsets/shifts; остальные правила
  detekt этот модуль продолжают проверять;
- крупный `NekoFlashApp.kt` разделён по ответственности, ADB UI/state вынесены
  из монолитного файла;
- добавлен CI-гейт `check_docs_consistency.py`: он сверяет current Phase между
  четырьмя входными документами, непрерывность нумерации evidence и фактическое
  число `@Test` с recovery handoff, чтобы эти расхождения не возвращались.

Текущий production-путь всё ещё **не является полноценным concurrent service
multiplexer**: постоянный physical reader/dispatcher, который одновременно
обслуживает несколько logical streams, остаётся отдельным пунктом Phase 4. Пока
он не построен и не подтверждён, одноразовые shell/file/service calls при живом
Terminal намеренно не запускаются параллельно. Это временное ограничение
реализации, а не продуктовый запрет capability.

На момент этого software changeset аппаратный blocker §6.30 ещё оставался
открытым. Он закрыт последующим прогоном §6.32. Полный Gradle test/lint/style
gate этого changeset подтверждён authoritative GitHub Actions на commit
`c1478aa932c485c1179108e5897c88d20f0e05e3`.

## 6.32. AUTH, большой RECV и late `CLSE` — 2026-09-07

Этот прогон выполнялся уже после зелёного GitHub Actions для
`c1478aa932c485c1179108e5897c88d20f0e05e3`. Он закрыл два аппаратных вопроса
Phase 4 и одновременно обнаружил один protocol-correctness defect.

**AUTH — PASS.** Первичная авторизация прошла через `AUTH TOKEN` → signature →
повторный token → `AUTH RSAPUBLICKEY` → системный RSA-диалог → `CNXN`. После
подтверждения устройство подключилось, а повторное подключение тем же ключом
дало `CNXN` через 14 мс без повторной отправки public key. Полная последовательность
и исправленная трактовка тишины после public key записаны в §6.30.

**Read-only Sync / RECV — PASS по критерию целостности.** Малый файл дал
`STAT size=10` и `RECV bytes=10`. Файл 2 MiB дал `STAT size=2097152`,
`RECV bytes=2097152`; SHA-256 на экране NekoFlash совпал с эталоном:
`5647f05ec18958947d32874eeb788fa396a05d0bab7c1b71f112ceb7e9b31eee`.
Подробности — §6.29.

**Найден late `CLSE`.** После освобождения и нового захвата интерфейса одна
попытка отправила новый `CNXN`, но первым входящим пакетом оказался
`command=0x45534c43` (`CLSE`) от logical stream предыдущего соединения. Старый
handshake трактовал любой пакет кроме `CNXN/AUTH` как фатальный и завершился
`UNEXPECTED_COMMAND`; следующая попытка через 10 секунд подключилась нормально.

Это не причина скрывать повторное подключение. `CLSE` с stream IDs до ответа
на новый `CNXN` не может быть ответом handshake и является поздним закрытием
старого logical stream. Исправление узкое: до первого `CNXN/AUTH` handshake
пропускает ограниченное число именно `CLSE`, записывая
`handshake_stale_close` с remote/local IDs. Другие неожиданные команды
по-прежнему фатальны; framing errors не игнорируются.

**UI AUTH.** Состояние «ждём авторизацию» раньше выставлялось до вызова
`connection.connect()`, то есть UI мог предлагать подтвердить RSA ещё до
фактического `AUTH RSAPUBLICKEY`. Теперь оно появляется только после успешной
записи public key. Текст также описывает факт протокола и лишь условно сообщает,
что обычный Android может показать RSA-диалог.

**Diagnostics.** Успешный `sync_received` теперь содержит `path`, `bytes` и
`sha256`. Следующий hardware bundle сможет сам доказать целостность RECV без
отдельного скриншота.

## 6.33. Сплошной аудит дерева — 2026-09-07

Аудит без нового кода и без аппаратного прогона: проверка того, что документы
говорят то же, что делает код. Проверено на `b3a6642`.

**Подтверждено независимо от гейтов.** 372 `@Test` — ровно столько, сколько
заявляет `99_RECOVERY_HANDOFF_RU.md`. Три архива сходятся с
`reference/SHA256SUMS` (сверка выполняется из каталога `archives/`: манифест
перечисляет имена без пути). Ни одного файла свыше блокирующего порога в 800
строк, максимум — 449 (`AdbHandshake.kt`), одиннадцать файлов в полосе ревью
300–449. Направление зависимостей и `api()` вместо `implementation()`
соблюдены во всех семи модулях. В production нет ни `TODO/FIXME/HACK`, ни
`NotImplemented`, ни `.orig`. Продуктовый закон держится и в коде: ни
allowlist, ни `if (dangerous) reject`, ни фильтрации команд в терминале;
`AdbServiceCall` принимает произвольное имя сервиса, а его пределы — ресурсные
границы вызывающего с отдельными исходами `OUTPUT_TOO_LARGE`/`TIMED_OUT`, а не
тихое обрезание. Инвариант `vayu` прослежен в `AdbPacketReader` по коду:
заголовок добирается циклом до 24 байт, payload читается одной операцией,
короткий результат даёт `SHORT_PAYLOAD` fail-closed.

**Найдено три расхождения, все документационные. Дефектов корректности нет.**

- `09_IMPLEMENTATION_ROADMAP_RU.md` утверждал, что `CNXN` ещё не объявляет
  `maxdata`. Объявляет: `AdbConnection` считает значение один раз и отдаёт его
  и в `arg1` пакета `CNXN`, и в `AdbPacketReader` как предел длины кадра.
  Документ противоречил при этом сам себе — строка выше называла объявление
  `maxdata` единственным непроверенным на железе пунктом;
- `AdbConnection.kt` нёс два KDoc-блока подряд: «Проводит рукопожатие» стоял
  над свойством `peerFeatures`, а сама `connect()` осталась без документации.
  Kotlin привязывает только последний блок, поэтому ни компилятор, ни detekt
  этого не видят. Проход по всему дереву показал, что случай единственный;
- `UsbSessionRegistry.kt` объяснял отказ писать диагностику тем, что так
  `usb:api` не тянет зависимость на `core:diagnostics`. Зависимость есть и
  используется — `UsbSessionCoordinator` пишет события, `UsbDiagnosticReport`
  собирает разделы. Решение реестра осталось верным, ложным стало обоснование.

**Оставлено сознательно.** `AdbSyncProtocol` объявляет `ID_SEND`, `ID_OKAY`,
`ID_DENT` и `ID_QUIT`, которых пока никто не вызывает. Это описание формата
провода, а не production stub: значения принадлежат протоколу целиком, и
объявлять их по одному вместе с командами значило бы разносить один формат по
разным changeset'ам. `emptyStateReason` в `:app` содержит выбор из четырёх
причин пустого списка внутри `@Composable`, поэтому pure-JVM тестом не
покрывается; это отступление от принципа §6.4 и кандидат на вынос чистой части,
но не нарушение контракта.

## 6.34. Аппаратный гейт записи файла — план, прогон не проведён

Раздел написан **до** прогона. `SEND` — первая мутация в проекте, и критерий,
придуманный после того, как результат виден, критерием не является.

**Что проверяется.** `AdbSyncSession.send`: спецификация назначения, поток
блоков `DATA`, `DONE` со временем изменения и вердикт устройства. Отдельно —
что о состоянии файла назначения сообщается ровно то, что доказано.

**Почему гейт нельзя пропустить.** Ни один тест здесь не отвечает на главный
вопрос: в какой момент `adbd` создаёт и обрезает файл. Подставной транспорт
знает только то, что заложил автор. До прогона граница мутации остаётся
консервативным предположением, а не измеренным фактом.

| Сценарий | Что должно наблюдаться |
|---|---|
| Запись малого файла в `/sdcard` | `OKAY`; `sync_sent` с `bytes` и `sha256`; `sha256sum` на устройстве совпадает с отпечатком на экране |
| Запись файла больше 2 MiB | то же; блоки идут по 64 КиБ, память приложения не растёт пропорционально файлу |
| Запись в `/system` без прав | `FAIL` с настоящим текстом устройства; исход `DEVICE_REFUSED`, назначение `UNKNOWN` |
| Перезапись существующего файла | `OKAY`; отпечаток совпадает с новым содержимым, а не со старым |
| Отключение кабеля посреди `DATA` | назначение `UNKNOWN`, автоматического повтора нет |
| **Проверка границы мутации** | после отключения посреди `DATA` заново подключиться и посмотреть `STAT` пути: существует ли файл и какого он размера |
| Режим созданного файла | `stat` на устройстве показывает режим, переданный в спецификации |

**Критерий PASS.** Первые шесть сценариев наблюдаются, evidence выгружен
приложением, `droppedEvents=0`, а отпечатки совпадают.

**Что даст седьмая строка.** Она измеряет то, что сейчас предполагается. Если
после обрыва посреди `DATA` файл на устройстве существует — граница мутации
выбрана верно, и запись `SEND` действительно уже меняет назначение. Если файла
нет ни в одном прогоне, это ещё не доказательство обратного: момент создания
может зависеть от версии `adbd` и файловой системы. Ослаблять границу до
первого блока `DATA` допустимо только отдельным решением с этим evidence на
руках, потому что ошибка в эту сторону превращает `Unknown` в ложное
«ничего не изменилось».

**Чего гейт не закрывает.** Вызывающего в production у `send` пока нет: выбор
локального файла требует artifact source из Phase 8. Гейт проверяет
протокольный путь, а не пользовательский сценарий push.

## 7. Hygiene CI

CI должен запрещать production tree leftovers:
- `*.orig`;
- `*.bak`;
- `*.rej`;
- obvious `Old*`, `New*`, `Temp*` duplicate implementations;
- TODO/FIXME/HACK в production без явно принятой policy/issue reference;
- `NotImplemented`/throw-stub production paths;
- accidental secrets/private keys beyond intentionally generated local ADB keys handled by secure app storage.

Не превращать это в тупой regex, который ломает legit test fixtures: правила должны быть узкими и объяснимыми.

## 8. Definition of Done для core capability

1. Один production path.
2. Public/internal API определён.
3. Unit/protocol tests PASS.
4. Fault-injection cases покрыты.
5. Peer response не теряется.
6. Cancellation/Unknown semantics определены.
7. Hardware-sensitive path доказан.
8. Diagnostics позволяют разобрать failure без догадок.
9. Документация обновлена одновременно с кодом.
