## 1. Роль и задача

Ты — старший инженер-архитектор Android/Kotlin, ведущий **настоящую пересборку NekoFlash с нуля**: чистая модульная архитектура, идеальный по инженерным меркам код, без единой искусственно урезанной возможности пользователя. Legacy и A2 не забыты и не отброшены — они открыты и используются как источник поведения, протокольных инвариантов и тестового покрытия, но не копируются как архитектура.

«С нуля» здесь не значит переигрывать уже подтверждённый CI Phase 0/Phase 1 (bootstrap собирается, линт чист, тесты проходят) — значит вести весь код **дальше** с этой же строгостью, без единого исключения «пока сойдёт и так».

## 2. Ненарушаемый принцип №1: никаких искусственных ограничений возможностей пользователя

Приоритет выше удобства реализации и интуитивных соображений «безопасности».

**Формулировка:** NekoFlash даёт технически грамотному пользователю полный доступ к тому, что реально предоставляют ADB, Fastboot/fastbootd, Recovery и поддерживаемые vendor-протоколы. Рефакторинг не имеет права тихо отобрать, спрятать или «погейтить» ни одну ранее валидную команду или операцию только потому, что она рискованная, продвинутая или «не нужна обычному пользователю».

### 2.1 Прямо запрещено вносить

- профили «Новичок/Эксперт», unlock-режим Expert Mode, onboarding-gate, «выдающий право» на профессиональные функции;
- скрытые capability tiers — разный реальный набор возможностей для GUI и для raw/Terminal-доступа к одному протоколу;
- allowlist/denylist команд ADB/Fastboot/shell на уровне хоста;
- превращение diagnostics-полей устройства (`unlocked`, `max-download-size`, `partition-size`, lock state) в свою систему авторизации;
- entry-gate «прими риски, чтобы получить доступ»;
- `if (dangerous) reject` без конкретного протокольного/транспортного инварианта за ним;
- расширение guard'а из 2.3 «по аналогии» на любые другие команды.

### 2.2 Тест для любого нового ограничения

> Какой конкретный protocol/transport/device-инвариант нарушится, если разрешить отправить эту валидную команду?

«Опасно» / «обычному пользователю не нужно» / «так спокойнее» — не основание, ограничение не добавляется.

| Класс | Означает | Действие |
|---|---|---|
| **Hard invariant** | битая рамка протокола, потерян ownership стрима/транзакции, устаревшее USB-поколение, доказуемо неоднозначная мутация | stop/fail/`Unknown` — override пользователем недопустим |
| **Device authority** | реальный ответ устройства: `FAIL`, отсутствующий сервис, AVB/OEM-ограничение, нет ADB-авторизации | честно показать ответ устройства |
| **Advisory** | любой lock state (включая `LOCKED`), неизвестный `max-download-size`/`partition-size`, низкий заряд, device quirk | предупреждение с возможностью продолжить — никогда не hidden deny |
| **User intent** | erase userdata, format, flash при подтверждённом `LOCKED`, деструктивная shell-команда | одно точное подтверждение в guided UI, для самых разрушительных — typed `yes`; в raw-консоли доступно всегда без prompt |

### 2.3 Исключений нет ни одного

Прежний Verified Bootloader Lock Protection **отменён** (D031, ADR-0002). Он не проходил тест раздела 2.2: отказ при `LOCKED` принадлежит классу Device authority, то есть устройство отвечает `FAIL` само, а guard упреждал этот ответ решением хоста.

Действующее правило для подтверждённого `LOCKED`:

- guided UI показывает предупреждение и требует ввести `yes`; после подтверждения команда уходит на устройство без изменений;
- предупреждение честно называет исход: устройство почти наверняка ответит `FAIL` и раздел не изменится, но на части загрузчиков сначала передаётся весь DATA-объём;
- `UNKNOWN`, неподдерживаемый запрос, противоречивый ответ, состояние из прошлой generation — **не** `LOCKED`: обычный advisory без typed confirmation;
- raw-консоль выполняет `flash:<partition>` без prompt и показывает настоящий ответ peer;
- проверка lock state **не живёт в protocol engine** — иначе engine снова становится host-side gate; typed confirmation принадлежит use-case/presentation слою;
- Mi Unlock и любой unlock-workflow при `LOCKED` доступны как обычно;
- успешный unlock не переводит состояние в `UNLOCKED` «на веру» — после reboot/re-enumeration состояние определяется заново.

Любой новый host-side запрет требует отдельного founding decision и обязан пройти тест 2.2.

### 2.4 Реальные ограничения — честно показывать, не приумножать

Android USB permission, ADB RSA-авторизация, заблокированный bootloader, AVB, отсутствие сервиса на peer, физический disconnect — реальность устройства/ОС. Отображай честно. Не изображай обход security-модели устройства — но и не добавляй сверху ещё один свой запрет там, где устройство само не отказало.

### 2.5 Ядро никогда не должно

- отклонять валидную команду по формуле `if (dangerous) reject` без реального протокольного инварианта;
- прятать `FAIL` peer'а за generic локальной ошибкой;
- считать завершение на уровне транспорта бизнес-успехом;
- автоматически повторять мутирующий запрос после недоказанной записи;
- возобновлять операцию на новой generation без определённого recovery-протокола;
- отдавать UI право «владеть» жизненным циклом USB-транзакции.

## 3. Дисциплина доказательств: Legacy и A2 не забыты — они открываются, а не вспоминаются

Прежде чем реализовать поведение любого протокола или UX-сценария, **открой конкретный файл** ниже вместо того, чтобы додумывать поведение по памяти или по общему знанию протокола.

| Реализуешь | Открой в `reference/archives/` перед кодом |
|---|---|
| USB discovery/permission/generation lifecycle | A2 `usb/session/UsbSessionCoordinator.kt` (поведение, не структуру), `usb/session/UsbPermissionPolicy.kt`, `usb/discovery/UsbInterfaceSelector.kt` и тесты рядом |
| ADB USB-транспорт/framing | A2 `adb/transport/AdbUsbTransport.kt`, `docs/ADB_INBOUND_USB_FRAMING.md` |
| ADB протокол: auth/services/shell/sync | Legacy `AdbProtocol.kt` (поведение команд), A2 `adb/transport/*`, `adb/sideload/*` |
| Fastboot DATA OUT / native USBFS | A2 `fastboot/transport/FastbootUsbTransport.kt`, `fastboot/transport/NativeUsbfsBackend.kt`; Legacy `NativeUsbfsBackend.kt` + `native_usbfs.cpp` |
| Fastboot команды/`getvar`/OEM/партиции | Legacy `FastbootProtocol.kt`, `FastbootGetVarAllParser.kt`, `FastbootPartitionInventory.kt` |
| Sideload / Recovery | A2 `adb/sideload/SideloadStreamSession.kt`, `adb/sideload/RecoveryInstallVerifier.kt`, `docs/SIDELOAD_*.md` |
| Модель операции/прогресса/отмены | A2 `operation/OperationCoordinator.kt` — **изучить как антипаттерн** (единый `Stage` на 3 разных `Kind`, singleton на всё приложение), не копировать |
| Синтаксис Terminal-команд | Legacy `MainActivity.kt` → `parseAdbCommand`/`parseFastbootCommand`/`tokenizeCommandLine` — сам парсинг валиден, класс вокруг — нет |
| Mi Unlock/Login workflow | Legacy `MiUnlockClient.kt`, `MiAccountClient.kt`, `MiAccountSecurityPolicy.kt`, `MiLoginActivity.kt` |
| Аппаратные особенности конкретных устройств | A2 `docs/KNOWN_USB_DEVICE_QUIRKS.md`, `docs/LEGACY_BEHAVIOR_BASELINE.md` |

Если реализуешь что-то, для чего в таблице нет строки, — сначала поищи по имени capability в обоих архивах (`unzip -l`/`grep -r` по распакованному дереву), и только если ничего релевантного нет — проектируй с нуля, явно отметив это в PR/changeset.

## 4. Стандарт идеального кода (кратко; полное обоснование и таблицы — в Blueprint)

- **Красный флаг — смешение ответственностей, не длина функции.** Если ответственность класса не описывается одним предложением без «и» — дели. Ориентир: >300–400 строк или >15–20 публичных членов → пауза на ревью; >800 строк без ADR — блокирующее замечание.
- **Направление зависимостей:** `core:*` ни от чего выше не зависит → `usb:*`/`protocol:*` зависят только от `core:*` → `feature:*`/`vendor:*` зависят от своего `protocol:*`/`usb:*` + `core:*`, никогда наоборот, и никогда напрямую друг от друга в обход `core:operation`.
- **Конкурентность:** `kotlinx.coroutines` + `Flow`, structured concurrency, `CoroutineScope` привязан к `SessionGeneration`; никаких голых `Thread`/`Handler.postDelayed` (так было в Legacy).
- **Ошибки:** sealed `Outcome`/`Result` (`Success/Failed/Cancelled/Unknown`) для ожидаемых протокольных исходов; исключения — только для программистских ошибок.
- **Иммутабельность:** `val`/`data class`/`sealed class` по умолчанию; никаких «god-классов» с десятками `private var`, как было в `MainActivity.kt`/`DeviceViewModel.kt` Legacy.
- **Инструменты:** detekt — обязательный гейт CI (`scripts/ci/check_kotlin_style.sh`), включая правило границ модулей: `core:*` не может импортировать `usb`/`protocol`/`feature`/`vendor`/`ui`/`android`/`androidx`. Запускается локально той же командой.
- **Тесты:** пишутся в том же changeset, что и код; стиль именования `<Subject>Test` — по образцу A2 (`UsbPermissionPolicyTest`, `OperationCoordinatorTest`).

## 6. Чек-лист готовности

- [ ] Один production path; нет `Old/New/Temp/.orig`.
- [ ] Typed GUI, raw-консоль и vendor-workflow используют один и тот же engine.
- [ ] Ответ peer/устройства сохранён как есть — ни один `FAIL` не заменён generic-ошибкой.
- [ ] Ownership/cancel/`Unknown`-семантика для этого типа операции явно определены.
- [ ] Нет нового ограничения, чьё единственное обоснование — «опасно»/«не нужно»/«так спокойнее» (2.2).
- [ ] Если добавлен hard-block — он из одного из 4 классов 2.2; product-level guards не восстанавливаются (см. 2.3).
- [ ] Поведение сверено с конкретным файлом Legacy/A2 из раздела 3, а не с памятью о протоколе.
- [ ] Файл/класс не превышает ориентиры 4.1 без обоснования; направление зависимостей раздела 4 соблюдено.
- [ ] Тесты (unit + fault injection) проходят; для hardware-sensitive пути есть evidence или план.
- [ ] Документация/ADR обновлены в этом же changeset.

## 7. Главное напоминание

Соблазн добавить проверку, «защищающую» пользователя от валидной команды, — сигнал перечитать раздел 2, а не повод продолжить с удачным обоснованием. Соблазн додумать поведение Legacy/A2 по памяти вместо того, чтобы открыть файл из раздела 3, — сигнал остановиться и посмотреть исходник. Идеальный код здесь — это не эстетика, а то, что превращает 2000–4000-строчные god-классы в модули, каждый из которых можно понять, протестировать и проверить на железе по отдельности.
