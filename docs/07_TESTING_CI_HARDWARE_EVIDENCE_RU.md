# NekoFlash — Testing, CI & Hardware Evidence

## 1. Тесты строятся по слоям

### Pure unit
- codecs/parsers;
- state machines;
- byte accounting;
- advisory classification;
- artifact logic;
- correlation logic.

### Protocol simulation
Fake peer/transport должен уметь моделировать:
- short reads/writes;
- packet fragmentation;
- delayed responses;
- duplicate/out-of-order relevant events;
- stream concurrency;
- malformed frames;
- `INFO/TEXT/FAIL` sequences;
- DATA length mismatch;
- disconnect at every interesting byte/state boundary.

### Integration
- Android USB permission/session ownership;
- foreground operation service;
- persistence/process recreation;
- SAF seekable/non-seekable providers where testable.

### Hardware
Нужен matrix реальных устройств/режимов, потому что USB host stacks и Recoveries имеют vendor quirks.

## 2. Hardware evidence policy

Hardware-sensitive change не считается proven только по unit tests.

Evidence bundle должен содержать:
- app commit/build identity;
- host device identity;
- target identity;
- mode;
- timestamps;
- relevant structured logs/transcript;
- exact byte counts;
- screenshots только как дополнительное подтверждение, не вместо logs;
- PASS criteria.

## 3. Reference devices

### `vayu`
Стабильный reference target для A2 evidence. Доказаны Native USBFS Fastboot DATA transfer/flash, cancel/drain semantics и финальный ADB inbound framing gate — **PASS**.

Frozen A2 archive не содержит финальный diagnostics bundle этого framing gate; статус PASS зафиксирован как project evidence по подтверждению владельца и должен учитываться отдельно от наличия самого bundle.

### `onyx` / POCO F7 / Redmi Turbo 4 Pro
USB-unstable stress patient. Не использовать как единственный reference gate. Quirk должен стать explicit observed capability/advisory, а не глобальным hard-block устройства.

## 4. Regression matrix нового проекта

Минимум постепенно покрыть:
- ADB Android mode;
- ADB Recovery mode;
- concurrent ADB streams;
- shell_v2 и legacy fallback;
- push/pull крупного файла;
- install;
- bootloader Fastboot;
- fastbootd;
- DATA OUT крупного image;
- DATA IN/fetch;
- physical detach during read-only operation;
- detach before and after mutation boundary;
- Sideload normal flow;
- Sideload duplicate requests;
- Sideload verifier reconnect/correlation;
- Mi Unlock staging на безопасных этапах и отдельно destructive/server-sensitive gate.

## 5. Localization quality gate

English и Russian являются first-class UI locales. Для каждого changeset, меняющего пользовательский интерфейс:
- default English resources и `values-ru` должны оставаться согласованными;
- Android Lint `MissingTranslation`/resource format failures являются блокирующими;
- user-facing Compose strings не должны возвращаться в hardcoded literals;
- protocol/raw/evidence data не переводятся на уровне core;
- при существенном UI изменении проверяется, что русский текст не ломает adaptive layout.

## 6. CI minimum

**Authoritative build/test environment нового NekoFlash — GitHub Actions.** Termux используется как Git/worktree environment и не обязан быть полноценной Android/Gradle build machine.

Каждый merge в main:
- compile;
- unit/protocol tests;
- static analysis/lint;
- formatting;
- repository hygiene scan;
- Kotlin style/complexity/module-boundary scan;
- Compose wiring scan — единственный модуль, который локально не собирается ничем;
- no generated binary drift where relevant;
- test report artifact;
- build identity embedded/exportable in diagnostics;
- canonical documentation updated in the same changeset when behavior, architecture, gates or project status changes.

## 6.3. usb:api — 2026-08-30

Первый модуль Phase 2. Чистый JVM-контракт без Android: дескрипторы USB, классификация интерфейсов и выведение идентичности target.

Классификация перенесена из двух независимых источников, сошедшихся на одном и том же — Legacy `UsbDeviceInspector.kt` и A2 `usb/discovery/UsbInterfaceSelector.kt`: класс `0xFF`, подкласс `0x42`, протокол `0x01` для ADB и `0x03` для Fastboot, четыре уровня уверенности с подавлением низших, обязательная пара bulk-эндпоинтов.

Выведение идентичности спроектировано заново: в A2 его не было. `TargetId` строится по серийному номеру, когда он доступен, и по имени USB-подключения, когда нет; источник хранится рядом с идентичностью, потому что второй вариант не переживает re-enumeration и не должен выдавать себя за первый.

Владение сессиями и `SessionGeneration` спроектированы заново по `02_CORE_ARCHITECTURE_RU.md`: generation монотонна в пределах процесса, каждое подключение получает новую, завершённая сессия необратима. Обращение по устаревшей generation отклоняется с указанием причины завершения, а не generic-ошибкой: реестр помнит ограниченное число недавно закрытых сессий именно ради честного ответа «устройство отключено».

Политика разрешений перенесена из A2 (`UsbPermissionPolicy`), но опирается на сессии, а не на отдельный реестр ожидающих запросов: два источника истины о том же самом рано или поздно расходятся. Сохранены проверенные детали — приоритет точного совпадения идентификатора подключения над именем, повторная привязка выбранного интерфейса к свежему дескриптору, таймаут 30 секунд и отказ подключаться неявно по разрешению, о котором система не сообщила.

57 unit-тестов модуля закрепляют перенесённые инварианты. Проверка границ модулей расширена на `usb/api`: Android-импорты в него запрещены машинно.

## 6.4. usb:android и декларации манифеста — 2026-08-30

Первый Android-модуль. Содержит только перекладку дескрипторов `android.hardware.usb.*` в модель `usb:api`: разбор сырых значений направления и типа передачи вынесен в `usb:api` и покрыт тестами, поэтому в непроверяемом на телефоне коде не осталось ни одного решения.

Attach-фильтр перенесён из Legacy как есть — один wildcard `class="255"` вместо списка производителей. Список конкретных vendorId был бы ровно тем запретом, который запрещает продуктовый устав: устройство отсеивалось бы за отсутствие в нашем списке, а не за собственный отказ. Wildcard покрывает канонические ADB и Fastboot, OEM Fastboot с нестандартными subclass/protocol и новые vendorId без правки списка.

`uses-feature android.hardware.usb.host` объявлен обязательным так же, как в Legacy и A2. На установку это не влияет: `uses-feature` используется магазином приложений, а не установщиком, а NekoFlash распространяется вне магазина.

Проверка границ модулей расширена на `usb/android`: зависимости на protocol, feature, vendor, UI и Compose запрещены машинно.

Владение USB на стороне Android добавлено следом: перечисление устройств, приёмники подключения и отключения, запрос разрешения. Хост не принимает решений — он сообщает факты и выполняет запрошенное, а классификация, идентичность, владение сессиями и разбор ответа остаются в `usb:api`.

Уникальность имени действия для ответа системы вынесена в `usb:api` и покрыта тестами: идентичность отложенного намерения не учитывает дополнительные данные, поэтому активации приходится различать самим именем действия, а токен процесса не даёт ответу, созданному до гибели процесса, совпасть с приёмником в новом.

Наблюдение на стороне Android построено на слушателе: приёмники платформы работают по колбэкам, и оборачивать их в `Flow` следует уровнем выше, а не внутри владельца USB.

`kotlinx.coroutines` введён отдельным изменением вместе с первым настоящим использованием: `UsbSessionRegistry` публикует незавершённые сессии как `StateFlow`. Прежняя функция-снимок удалена — два способа получить одно и то же расходятся. Зависимость проверена сборкой в том же изменении, которым введена.

Связывание добавлено следом. Платформенная часть вынесена за интерфейс `UsbHost` в `usb:api`, поэтому `UsbSessionCoordinator` остался чистым и покрыт тестами на подставном хосте: полный цикл подключения, выдача и отказ в разрешении, таймаут, отключение, уточнение идентичности серийным номером после разрешения.

Границы координатора намеренно узкие. В A2 ровно эта склейка разрослась до 2495 строк, потому что туда же попали запуск и остановка транспортов, оркестрация прошивки и Sideload, экспорт диагностики. Здесь координатор умеет только превращать события USB в состояние сессий.

Планирование времени координатору не принадлежит: стартовое сканирование, повторные попытки и таймаут ожидания разрешения запускает платформенный слой, вызывая его методы. Планирование нельзя выполнить детерминированно в тесте, а всё остальное — можно.

Экран добавлен последним. Владение USB живёт в `NekoFlashApplication`, а не на экране: подключённое устройство не должно теряться при повороте. Таймаут ожидания разрешения планируется там же, в области с `Dispatchers.Default` — главный диспетчер потребовал бы отдельного артефакта корутин, а реестр сессий и наблюдаемое состояние потокобезопасны, доставку на экран берёт на себя Compose.

Экран показывает только то, что действительно известно: идентичность target вместе с её источником, транспортный вид интерфейса, уверенность классификации, состояние сессии и generation. Протокольный режим не показывается вовсе, и вместо него выводится прямое объяснение, что до handshake он неизвестен: дескриптор отличает интерфейс класса ADB от класса Fastboot, но не Android от Recovery, а bootloader Fastboot от fastbootd. Подставлять правдоподобное вместо неизвестного значило бы обманывать оператора.

Ресурсы прежнего статичного макета, ставшие ненужными, удалены вместе с ним, а не оставлены про запас.

Сборщик evidence-пакета добавлен в `core:diagnostics` отдельно от платформы, потому что `java.util.zip` доступен и без Android — а значит формат архива проверяется тестами, а не наблюдением. Архив детерминирован: одинаковый набор разделов и одна отметка экспорта дают побайтово одинаковый файл, поэтому два прогона можно сравнить напрямую и расхождение будет означать расхождение данных, а не времени файловой системы. Время записей в архиве обнуляется намеренно.

Записывается только то, что передал вызывающий: каталог целиком не упаковывается, чтобы посторонний файл рядом не попал в evidence. Поток остаётся за вызывающим и не закрывается сборщиком.

Событие превращается в одну строку, пригодную и для чтения человеком, и для `grep`; переносы внутри значений заменяются пробелом, чтобы одно событие не распалось на несколько строк.

Запись событий подключена следом. `UsbSessionCoordinator` сообщает в приёмник каждый значимый переход: открытие сессии с параметрами подключения и выбранного интерфейса, запрос и исход разрешения, уточнение идентичности после его выдачи, таймаут с принятым решением, закрытие при отключении. Реестр по-прежнему ничего не пишет сам — он возвращает достаточно подробные результаты, а решает, что из этого событие, координатор.

Приёмник событий ограничен по объёму: владелец USB живёт всё время работы приложения, и неограниченный список рос бы часами. Число вытесненных событий сохраняется и попадает в evidence — молча потерять начало журнала значит выдать неполный отчёт за полный.

Выгрузка завершает диагностику. Архив содержит три раздела помимо описи: `host.txt` с идентичностью сборки и устройства-хоста, `sessions.txt` со снимком сессий на момент выгрузки, `events.txt` с журналом. Файл создаёт пользователь через системный диалог сохранения — приложение не заводит собственного хранилища отчётов.

Состав отчёта ничем не урезан. Он собирается оператором о собственном устройстве, и вырезать из него сведения «на всякий случай» означало бы ровно тот host-side запрет, который запрещает `01_PRODUCT_CHARTER_RU.md`. Поле, которого платформа не даёт, записывается с причиной отказа, а не пропускается: серийный номер хоста требует `READ_PRIVILEGED_PHONE_STATE`, разрешения системного уровня, которое обычному приложению не выдаётся ни при каких действиях пользователя. Вызов не делается вовсе — он не может завершиться успешно, — а в отчёт идёт причина. Это отказ платформы, который по классу Device authority показывается как есть.

Протокольный режим в отчёт не подставляется и записан как `unknown_until_handshake`. Пустое место и правдоподобная догадка одинаково портят evidence.

## 6.9. Claim / release

Захват интерфейса реализован как возможность, но **не выполняется автоматически**.

В Legacy и A2 захват живёт внутри протокольного транспорта (`AdbUsbTransport.open`, `FastbootUsbTransport.open`) и происходит сам собой при успешном обнаружении и разрешении. У нас протокольных движков ещё нет, поэтому автоматический захват удерживал бы исключительный ресурс, ничего с ним не делая, и мешал бы другим владельцам USB на этом хосте.

Поэтому захват и освобождение выполняются действием оператора. С появлением протокольных движков захват станет частью открытия транспорта, как в архивах, а явное освобождение сохранится: удерживать устройство без способа отпустить — само по себе ограничение.

`claimInterface` вызывается с принудительным отбором, единогласно с обоими архивами: вендорный интерфейс на некоторых хостах занят ядерным драйвером, и без этого ADB и Fastboot не работают. Это отбор у драйвера, который по этим протоколам всё равно не говорит.

Отказ платформы возвращается как есть — `DEVICE_GONE`, `OPEN_REFUSED`, `INTERFACE_REFUSED` — и попадает в журнал с причиной, а не подменяется собственным умолчанием.

## 6.15. Почему диалог авторизации появился повторно — 2026-09-03

В прогоне §6.14 устройство снова спросило подтверждение, хотя тот же хост был
авторизован двумя часами раньше. Разрешения отладки при этом не отзывались.

**Что видно в журнале.** Подпись была отправлена и **не принята**: следом ушёл
публичный ключ. Значит ключ хоста отличался от того, который устройство
запомнило. Между `auth_required` и `auth_signature_sent` прошло 120 мс — для
чтения ключа с диска долго, для генерации RSA-2048 правдоподобно.

**Причина, подтверждённая владельцем устройства.** Приложение при каждой новой
сборке удаляется и ставится заново, а не обновляется. Удаление уносит приватный
каталог вместе с ключом. Обновление же было невозможно по своей причине:
у сборки не было `signingConfig`, поэтому
`assembleDebug` на чистом раннере GitHub Actions создаёт новый
`debug.keystore` при каждом запуске. Каждая сборка подписана другим ключом,
установка поверх прежней невозможна, и приложение приходится удалять. Удаление
уносит приватный каталог вместе с `adbkey.pk8`, а новый ключ для устройства —
новый хост.

**Почему это не доказано.** Отпечаток ключа нигде не записывался, и отличить
«хост потерял ключ» от «устройство забыло хост» было нечем. Поэтому вместе с
этим разделом добавлено событие `host_key` с происхождением ключа
(`GENERATED` или `LOADED`) и его отпечатком.

**Как проверить в следующий раз.** Установить сборку, подключиться, посмотреть
`host_key`. `GENERATED` при уже авторизованном устройстве означает потерю
каталога, `LOADED` с прежним отпечатком и повторным диалогом — что забыло
устройство.

**Что сделано.** Сборка научилась брать отладочный ключ из переменной
`NEKOFLASH_DEBUG_KEYSTORE`, а CI — раскладывать его из секрета
`NEKOFLASH_DEBUG_KEYSTORE_BASE64` во временный каталог раннера. Файл в дерево
не кладётся: гейт гигиены запрещает `*.keystore` среди отслеживаемых файлов, и
запрещает правильно. Пока секрет не задан, поведение прежнее — сборка подписана
одноразовым ключом.

Секрет создаётся один раз на стороне владельца репозитория:

```
keytool -genkeypair -v -keystore ~/nekoflash-debug.keystore \
  -storepass android -keypass android -alias androiddebugkey \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -dname "CN=NekoFlash Debug,O=NekoFlash,C=US"
base64 -w0 ~/nekoflash-debug.keystore | gh secret set NEKOFLASH_DEBUG_KEYSTORE_BASE64
```

После этого сборки подписаны одним ключом и ставятся поверх прежних. Приватный
каталог переживает установку, ключ хоста ADB сохраняется, и устройство не
спрашивает подтверждения заново. Пароли `android` и `androiddebugkey` — принятое
соглашение отладочных хранилищ; секретом они не являются и ничего не защищают.

## 6.16. Разбор «приложение не видит устройство» — 2026-09-04

Два выгруженных evidence подряд оказались пустыми: `no events were recorded`,
`no sessions at export time`, `droppedEvents=0`.

**Что из этого следует.** Координатор пишет `device_ignored_no_usable_interface`
всякий раз, когда устройство видно, но подходящего интерфейса в нём нет. Этой
записи тоже нет, значит `getDeviceList` вернул пустой список: приложению не для
чего было запрашивать разрешение.

**Чего не хватило для ответа.** Ровно ничего в журнале не отличало «система не
отдала ни одного устройства» от «приложение не работает». Разбираться пришлось
по отсутствию записей — то есть по умолчанию, а не по свидетельству. Это дефект
самой диагностики, и он важнее конкретной причины.

**Что исправлено.**

- Скан пишет `scan_completed` всегда, включая случай нуля устройств, и
  сообщает, сколько система отдала, сколько разобрано впервые и сколько уже
  известно.
- `host.usbHostFeature` попадает в `host.txt`: сообщает ли платформа о
  поддержке host-режима USB вообще.
- Экран при пустом списке говорит, чего именно нет: host-режима, устройств или
  подходящего интерфейса.
- В манифест добавлено `<uses-feature android:name="android.hardware.usb.host">`.
  Его там не было ни разу за всю историю нового ядра, хотя платформа требует
  объявления от приложений, работающих с USB Host API, и часть систем без него
  не доставляет `USB_DEVICE_ATTACHED`. `required="false"` намеренно: `true`
  заблокировал бы установку на аппаратах, которые о фиче не сообщают.

**Что это не доказывает.** Отсутствие объявления не объявляется причиной: до
2026-09-03 на том же хосте всё работало. Причина станет видна из следующего
evidence — по `host.usbHostFeature` и `scan_completed`.

**Про роль `onyx` — исправлено.** В первой редакции этого раздела запись из
`KNOWN_USB_DEVICE_QUIRKS.md` была отнесена к хосту. Это неверное чтение: весь
материал того документа описывает `onyx` **в роли пациента**, то есть цели, и
про его поведение в роли хоста там не сказано ничего. Полевое наблюдение
владельца: как хост `onyx` работает нормально, проблемным он был именно как
цель.

К разбору 2026-09-04 та запись к тому же не относится вовсе: целью был
POCO X3 Pro (`vayu`), а не `onyx`. Хост из числа подозреваемых исключается, пока
`scan_completed` и `host.usbHostFeature` не скажут обратного.

приложение не работало, — узнать об этом станет только по кнопке. Скан при
возвращении на экран это закрыл бы. В текущем случае не помог бы: ручной скан
дал ноль.

## 6.24. Recovery на устройстве — 2026-09-05, PASS частичный

Другая цель: `serial:cc16218c`, `productId=0xD001`, интерфейс `ADB · CANONICAL`.

| Что наблюдалось | Результат |
|---|---|
| Режим peer'а | `RECOVERY` — определён из баннера, а не угадан |
| Авторизация | **не потребовалась**: ни `auth_required`, ни `host_key` в журнале |
| Рукопожатие | `CNXN` отправлен и ответ получен за **1 мс** |
| Возможности | 17 против 23 у обычной системы |
| Переподключение | второе поколение открылось и подключилось так же |

**Почему это важно.** До сих пор все прогоны шли против обычной системы, где
`adbd` требует подтверждения. Recovery подтверждает вторую ветку: соединение
устанавливается сразу, и предположение «диалог будет всегда» неверно. В
Recovery подтверждать его было бы некому — там нет экрана блокировки и
пользователя, который нажимает «Разрешить».

**Команды в Recovery — прогон 2026-09-05 20:48.** `id` вернул 272 байта,
`getprop ro.build.version.release` — 14, обе через `shell,v2,raw:`. Список
возможностей теперь виден в журнале, и `shell_v2` в нём есть: **Recovery
объявляет его наравне с обычной системой**. Ожидание, что откат сработает
именно здесь, не оправдалось.

**Откат на `shell:` по-прежнему не выполнялся на железе.** Сработает он на
peer'е без `shell_v2` — это Android 6 и старше либо Sideload. До такого прогона
ветка остаётся покрытой только тестами, и в `09` она отмечена частичной.

**Чего не хватило журналу.** Событие `connected` записывало **число**
возможностей, а не их список. По числу нельзя сказать, объявлен ли `shell_v2`, и
разбор упёрся в это сразу же. Исправлено: теперь записывается список.

**Что нашлось попутно.** Тест на новую запись упал и вскрыл настоящее
ограничение разбора: `features=` искались только среди частей, разделённых
точкой с запятой. Для баннера обычной системы это одно и то же — там перед
списком всегда есть свойства. Но `recovery::features=cmd` без единого свойства
был бы разобран как «возможностей нет», и команда ушла бы устаревшей веткой при
живом `shell_v2`. Разбор расширен, случай покрыт тестом.

## 6.30. Разбор AUTH без диалога — закрыт новым evidence

Предыдущие попытки с `vayu` на разных host-install состояниях доходили до

## 6.31. Аудит согласованности и Terminal correctness — 2026-09-07

Это **software/static audit changeset**, а не новый аппаратный PASS. Он приводит
код и каноническую документацию в соответствие с уже действующим правилом:
NekoFlash — инструмент для профессионалов; correctness-защита обязательна, но
валидные возможности протокола не должны скрываться за product-level gate.

Исправлено по результатам полного прохода дерева:

- `README.md`, `docs/README.md`, roadmap и recovery handoff синхронизированы с
  фактической текущей **Phase 4**;
- нумерация evidence §6.x восстановлена: `6.5` снова стоит после `6.4`, а
  пропущенный номер перед интерактивной оболочкой устранён;
- `push` и `pull` больше не объединены одним статусом: read-only `RECV` существует

- блокирующий USB I/O Terminal больше не запускается из Compose callback/UI

  по-прежнему один;

- stdout/stderr/legacy shell декодируются потоковым UTF-8 decoder, поэтому
  многобайтовый символ не портится, если граница символа совпала с границей

- выгрузка diagnostics перенесена на `Dispatchers.IO`;
- добавлены unit-тесты для controller-level очередности Terminal и для чистой
  части `usb:android`; protocol-тестами закреплены `OKAY`, разрезанный UTF-8 и
  сохранение прежней очистки NUL в `shell,v2`;
- закрытие Terminal удерживает reader ownership до отправки корректного
  `CLSE` и выхода reader loop; если `OKAY` ещё не пришёл, закрытие сначала
  дожидается remoteId и не удаляет opening-stream преждевременно;
- стилевой detekt-run теперь охватывает production Kotlin всех семи модулей, а
  не только `app/src` и `core`; единственное явно зафиксированное rule-level
  исключение — `MagicNumber` для production source `protocol:adb`, где числа
  являются wire-format command words/masks/offsets/shifts; остальные правила
  detekt этот модуль продолжают проверять;
- крупный `NekoFlashApp.kt` разделён по ответственности, ADB UI/state вынесены
  из монолитного файла;
- добавлен CI-гейт `check_docs_consistency.py`: он сверяет current Phase между

multiplexer**: постоянный physical reader/dispatcher, который одновременно

он не построен и не подтверждён, одноразовые shell/file/service calls при живом

## 6.32. AUTH, большой RECV и late `CLSE` — 2026-09-07

Этот прогон выполнялся уже после зелёного GitHub Actions для
`c1478aa932c485c1179108e5897c88d20f0e05e3`. Он закрыл два аппаратных вопроса
Phase 4 и одновременно обнаружил один protocol-correctness defect.

**AUTH — PASS.** Первичная авторизация прошла через `AUTH TOKEN` → signature →
повторный token → `AUTH RSAPUBLICKEY` → системный RSA-диалог → `CNXN`. После
подтверждения устройство подключилось, а повторное подключение тем же ключом
дало `CNXN` через 14 мс без повторной отправки public key. Полная последовательность
и исправленная трактовка тишины после public key записаны в §6.30.

**Read-only Sync / RECV — PASS по критерию целостности.** Малый файл дал
`STAT size=10` и `RECV bytes=10`. Файл 2 MiB дал `STAT size=2097152`,
`RECV bytes=2097152`; SHA-256 на экране NekoFlash совпал с эталоном:
`5647f05ec18958947d32874eeb788fa396a05d0bab7c1b71f112ceb7e9b31eee`.
Подробности — §6.29.

**Найден late `CLSE`.** После освобождения и нового захвата интерфейса одна
попытка отправила новый `CNXN`, но первым входящим пакетом оказался
`command=0x45534c43` (`CLSE`) от logical stream предыдущего соединения. Старый
handshake трактовал любой пакет кроме `CNXN/AUTH` как фатальный и завершился
`UNEXPECTED_COMMAND`; следующая попытка через 10 секунд подключилась нормально.

Это не причина скрывать повторное подключение. `CLSE` с stream IDs до ответа
на новый `CNXN` не может быть ответом handshake и является поздним закрытием
старого logical stream. Исправление узкое: до первого `CNXN/AUTH` handshake
пропускает ограниченное число именно `CLSE`, записывая
`handshake_stale_close` с remote/local IDs. Другие неожиданные команды
по-прежнему фатальны; framing errors не игнорируются.

**UI AUTH.** Состояние «ждём авторизацию» раньше выставлялось до вызова
`connection.connect()`, то есть UI мог предлагать подтвердить RSA ещё до
фактического `AUTH RSAPUBLICKEY`. Теперь оно появляется только после успешной
записи public key. Текст также описывает факт протокола и лишь условно сообщает,
что обычный Android может показать RSA-диалог.

**Diagnostics.** Успешный `sync_received` теперь содержит `path`, `bytes` и
`sha256`. Следующий hardware bundle сможет сам доказать целостность RECV без
отдельного скриншота.

## 6.33. Сплошной аудит дерева — 2026-09-07

Аудит без нового кода и без аппаратного прогона: проверка того, что документы
говорят то же, что делает код. Проверено на `b3a6642`.

**Подтверждено независимо от гейтов.** 372 `@Test` — ровно столько, сколько
заявляет `99_RECOVERY_HANDOFF_RU.md`. Три архива сходятся с

соблюдены во всех семи модулях. В production нет ни `TODO/FIXME/HACK`, ни
`NotImplemented`, ни `.orig`. Продуктовый закон держится и в коде: ни
allowlist, ни `if (dangerous) reject`, ни фильтрации команд в терминале;
`AdbServiceCall` принимает произвольное имя сервиса, а его пределы — ресурсные
границы вызывающего с отдельными исходами `OUTPUT_TOO_LARGE`/`TIMED_OUT`, а не
тихое обрезание. Инвариант `vayu` прослежен в `AdbPacketReader` по коду:
заголовок добирается циклом до 24 байт, payload читается одной операцией,
короткий результат даёт `SHORT_PAYLOAD` fail-closed.

**Найдено три расхождения, все документационные. Дефектов корректности нет.**

- `09_IMPLEMENTATION_ROADMAP_RU.md` утверждал, что `CNXN` ещё не объявляет
  `maxdata`. Объявляет: `AdbConnection` считает значение один раз и отдаёт его
  и в `arg1` пакета `CNXN`, и в `AdbPacketReader` как предел длины кадра.
  Документ противоречил при этом сам себе — строка выше называла объявление
  `maxdata` единственным непроверенным на железе пунктом;
- `AdbConnection.kt` нёс два KDoc-блока подряд: «Проводит рукопожатие» стоял
  над свойством `peerFeatures`, а сама `connect()` осталась без документации.
  Kotlin привязывает только последний блок, поэтому ни компилятор, ни detekt
  этого не видят. Проход по всему дереву показал, что случай единственный;
- `UsbSessionRegistry.kt` объяснял отказ писать диагностику тем, что так
  `usb:api` не тянет зависимость на `core:diagnostics`. Зависимость есть и
  используется — `UsbSessionCoordinator` пишет события, `UsbDiagnosticReport`
  собирает разделы. Решение реестра осталось верным, ложным стало обоснование.

**Оставлено сознательно.** `AdbSyncProtocol` объявляет `ID_SEND`, `ID_OKAY`,
`ID_DENT` и `ID_QUIT`, которых пока никто не вызывает. Это описание формата
провода, а не production stub: значения принадлежат протоколу целиком, и
объявлять их по одному вместе с командами значило бы разносить один формат по
разным changeset'ам. `emptyStateReason` в `:app` содержит выбор из четырёх
причин пустого списка внутри `@Composable`, поэтому pure-JVM тестом не
покрывается; это отступление от принципа §6.4 и кандидат на вынос чистой части,

## 6.34. Аппаратный гейт записи файла — план; закрыт прогонами §6.36 и §6.38

Раздел написан **до** прогона. `SEND` — первая мутация в проекте, и критерий,
придуманный после того, как результат виден, критерием не является.

**Что проверяется.** `AdbSyncSession.send`: спецификация назначения, поток
блоков `DATA`, `DONE` со временем изменения и вердикт устройства. Отдельно —
что о состоянии файла назначения сообщается ровно то, что доказано.

**Почему гейт нельзя пропустить.** Ни один тест здесь не отвечает на главный
вопрос: в какой момент `adbd` создаёт и обрезает файл. Подставной транспорт
знает только то, что заложил автор. До прогона граница мутации остаётся
консервативным предположением, а не измеренным фактом.

| Сценарий | Что должно наблюдаться |
|---|---|
| Запись малого файла в `/sdcard` | `OKAY`; `sync_sent` с `bytes` и `sha256`; `sha256sum` на устройстве совпадает с отпечатком на экране |
| Запись файла больше 2 MiB | то же; блоки идут по 64 КиБ, память приложения не растёт пропорционально файлу |
| Запись в `/system` без прав | `FAIL` с настоящим текстом устройства; исход `DEVICE_REFUSED`, назначение `UNKNOWN` |
| Перезапись существующего файла | `OKAY`; отпечаток совпадает с новым содержимым, а не со старым |
| Отключение кабеля посреди `DATA` | назначение `UNKNOWN`, автоматического повтора нет |
| Режим созданного файла | вне `/sdcard`: `ls -l` показывает переданный режим. На `/sdcard` строка непроверяема — эмулированное хранилище навязывает свои права (§6.38), и это ответ устройства, а не наш дефект |

**Критерий PASS.** Наблюдаются первые пять сценариев плюс режим созданного
файла, evidence выгружен приложением, `droppedEvents=0`, отпечатки совпадают.

**Строка про границу мутации в критерий PASS не входит и входить не может.**
Она не проверяет реализацию, а измеряет предположение, на котором реализация
построена. Формулировка этой строки в первой редакции была негодной, и прогон
§6.36 это показал: «посмотреть, существует ли файл» **не различает две
гипотезы**. «Файл не создавался» и «файл создан, а при обрыве `adbd` его
удалил» дают одинаковый ответ `STAT` с нулевым режимом. Разница же
принципиальная: во втором случае назначение было мутировано, и лежавший там
раньше файл уничтожен.

Решающий сценарий — §6.37: писать поверх **существующего** файла с известным
отпечатком и оборвать передачу. Уцелевшее старое содержимое доказывает, что
`SEND` назначения не тронул; изменившееся или исчезнувшее — что тронул.

**Чем нажимать.** В секции «Файлы устройства» появились кнопки «Записать
4 КиБ» и «Записать 16 МиБ». Содержимое порождает само приложение: выбор
пользовательского файла требует artifact source из Phase 8, а для этого гейта
он и не нужен — проверяется протокольный путь, а не сценарий push. Узор
детерминирован, поэтому прогон воспроизводим, и его период — простое число,
чтобы перепутанные местами блоки не дали тот же отпечаток.

Малый размер проходит одним блоком, большой — двумястами пятьюдесятью шестью;
шестнадцати мегабайт хватает и на требование «больше 2 MiB», и на то, чтобы
успеть выдернуть кабель посреди передачи.

**Чего гейт не закрывает.** Пользовательский push: выбрать свой файл всё ещё
нельзя. Гейт проверяет протокольный путь.

## 6.37. Аппаратный гейт границы мутации — план; закрыт прогоном §6.38

Раздел написан до прогона. Гейт измеряет предположение, на котором построен
`AdbSyncSendOutcome`: что запрос `SEND` уже меняет назначение.

**Почему §6.36 не ответил.** Там писали в несуществующий путь, и отсутствие
файла после обрыва одинаково объясняется двумя противоположными гипотезами.
Различить их можно только по судьбе **уже лежащего** там содержимого.

| Шаг | Что сделать |
|---|---|
| 1 | Записать 4 КиБ в `/sdcard/nf-b.bin`, запомнить отпечаток |
| 2 | Сверить `sha256sum /sdcard/nf-b.bin` — исходное состояние зафиксировано |
| 3 | Записать в **тот же** путь 16 МиБ и выдернуть кабель через 1–2 с |
| 4 | Переподключиться, `Проверить` путь — записать режим и размер |
| 5 | `sha256sum /sdcard/nf-b.bin` и `ls -l /sdcard/nf-b.bin` |

**Как читать результат.**

- отпечаток шага 5 равен отпечатку шага 2 → `SEND` назначения **не тронул**,
  и граница мутации может быть ослаблена до первого блока `DATA` — отдельным
  решением, потому что это меняет, когда операция вправе отвечать `Cancelled`;
- отпечаток изменился, размер другой или файл исчез → `SEND` тронул
  назначение, и текущая консервативная граница **доказана**;
- результат плавает от прогона к прогону → граница остаётся консервативной,
  и это записывается как свойство устройства, а не как неудача.

Повторить не менее трёх раз: одиночный результат здесь ничего не значит.

**Чего гейт не решает.** Ответ верен для этой версии `adbd` и этой файловой
системы. Переносить его на другие устройства без своего прогона нельзя —
`16_AGENT_OPERATING_PROMPT_RU.md` §3 про квирки в роли.

## 6.44. Аппаратный гейт перезагрузки — план; закрыт прогоном §6.46

Раздел написан **до** прогона. `reboot:` — односторонний сервис, и проверить
его подставным транспортом нельзя по той же причине, по которой он и особенный:
успех здесь выглядит как обрыв, а обрыв подставного транспорта устраивает не
устройство, а тест.

**Что проверяется.** Что успешная перезагрузка отличается от неудачной. Обе
кончаются потерей соединения, и если приложение не умеет их различать, оно
будет сообщать успех всегда — в том числе когда устройство отказало.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Подключиться, оставить поле цели **пустым**, нажать «Перезагрузить» | `reboot_requested service=reboot:`, затем `reboot_accepted`; устройство уходит в перезагрузку |
| 2 | Дождаться загрузки, подключиться снова | `reboot_accepted` не помешал следующему поколению: generation растёт, рукопожатие проходит |
| 3 | Цель `bootloader`, нажать «Перезагрузить» | `reboot_accepted service=reboot:bootloader`; устройство ушло в загрузчик |
| 4 | Вернуть устройство в систему, подключиться | подключение проходит |
| 5 | Цель `нетакойцели`, нажать «Перезагрузить» | **вот здесь главное**: что ответит устройство. Записать `reboot_failed` целиком — `reason`, `device`, `detail` |
| 6 | Открыть оболочку, не закрывая её — нажать «Перезагрузить» с пустой целью | перезагрузка уходит своим потоком; в журнале виден её `stream=`, отличный от `stream=` оболочки |

**Как читать результат.**

- шаги 1–4 прошли → протокольный путь верен, и пункт чеклиста можно закрывать;
- ~~шаг 5 дал `reboot_accepted` → это дефект~~ — **критерий был неверен, и это
  исправлено после прогона §6.46**. Он опирался на предположение, что `adbd`
  отвергнет незнакомую цель. Железо показало обратное: причина перезагрузки —
  произвольная строка, и устройство перезагружается с любой. Ошибка была в
  представлении автора гейта об устройстве, а не в коде;
- шаг 5 дал `reboot_failed` с `device=UNTOUCHED` → верно: устройство отказало
  словами, ничего не тронуто, повтор безопасен;
- шаг 5 дал `NO_TRANSITION` с `device=UNKNOWN` → устройство промолчало и не
  ушло с шины. Тоже верно, но записать отдельно: значит, эта версия `adbd` на
  неизвестную цель не отвечает вовсе, и это свойство устройства.

**Чего гейт не проверяет.** Оборванную отправку самого запроса: попасть
выдёргиванием кабеля в 24 байта заголовка нельзя. Ветки `SEND_FAILED` и
`FRAMING_LOST` остаются на тестах, и это записано честно, а не выдано за
проверенное.

**Отдельно про шаг 5.** Цель не ограничивается списком (`01` §3), поэтому
«нетакойцели» — не диверсия, а обычный ввод, на который у устройства есть свой
ответ. Гейт проверяет, что мы этот ответ передаём, а не подменяем своим.
## 6.45. Аппаратный гейт произвольного сервиса — план; закрыт прогоном §6.46

Раздел написан **до** прогона. Проверяется не «сервис вызвался», а три вещи,
которые подставным транспортом не проверяются: что имя уходит как набрано, что
ответ не текстового сервиса не выдаётся за текст и что односторонний сервис
узнаётся **по имени**, откуда бы его ни набрали.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Вызвать `shell:id` | `service_completed`; на экране размер в байтах и текст `uid=…` |
| 2 | Вызвать `sync:` | ожидается `TIMED_OUT` примерно через 30 с: сервис открылся, но ждёт бинарных запросов, которых поле ввода не шлёт. Важно, что вызов **кончается сам** и не роняет соединение |
| 3 | Вызвать `exec:id` | ответ без рамок `shell,v2`: сравнить с шагом 1 и записать разницу |
| 4 | Вызвать `нетакогосервиса:` | `service_failed reason=REJECTED`; соединение живо, следующий вызов проходит |
| 5 | Вызвать `reboot:` **из этого поля** | **главная строка**: `reboot_requested` и `reboot_accepted` в журнале, на экране «принят, устройство ушло с шины» — а не отказ |
| 6 | После перезагрузки подключиться и вызвать `shell:id` | соединение восстановилось, вызовы идут |

**Как читать результат.**

- шаг 5 показал отказ → дефект: одностороннюю политику применили не по имени
  сервиса, и экран соврал про то, что произошло на самом деле;
- шаг 4 оборвал соединение → дефект: отказ в сервисе не должен ронять
  транспорт, это подтверждалось ещё в §6.29 для `RECV`;
- шаг 2 повис навсегда или оборвал соединение → дефект; `TIMED_OUT` через
  отведённое время — верный исход, а не неудача гейта.

**Про нетекстовый ответ.** Ни один шаг выше его не даёт: у `sync:` ответа не
будет вовсе, а `shell:` и `exec:` отвечают текстом. Показ размера отдельно от
текста поэтому остаётся проверенным только тестами, и записать это надо прямо,
а не считать проверенным заодно. Сервис, который отдаёт байты и сам закрывает
поток, на подопытном устройстве ещё предстоит найти.

**Чего гейт не проверяет.** Сервисы, которых нет на подопытном устройстве, и
поведение при выводе больше 64 КиБ — потолок вызова обрезает раньше, и это
свойство `AdbServiceCall`, а не произвольного сервиса.
## 6.46. Перезагрузка и произвольный сервис — 2026-09-10, PASS и найденный дефект

Гейты §6.44 и §6.45 отработали за один прогон. Сборка `584c505`,
`droppedEvents=0`. Всё, что гейты просили, прошло, и сверх того нашёлся
**дефект в моём коде**, который не мог найтись иначе.

**Произвольный сервис — PASS по всем строкам.**

| Сервис | Итог |
|---|---|
| `shell:id` | `service_completed bytes=263` |
| `sync:` | `TIMED_OUT` ровно через 30 с; соединение живо, следующий вызов прошёл |
| `exec:id` | `service_completed bytes=263` — **тот же размер**, что у `shell:id` |
| `нетакогосервиса:` | `REJECTED`, `closed before OKAY`; соединение живо |
| `reboot:` из поля сервиса | `reboot_requested` → `reboot_accepted` |

Последняя строка была главной, и она прошла: односторонняя политика применилась
**по имени сервиса**, а не по нажатой кнопке.

Совпадение размеров у `shell:id` и `exec:id` стоит записать: гейт ожидал
разницы в рамках, а её нет, потому что `shell:` без `,v2` рамок и не имеет.
Разница появилась бы при сравнении с `shell,v2,raw:`, а не с `shell:`.

**Перезагрузка — PASS, и один результат решающий.**

| Цель | Что наблюдалось |
|---|---|
| пустая | `accepted evidence=transport closed`, generation 1 закрыта `DETACHED`, устройство вернулось |
| `нетакойцели` | `accepted`, устройство **перезагрузилось** и вернулось как ADB |
| `bootloader` | `accepted`, generation 4 поднялась с интерфейсом **FASTBOOT** |
| `recovery` | `accepted`, устройство вернулось как ADB в recovery |

Строка `bootloader` — самая убедительная: смена роли интерфейса на `FASTBOOT`
это наблюдение, а не толкование. Устройство действительно ушло в загрузчик.

**Критерий гейта §6.44 про несуществующую цель был написан неверно, и это моя
ошибка.** Гейт говорил: `reboot_accepted` на цель `нетакойцели` — дефект.
Железо показало обратное: `adbd` принимает любую строку как причину
перезагрузки и перезагружается. Ошибка не в коде, а в предположении автора
гейта о том, как устроено устройство. Строка исправлена — но исправлена **после**
прогона и потому помечена как исправленная, а не переписана молча.

### Найденный дефект: `UNTOUCHED` после границы мутации

Пятый запрос ушёл, когда устройство было **в recovery**. Ответ:

    19:10:52.624  reboot_failed reason=DEVICE_REFUSED device=UNTOUCHED detail=reboot.
    19:10:52.960  usb session_closed_detached generation=6
    19:11:08      generation 7 — устройство вернулось

Мы сказали оператору «устройство не тронуто» — и **через 336 мс** устройство
ушло в перезагрузку. Recovery ответила словом `reboot.` и перезагрузилась.

Дефект не в том, что мы не угадали смысл слова `reboot.`. Дефект в том, что
ветка ответа текстом стоит **после границы мутации** — `OPEN` к тому моменту
записан целиком, — а отвечала `UNTOUCHED`. Правило про границу записано в KDoc
того же класса с самого начала: до границы устройство не тронуто, после —
доказать это нечем. Ветка его нарушала.

Исправлено тем же changeset: причина переименована в `DEVICE_ANSWERED`,
состояние — `UNKNOWN`. Слово устройства передаётся оператору дословно и не
переводится в вердикт: что оно значит, знает устройство, а приписывать ему
решение, которого оно не выносило, — то же самое враньё, только вежливое.

**Что это стоит помнить.** Тесты этот случай пропустили не по невнимательности:
они проверяли то же самое утверждение, которое было неверным. Проверка
называлась `textFromTheDeviceIsARefusalAndNotATransition` и добросовестно
закрепляла ошибку. Такое ловится только устройством.

**Возможное улучшение, у которого пока нет гейта.** Если после ответа текстом
подождать смерти транспорта, случай recovery превратился бы из `UNKNOWN` в
честный `Accepted`. Это изменение поведения, и делать его без своего гейта
нельзя — гейт пишется первым; он записан как §6.47.

**Поправка к этому абзацу, сделанная при подготовке §6.47.** Сначала здесь
было сказано, что такое окно «держал Legacy», со ссылкой на
`EXPECTED_REBOOT_DISCONNECT_WINDOW_NS`. Это неверно, и ошибка моя: константа
была найдена грепом, а её использование не открыто. Пятнадцать секунд в Legacy
нужны **читающему циклу** — чтобы последующий обрыв транспорта не
эскалировался как ошибка операции (`AdbProtocol.kt:2540`); исход же сервиса
Legacy решает на `A_CLSE` и возвращает успех независимо от того, сказало
устройство что-нибудь или нет. Идея «подождать смерти транспорта после ответа
текстом» — наша, а не архивная, и приписывать её Legacy нельзя. Ровно от этого
предостерегает `16` §3, и предостережение сработало не зря.
## 6.47. Гейт ожидания разрыва после ответа текстом — план; прогоны §6.48 и §6.50

Раздел написан **до** кода и до прогона. Закрывает то, что осталось от §6.46:
recovery отвечает словом и уходит в перезагрузку, а мы отвечаем `UNKNOWN`.

**Что меняется.** После ответа текстом решение не принимается сразу. Мы ждём —
не дольше отдельного небольшого окна, — умрёт ли транспорт. Умер: устройство
ушло с шины, значит перешло, и это `Accepted`; слова устройства при этом
переносятся в evidence целиком. Не умер: устройство ответило и осталось, и
состояние остаётся `UNKNOWN`.

**Почему не проще.** Рассматривались три варианта, и два отвергнуты.

| Вариант | Почему нет |
|---|---|
| Считать закрытие потока успехом, как Legacy | Настоящий отказ «not permitted» стал бы `Accepted`. Это ложь в сторону, где оператор поверит, что устройство перезагружается, и уйдёт ждать |
| Оставить `UNKNOWN` навсегда | Не врёт, но в частом случае даёт худший ответ, чем позволяет наблюдение |
| **Ждать смерти транспорта** | Различает случаи **наблюдением**, а не толкованием текста устройства |

Толковать текст мы по-прежнему не будем: `reboot.` и `not permitted` для нас
одинаково непрозрачны, и решает не их смысл, а ушло ли устройство с шины.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Перевести устройство в recovery (`reboot:recovery`) и дождаться подключения | generation поднялась, ADB отвечает |
| 2 | В recovery нажать «Перезагрузить» с пустой целью | `reboot_accepted`, и в `evidence` видны **и слова устройства, и уход с шины** |
| 3 | Дождаться загрузки, подключиться | устройство вернулось; `reboot_failed` в журнале за этот запрос нет |
| 4 | В обычной системе повторить пустую цель | `reboot_accepted` как в §6.46 — поведение без текста не изменилось |
| 5 | Повторить `bootloader` | `accepted`, интерфейс поднимается как `FASTBOOT` — прежний результат не сломан |

**Как читать результат.**

- шаг 2 дал `accepted` со словами устройства в evidence → улучшение работает,
  и §6.46 закрыт;
- шаг 2 дал `accepted` **без** слов в evidence → ветка ответа не вызвана:
  устройство ушло молча. В первой редакции здесь стояло «мы потеряли то, что
  сказало устройство», и это сильнее, чем позволяет наблюдение — с хоста
  неразличимы «промолчало» и «сказало, но слова не пережили отпадение»
  (§6.50). Шаг повторяется, пока в evidence не появится `device said:`;
- шаг 2 дал `DEVICE_ANSWERED`/`UNKNOWN` → сравнить измеренную паузу из журнала
  (`reboot_failed` и соседний `session_closed_detached`) с окном. Пауза **больше**
  окна — окно мало, менять по измеренному числу. Пауза **меньше** — дело не в
  окне, а в сигнале: смотреть, откуда узнаётся уход с шины. Второй случай
  и произошёл, см. §6.48; в первой редакции этой строки он предусмотрен не был;
- шаги 4 и 5 изменились по сравнению с §6.46 → регрессия: улучшение задело
  путь, которого не должно было касаться.

**Чего гейт не проверяет, и это важно.** Случай «устройство ответило текстом и
осталось на шине» на подопытном устройстве вызвать нечем: отказать в
перезагрузке `vayu` не отказывается. Ветка «окно истекло, транспорт жив»
остаётся на тестах, и записать это надо прямо, а не считать проверенным
заодно. Именно в этой ветке живёт `UNKNOWN`, ради которого всё и затевалось.

**Мера предосторожности.** Ожидание добавляется **после** ответа и потому может
увеличить общее время вызова сверх запрошенного таймаута. Это осознанно: цена —
несколько секунд ожидания, выигрыш — верный ответ вместо «не знаю».
## 6.48. Ожидание разрыва не сработало — 2026-09-10, дефект найден и исправлен

Гейт §6.47 отработал и **провалил** улучшение. Сборка `905abb7`,
`droppedEvents=0`. Провал полезнее, чем прошёл бы успех: он показал, что
неверен был не размер окна, а сам сигнал.

**Что наблюдалось.** Второй запрос ушёл из recovery:

    19:42:23.246  reboot_requested service=reboot:bootloader
    19:42:23.552  usb session_closed_detached generation=2
    19:42:25.288  reboot_failed reason=DEVICE_ANSWERED device=UNKNOWN detail=reboot-bootloader.
    19:42:27.217  usb session_opened generation=3 interfaceKind=FASTBOOT

Устройство ответило словом `reboot-bootloader.` и ушло с шины через **306 мс**
— то есть глубоко **внутри** двухсекундного окна. Мы всё равно ответили «не
знаю», а ещё через две секунды устройство поднялось загрузчиком.

**Диагноз гейта не подошёл, и это надо сказать прямо.** §6.47 предусматривал
единственную причину такого исхода: «окно короче, чем пауза устройства», и
предписывал измерить паузу. Пауза измерена — 306 мс, — и она в шесть раз
меньше окна. Причина оказалась другой, гейтом не предусмотренной.

**Настоящая причина.** `transportEnd` смотрел только на цикл раскладки, а цикл
знает лишь те беды, которые принёс сам: обрыв чтения и потерю кадра. В
production об отпадении устройства первым узнаёт USB-слой — он закрывает
сессию, владелец закрывает соединение, и цикл кончается **по просьбе**. Его
поле в этом случае пусто, что видно и по evidence успешных перезагрузок:
`dispatch loop stopped`, а не `transport closed`.

Я исключил остановку по просьбе намеренно и написал в KDoc, что путать её со
смертью транспорта нельзя. Рассуждение верное, вывод неверный: смерть
транспорта эту остановку и **вызывает**.

**Исправление.** Спрашивать надо у транспорта, а не выводить из цикла:
интерфейс больше не удерживается — значит устройства нет. Причина, названная
самим циклом, остаётся весомее: она точнее. Решение вынесено в
`AdbTransportEnd.of(loopEnd, held)` и покрыто тремя проверками, среди которых
ровно та комбинация, что провалилась здесь: цикл молчит, интерфейс отпущен.

**Чего этот прогон не отменяет.** Первый запрос (`reboot:recovery` из системы)
прошёл как `accepted`, и `bootloader` поднял FASTBOOT-интерфейс — прежние
результаты §6.46 не сломаны. Улучшение не сломало ничего; оно просто не
работало.

**Что осталось непроверенным.** Само улучшение на железе так и не
подтверждено: прогон показал, что его не было. Гейт §6.47 остаётся открытым и
повторяется на исправленной сборке — шаги те же.

## 6.49. Сборка упала на гонке в тесте — 2026-09-10, разбор и исправление

**Сначала о своей ошибке.** Я отчитался об исправлении §6.48, не дождавшись
сборки. Сборка упала, и заметил это не я. Отчёт до зелёного CI — это не отчёт,
и правило простое: сначала прогон, потом слова.

**Что упало.** Run 97, `dd2d4d5`:

    AdbServiceCallTest > closedStreamIsAcknowledgedBack FAILED
        java.lang.AssertionError at AdbServiceCallTest.kt:60
    289 tests completed, 1 failed

**Это не тот коммит.** Ни `dd2d4d5`, ни `905abb7` не трогают ни
`AdbServiceCall`, ни его сюиту, а `1cd2816` и `905abb7` прошли зелёными.
Коммит не сломал тест — он изменил раскладку по времени ровно настолько, чтобы
уже существующая гонка сработала. Списывать такое на «флаки» нельзя: причина
находится и оказывается настоящей.

**Причина.** Проверка наблюдала **чужой** поток. Ответное `CLSE` на закрытие
устройства пишет цикл раскладки, и пишет он его **после** `dispatcher.dispatch`
— а разбудил вызов `dispatch` уже внутри себя, закрыв ящик. Между «вызов
вернул `Completed`» и «подтверждение ушло на провод» порядка нет, и снимок
`sentFrames()` сразу после `run` показывал последним кадром `OPEN`.

**Порядок остаётся таким намеренно.** Отправлять подтверждение под замком
диспетчера значило бы держать замок всё время передачи — до пяти секунд по
`AdbPacketWriter.DEFAULT_SEND_TIMEOUT_MS` — и блокировать этим `open`, `write`
и `close` чужих потоков, то есть ровно ту одновременность, ради которой
затевался ADR-0004. Неверна была проверка, а не код: она утверждала
последовательность, которой система не обещает и обещать не должна.

**Гейт записан до исправления.** Воспроизведение — одно ядро, `taskset -c 0`:
на нём планировщик отдаёт потоки крупными кусками, и окно гонки становится
широким. Критерий: до исправления класс падает, после — не падает ни разу за
30 прогонов на тех же условиях.

Замер до исправления: `AdbServiceCallTest` в одиночку — **20 падений из 45**.
Вся сюита на том же ядре — 0 из 6: полная сюита прогревает JIT и окно
закрывается, поэтому одиночный класс здесь показательнее.

**Исправление.** В подставном транспорте появилось ожидание
`awaitSentFrames(count)`: «мы отправили X» проверяется дождавшись, а не
снимком. Заодно `sentFrames()` научилась отбрасывать незаконченный хвост —
снимок, взятый между заголовком и payload чужого потока, раньше падал по
выходу за границу списка, и выглядело бы это как поломка писателя.

**Тот же класс нашёлся ещё дважды.**

- `outputBeyondTheCapStopsTheCall`: `OKAY` за второй блок пишет цикл, а `CLSE`
  — сам вызов. «Последний кадр» здесь не был свойством никогда; проверяется то,
  что и требуется: поток закрыт ровно один раз.

## 6.50. Перезагрузка на исправленной сборке — 2026-09-10, регрессий нет, ветка не вызвана

Прогон гейта §6.47 на `ea84a66`. `droppedEvents=0`, одиннадцать поколений,
шесть запросов перезагрузки, ни одного `reboot_failed` за весь журнал.

**Шаги гейта пройдены все пять.**

| Шаг | Наблюдение |
|---|---|
| 1 | `reboot:recovery` из системы → `accepted`, generation 5→6, `peerMode=RECOVERY` |
| 2 | пустая цель из recovery → `accepted`, evidence `dispatch loop stopped`, 345 мс |
| 3 | устройство вернулось (generation 8, `peerMode=DEVICE`), `reboot_failed` за этот запрос нет |
| 4 | пустая цель в системе → `accepted`, evidence `transport closed`, 3,37 с |
| 5 | `bootloader` → `accepted`, generation 10 поднялась как `FASTBOOT` |

Первый проход прогона добавил шестое измерение: `reboot:bootloader` **из
recovery** — `accepted` за 363 мс, `FASTBOOT` через 4,4 с.

**Обе дороги к `accepted` встретились в одном прогоне, и обе верны.** На шаге 4
`reboot_accepted` пришло на 170 мкс раньше, чем USB-слой записал отпадение:
конец принёс сам читатель (`transport closed`). На шаге 2 наоборот — сначала
`session_closed_detached`, через 4 мс `accepted` с `dispatch loop stopped`:
первым узнал USB-слой, а цикл кончился по просьбе. Ровно эти два источника и
разбирает `AdbTransportEnd.of`.

**Главное: улучшение снова не вызвано.** Ни в одном из шести запросов
устройство не сказало ни слова — `evidence` везде `transport closed` или
`dispatch loop stopped`, и ни разу `device said:`. Ветка «ответило словами →
ушло с шины → `accepted` со словами» на железе так и не выполнялась. Значит и
исправление §6.48 остаётся неподтверждённым: подтверждать нечего, пока ветка не
входит.

**Почему слов не было, хотя в §6.48 они были.** Комбинация та же — recovery,
цель `bootloader`, — а результат другой: тогда пришло `reboot-bootloader.`,
теперь тишина. Разница не в коде: слова успевают дойти или не успевают, это
гонка с отпадением интерфейса. После отпадения дочитать то, что осталось в
пути, нечем.

**Строку чтения результата в §6.47 надо поправить, и вот почему.** Там
записано: «шаг 2 дал `accepted` без слов → мы потеряли то, что сказало
устройство». Это утверждение сильнее, чем позволяет наблюдение. С хоста
неразличимы два случая: устройство промолчало и устройство сказало, но слова не
пережили отпадение. Правильный вывод из `accepted` без слов — «ветка ответа не
вызвана», а не «слова потеряны».

**Что осталось и как это закрыть.** Ветка входит только тогда, когда устройство
успевает ответить до ухода. На vayu это выпадает примерно через раз на
комбинации «из recovery, цель `bootloader`». Значит гейт закрывается не новым
сценарием, а **повторением** этого шага, пока в `evidence` не появится
`device said:`. Критерий записан до прогона: `accepted`, в `evidence` и слова
устройства, и упоминание ухода с шины; `DEVICE_ANSWERED`/`UNKNOWN` на этом шаге
означает, что окно всё-таки мало, и тогда менять его по измеренной паузе.

**Fastboot.** Поколения 4 и 10 поднялись как `FASTBOOT` и дошли до
`permission_granted`; `interface_claimed` в них нет — интерфейс захватывается
вручную, и команд для него нет вовсе. Это не дефект: протокол Fastboot в
Phase 4 не входит. Из загрузчика оператор вышел кнопками, и другого способа
приложение сейчас не даёт.

## 6.51. Аппаратный гейт проброса портов — план; закрыт прогоном §6.59

Раздел написан **до** прогона. Закрывает шаги 1–4 плана
`docs/adr/0005_LOCAL_SOCKET_FORWARDING_RU.md`: слушатель на хосте и соединения,
проброшенные через него на устройство. `reverse` сюда не входит и остаётся на
шаги 5–7.

**Что проверяется.** Не «работает ли», а пять утверждений по отдельности:
проброс поднимается, байты идут в обе стороны без потерь, конец с каждой
стороны называется своей причиной, отпадение устройства снимает слушатель, и
два соединения живут одновременно.

**Чем это проверять на телефоне.** Клиент нужен любой, лишь бы соединялся с
`127.0.0.1`. Браузер годится: он шлёт запрос и показывает ответ.

**В браузер вводится `127.0.0.1` и номер порта проброса — и больше ничего.**
Адрес на устройстве (`shell:cat`, `localabstract:...`) набирается только в
приложении и в браузер не вводится никогда. Оператор споткнулся об это дважды,
значит виновата формулировка: подсказка на экране дополнена той же фразой.

**Браузер открывается на хосте — на том же телефоне, где NekoFlash.** Сказать
это прямо пришлось после прогона §6.56: `127.0.0.1` на подопытном означает сам
подопытный, слушателя там нет, и Chrome отвечает `ERR_CONNECTION_REFUSED`.
Формулировка «открыть в браузере» была неоднозначной, и однозначной её делает
только эта строка. Подопытный при этом остаётся подключённым кабелем и ничего
не делает — он вторая сторона проброса, а не клиент.

Адрес на устройстве выбирается из двух, и первый предпочтительнее.

- `localabstract:chrome_devtools_remote` — если на подопытном запущен Chrome с
  отладкой по USB. Тогда `http://127.0.0.1:ПОРТ/json/version` отдаёт **JSON с
  версией Chrome того устройства**, и это проверяемое глазами содержимое, а не
  «что-то пришло».
- `shell:cat` — если Chrome нет. Годится всегда: `cat` возвращает присланное
  обратно, то есть работает эхом. Браузер покажет ошибку — ответ не HTTP, — но
  в журнале будет `forward_closed` со счётчиками, и `fromClient` обязан
  совпасть с `fromDevice`. Совпадение и есть доказательство.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Подключиться, в секции «Проброс портов» набрать порт `0` и адрес, нажать «Пробросить» | в списке появился проброс с **настоящим** портом (не нулём); в журнале `forward_listening` |
| 2 | Открыть в браузере хоста `http://127.0.0.1:ПОРТ/json/version` (или `/` для `shell:cat`) | JSON с версией Chrome **устройства**; для `shell:cat` — `forward_closed`, где `fromClient` равен `fromDevice` |
| 3 | Повторить шаг 2, не закрывая вкладку, во второй вкладке | оба соединения видны как живые одновременно; `forward_open` дважды, разные `stream` |
| 4 | Закрыть вкладки | `forward_closed` с `CLIENT_CLOSED` — конец назван стороной клиента, а не устройством |
| 5 | Набрать заведомо несуществующий адрес, например `localabstract:нет-такого`, и подключиться браузером | `forward_closed` с `REJECTED`; **слушатель остался в списке** — отказ адреса это конец соединения, а не проброса |
| 6 | Нажать «Снять» | проброс исчез из списка; повторное подключение браузером не проходит |
| 7 | Завести проброс снова и выдернуть кабель | пробросов в списке нет; слушатель не пережил транспорт |

**Как читать результат.**

- шаг 2 дал содержимое устройства (или равные счётчики) → направление
  устройство → клиент доказано содержимым, а не фактом соединения;
- счётчики в шаге 2 разошлись → байты теряются, и это дефект передачи, а не
  отображения: смотреть на деление по `maxdata` и на порядок закрытия;
- шаг 3 показал одно соединение вместо двух → одновременности нет, и это
  регрессия ADR-0004, а не особенность проброса;
- шаг 4 дал `DEVICE_CLOSED` вместо `CLIENT_CLOSED` → причины переклеиваются, и
  оператору сообщается не то, что случилось (`ADR-0005` §6);
- шаг 5 убрал слушатель вместе с соединением → перепутаны их времена жизни;
- шаг 7 оставил проброс в списке → слушатель пережил транспорт и принимает
  клиентов в никуда.

**Чего гейт не проверяет, и это надо сказать заранее.** Потолок в шестнадцать
соединений на браузере не вызвать: вкладок столько никто открывать не станет, и
проверка остаётся на тестах (`AdbForwardControllerTest`). Там же остаётся
`REJECTED` без сети и обрыв канала клиента посреди передачи.

**Разрешение, и это оказалось решающим.** Сборка впервые просит `INTERNET`.
Ставить её **поверх прежней нельзя** — надо удалить приложение целиком и
поставить заново. Прежняя сборка `INTERNET` не объявляла, и при установке
поверх хост сетевой доступ не выдал: сокет отказывал на создании, хотя само
разрешение числилось выданным. Разбор — §6.52, §6.53; подтверждение чистой
установкой — §6.54.

В свойствах приложения `INTERNET` не видно и не будет: это normal permission,
её выдают при установке, не спрашивая и не показывая. Проверять её надо по
`app.permissions` в отчёте или по строке отказа на экране.

## 6.52. Сокет отказывает на создании — 2026-09-11, чей отказ, журнал не говорит

Прогон гейта §6.51. `droppedEvents=0`, подопытный подключился и прошёл
рукопожатие (`serial:eff4927c`, `peerMode=DEVICE`). Дальше — восемь попыток
завести проброс и восемь отказов:

    16:11:09.887  forward_failed detail=port 0: socket failed: ECONNREFUSED (Connection refused)
    16:14:18.909  forward_failed detail=port 5555: socket failed: ECONNREFUSED (Connection refused)

Гейт встал на шаге 1 и до шага 2 не дошёл.

**Что установлено наверняка.**

- Отказ произошёл на **создании** сокета, а не на привязке. `ServerSocket(порт,
  очередь, адрес)` делает `socket()`, потом `bind()`, и в тексте названо именно
  `socket`. Значит ни номер порта, ни адрес привязки, ни очередь тут ни при чём.
- Порт роли не играет: `0` (любой свободный) и `5555` отказали одинаково.
  Версия «порт занят» этим закрыта.
- Отказ **виден**, а не молчалив: и на экране, и в журнале. Эта часть шага 1
  отработала так, как задумана, — но она единственная, что отработала.

**Что не установлено, и это главное.** Чей это отказ. Есть ровно две версии, и
журнал не даёт выбрать между ними:

1. в установленной сборке `INTERNET` не было — тогда это наша ошибка, и лечится
   она установкой сборки не старше `7a9ded8`;
2. разрешение было выдано, а сокет всё равно отказывают — тогда запрет стоит
   вне приложения, и установкой другой сборки не лечится.

Различить их по этому отчёту нечем: `host.txt` состава разрешений не содержал.

**Исправление — не догадка, а факт в журнале.** Отчёт получил
`app.permissions`: все объявленные разрешения с их состоянием, как его видит
сама платформа. Строка отказа завести слушатель дополнена тем же фактом:
`port 5555: socket failed: ECONNREFUSED (INTERNET=granted)`. Умолчание —
`unknown`, а не `granted`: соврать там, где не спрашивали, хуже, чем сказать,
что не знаем.

Это ровно тот урок, который §6.43 уже формулировал: доказательство упирается в
то, что записано в журнале, не реже, чем в поведение. Здесь поведение было
видно сразу, а прочесть его было нельзя.

**Что делать на следующем прогоне.** Поставить сборку, где `app.permissions`
есть, и повторить шаг 1. Одна строка журнала закроет вопрос:

- `INTERNET=denied` → версия 1, и дальше смотреть, почему разрешение не
  выдалось при установке;
- `INTERNET=granted` при том же `ECONNREFUSED` → версия 2, запрет вне
  приложения; проверять настройки сети для приложения на самом хосте.

Менять код до этой строки нечего: оба пути ведут наружу от приложения, и
подбирать «обход» вслепую значило бы чинить то, что ещё не названо.

## 6.53. Отказ не наш — 2026-09-11, разрешение выдано, сокет всё равно отказывают

Повторный прогон на сборке `2062702`, где отчёт называет состав разрешений.
Вопрос §6.52 закрылся одной строкой, и закрылся в пользу второй версии:

    app.permissions=INTERNET=granted,DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION=granted

    16:26:17.162  forward_failed detail=port 5555: socket failed: ECONNREFUSED (INTERNET=granted)

**Вывод.** Разрешение у приложения есть — это ответ самой платформы, а не наш
вывод из поведения. Сокет всё равно не создаётся. Значит запрет стоит **вне
приложения**, и ни сборкой, ни кодом он не лечится. Версия «в сборке не было
`INTERNET`» закрыта окончательно.

Заодно закрыт и вопрос о том, куда смотреть оператору: экран «О приложении»
показывает только runtime-разрешения, а `INTERNET` — normal permission, которую
платформа выдаёт при установке, не спрашивая и не показывая. Проверить её на
устройстве было нечем, и теперь есть.

отказе превратили «непонятно, чей отказ» в «отказ не наш» за один прогон. Это
третий случай подряд, когда прогон упирается не в поведение, а в то, что о нём
записано (§6.43, §6.46, §6.52) — и первый, когда запись была подготовлена
заранее и сработала сразу.

**Что остаётся открытым.** Почему хост отказывает в `AF_INET`-сокете
приложению, которому сам же выдал `INTERNET`, — вопрос настройки хоста, а не
кода. Первое, что надо исключить: установку поверх прежней сборки. Прежняя
`INTERNET` не объявляла, и разрешение на сеть у неё не спрашивали; полное
удаление и чистая установка — самая дешёвая проверка.

**Чего делать не следует.** Подбирать обход вслепую. Приложение ведёт себя
правильно: просит разрешение, получает его, честно сообщает отказ и не выдаёт
его за что-то другое. Обход, написанный до того, как отказ назван, чинил бы не
то.

**Если окажется, что `AF_INET` на этом хосте приложению недоступен в
принципе** — в силу вступает альтернатива, отвергнутая в `ADR-0005` §5:
абстрактный Unix-сокет вместо TCP. Она хуже (браузером к нему не подключиться),
и выбирать её заранее не стоит; но тогда решение принимается заново, с этим
наблюдением на руках.

## 6.54. Причина найдена: установка поверх — 2026-09-11, шаг 1 гейта пройден

Приложение удалено целиком и поставлено заново. Слушатель поднялся с первой

    36455 на shell:cat — 0 живых, 0 обслужено

Порт настоящий, а не запрошенный ноль, — значит `ServerSocket` создан,

**Причина названа и подтверждена действием.** Прежняя сборка `INTERNET` не
объявляла. При установке поверх неё хост сетевой доступ приложению не выдал,
хотя само разрешение после обновления манифеста числилось выданным —
`app.permissions` в §6.53 это и показывал. Различие между «разрешение
объявлено и выдано» и «хост пускает в сеть» оказалось наблюдаемым только по
поведению сокета, и именно поэтому §6.52 и §6.53 не могли обойтись без записи

другое. Обход, если бы я его написал после §6.52, чинил бы не то и остался бы
в коде навсегда.

**Что записано в гейт.** Подготовка §6.51 дополнена требованием ставить сборку
начисто, а не поверх. Это не особенность одного телефона: поверх будет ставить
каждый, кто обновляется с версии без `INTERNET`, и наступит на то же самое.

**Что остаётся.** Шаги 2–7 гейта: содержимое в обе стороны, два одновременных
соединения, закрытие с каждой стороны, отказ адреса, снятие, отпадение
устройства.

двумя способами: клиент не приходил, или пришёл и не дошёл до устройства. Это
разные беды — первая на стороне клиента, вторая наша, — и лечатся они в разных
местах. Различить их по этому отчёту нечем.

Хуже того, гейт §6.51 в двух шагах оказался непроверяемым вовсе: снятие
проброса — и по кнопке, и по смерти транспорта — в журнале не писалось ничем.
«Пробросов в списке нет» нельзя было отличить от «их и не заводили». Это надо
было заметить при написании гейта, а не после прогона.

**Исправление.** Три записи и один счётчик:

- `forward_accepted` — слушатель принял соединение. Пишется **до** попытки
  открыть поток, и потому отделяет приход клиента от всего, что дальше;
- `forward_removed` — проброс снят оператором;
- `forward_stopped` — все пробросы сняты разом, с причиной и числом. Пустое
  снятие в журнал не лезет: записывать «снято ноль» значило бы засорять;
- счётчик принятых соединений в самой строке проброса на экране, рядом с
  обслуженными. Теперь `1 принято, 0 обслужено` читается однозначно.

**Что это даёт следующему прогону.** Если браузер до слушателя не доходит,
строка останется `0 принято` — и вопрос будет к клиенту, а не к нам. Если
станет `1 принято, 0 обслужено` — клиент дошёл, а поток не открылся, и это уже
наше, с продолжением в `forward_open`/`forward_failed`.

**Чего прогон не показал.** Почему браузер не подключился, по-прежнему
неизвестно, и гадать об этом до следующего прогона незачем: ровно для этого
запись и добавлена.

## 6.56. Клиент стучался не в тот телефон — 2026-09-11, гейт был двусмысленным

Прогон на сборке со счётчиком принятых соединений. Обе стороны сказали одно и
то же, и вместе они назвали причину:

    16:51:00.514  forward_listening address=shell:cat localPort=40123

На экране NekoFlash: `40123 на shell:cat — 0 живых, 0 принято, 0 обслужено`.
В Chrome на `127.0.0.1:40123`: `ERR_CONNECTION_REFUSED`.

**Счётчик принятых сработал ровно так, как задумывался.** `0 принято` означает,
что до слушателя никто не дошёл, и снимает с нас всё, что было бы дальше:
открытие потока, передачу, закрытие. Дефект — на стороне клиента, а не в
пробросе. Ради этого различения §6.55 и вводил счётчик, и первый же прогон на
нём окупился.

**Причина.** `ERR_CONNECTION_REFUSED` — это TCP RST: на том устройстве, откуда
стучится браузер, на этом порту никто не слушает. Слушатель при этом жив.
Значит браузер и слушатель оказались на **разных** телефонах: `127.0.0.1` на
подопытном означает сам подопытный.

**Дефект в гейте, а не в коде.** §6.51 говорил «открыть в браузере хоста», и
этого оказалось мало: слово «хост» в инструкции для оператора, который держит
два телефона, само по себе не различает их. Формулировка исправлена на прямую —
«на том же телефоне, где NekoFlash», с пояснением, что подопытный остаётся
подключённым и клиентом не является.

**Чего прогон не проверил.** Ничего сверх шага 1: до устройства байты не
доходили, потому что не доходили до слушателя. Шаги 2–7 остаются.

## 6.57. Соединение не проходит и на хосте — 2026-09-11, две версии, одна проверяема

Повтор §6.56 правильно: браузер на том же телефоне, что и NekoFlash.
Результат тот же — `ERR_CONNECTION_REFUSED`, и на экране везде ноль.

    16:51:00.514  forward_listening address=shell:cat localPort=40123
    16:57:54.039  forward_listening address=shell:cat localPort=38261
    16:57:59.554  forward_removed localPort=40123

**Что это сразу исключает.** Слушатель был жив всё время, пока шли попытки:
40123 завели в 16:51 и сняли только в 16:57:59, а `forward_removed` теперь
пишется — запись из §6.55 работает. Значит версия «сокет успел закрыться» не
проходит. Заморозка процесса тоже не подходит: замороженный `accept()` оставил
бы соединение висеть в очереди ядра, а `ERR_CONNECTION_REFUSED` — это RST, то
есть слушающего сокета на этом адресе **нет**.

**Остаются две версии.**

1. Слушаем не на том адресе. `InetAddress.getLoopbackAddress()` отдаёт то
   `127.0.0.1`, то `::1` — в зависимости от настройки JVM, а не от того, куда
   придёт клиент. Слушать на `::1`, когда браузер стучится на `127.0.0.1`,
   значит не слушать вовсе, и снаружи это неотличимо от запрета.
2. Loopback-соединение режет сама система.

**Что сделано.** Неопределённость убрана: привязка теперь к явному
`127.0.0.1`, собранному из байт, а не к тому, что вернёт функция. И адрес
привязки пишется в `forward_listening` — порт о нём не говорил ничего.

**Почему это не «починка вслепую».** Выбор конкретного loopback вместо
недетерминированного — устранение неоднозначности в том, что мы делаем, а не
догадка о причине. Обе версии остаются открытыми, и следующий прогон закроет
их однозначно:

- `bindAddress=127.0.0.1` и соединение пошло → была версия 1;
- `bindAddress=127.0.0.1` и снова ноль принято → версия 1 закрыта
  окончательно, остаётся версия 2, и разбираться надо с системой.

**Чего проверка в тестах не доказывает.** Добавлен тест, который подключается
к не подменённому слушателю по литеральному `127.0.0.1`. Доказательством он не
является и в его KDoc это записано: на JVM ассистента `getLoopbackAddress()`
возвращает `127.0.0.1` при любой настройке `preferIPv6Addresses` — проверено, —
и потому тест не упал бы и до исправления. Он закрепляет намерение, а не
подтверждает догадку.

## 6.58. Проброс работает — 2026-09-11, дело было в адресе привязки

Прогон на сборке с явной привязкой к `127.0.0.1`. Соединения пошли с первой
попытки:

    41727 на shell:cat — 1 живых, 4 принято, 3 обслужено
    Последнее соединение: CLIENT_CLOSED: client closed after 718 bytes (718/718 bytes)

**Версия 1 из §6.57 подтверждена.** Между этим прогоном и предыдущим менялась
ровно одна вещь — адрес привязки слушателя, — и соединения, которых не было ни
одного, пошли все. `getLoopbackAddress()` отдавал не тот loopback, на который
стучится браузер; слушать на нём значило не слушать вовсе, и снаружи это
выглядело как запрет сети. Версия 2 («loopback режет система») закрыта.

**Шаг 2 гейта закрыт, и закрыт содержимым.** `718/718` — это `fromClient` и
`fromDevice`: `shell:cat` вернул ровно столько, сколько послал браузер, байт в
байт. Доказательством служит **совпадение**, а не сам факт соединения: потеря
или лишний байт в любую сторону разошлись бы здесь.

**Шаг 4 закрыт заодно.** `CLIENT_CLOSED` — конец назван стороной клиента, а не
устройством. Причины не переклеиваются (`ADR-0005` §6).

**Три счётчика разошлись, и это правильно.** `4 принято, 3 обслужено, 1 живых`:
слушатель принял четыре соединения, три доведены до конца, одно ещё шло в
момент снимка. Различение из §6.55 работает на живом устройстве ровно так, как
задумывалось, — и именно оно позволило §6.56 и §6.57 не гадать.

**Что осталось.** Шаги 3, 5, 6, 7: два соединения одновременно, отказ адреса
при живом слушателе, снятие, отпадение устройства.

## 6.59. Гейт проброса закрыт — 2026-09-11, все семь шагов

`droppedEvents=0`. Два слушателя, 18 соединений, ни одной записи `forward_failed`
и ни одного `forward_refused` за прогон.

    17:06:56.917  forward_listening address=shell:cat bindAddress=127.0.0.1 localPort=41727
    17:12:39.834  forward_listening address=localabstract:nosuchthing bindAddress=127.0.0.1 localPort=35277
    17:18:02.243  forward_removed localPort=41727
    17:20:00.701  forward_stopped count=1 reason=transport is gone

Счётчики сошлись между собой: 18 `forward_accepted`, 18 `forward_open`,
18 `forward_closed`. Каждое принятое слушателем соединение дошло до открытия
потока — между приёмом и протоколом ничего не терялось.

**Все семь шагов §6.51.**

| Шаг | Чем закрыт |
|---|---|
| 1 | `bindAddress=127.0.0.1`, порт назначен системой, слушатель поднялся |
| 2 | `fromClient=718 fromDevice=718` — `shell:cat` вернул байт в байт |
| 3 | по журналу **четыре** одновременных потока в 17:11:13, не два |
| 4 | 13 исходов `CLIENT_CLOSED` — конец назван стороной клиента |
| 5 | 5 исходов `REJECTED`, слушатель 35277 при этом остался в списке |
| 6 | `forward_removed localPort=41727`, и браузер на 41727 получил `ERR_CONNECTION_REFUSED` |
| 7 | `forward_stopped count=1 reason=transport is gone`, список опустел |

**Шаг 3 доказан сильнее, чем требовалось.** Гейт просил два соединения
одновременно; журнал показал четыре живых потока в одну миллисекунду. Это та
самая одновременность, ради которой затевался ADR-0004, и здесь она работает
на постороннем потребителе — браузере, который о нашем диспетчере не знает
ничего.

**Наблюдение, которого гейт не предусматривал.** Два соединения из тринадцати
закрылись с `fromClient=666 fromDevice=0` и `fromClient=698 fromDevice=0`:
клиент отправил запрос и закрыл сокет раньше, чем `cat` успел вернуть ответ.
Потерей это не является — отдавать было уже некому, — и дефектом тоже:
логический поток ADB закрывается целиком, полузакрытия в протоколе нет, так же
ведёт себя и настоящий `adb forward`. Записано, чтобы следующий читатель
журнала не принял разошедшиеся счётчики за потерю.

**Что закрыто окончательно.** `forward` доказан на железе целиком: подъём,
содержимое в обе стороны, одновременность, обе причины конца, отказ адреса при
живом слушателе, снятие с освобождением порта, снятие по смерти транспорта.

**Что остаётся.** `reverse` — шаги 5–7 плана `ADR-0005`: входящий `OPEN` в
маршрутизаторе и формат запроса, который выясняется наблюдением. Пункт
чеклиста остаётся «частично»: половина возможности готовой не считается
(`04`, capability completeness rule).

## 6.60. Наблюдение формата обратного проброса — план; проведён, см. §6.61

Раздел написан **до** прогона. Это шаг 5 плана
`docs/adr/0005_LOCAL_SOCKET_FORWARDING_RU.md`, и он не похож на остальные гейты:
здесь ничего не проверяется — здесь **выясняется**.

**Почему это отдельный прогон.** Формата запроса, которым хост просит устройство
начать слушать, в архивах нет: оба дерева проверены по именам файлов и по
содержимому до начала работы. Восстанавливать его по памяти запрещает `16` §3, и
запрет не теоретический — проект уже спотыкался об это (`07` §6.46: константа
была найдена грепом, а использование не открыто).

Инструмент для наблюдения существует и ровно для этого делался: поле
произвольного сервиса передаёт имя как набрано и показывает ответ устройства
вместе с числом байт.

**Имена ниже — гипотезы, а не знание.** Они перечислены затем, чтобы их
проверить, и любая может оказаться неверной. Верным считается то, что ответит
устройство, а не то, что здесь написано.

| Шаг | Что набрать в поле произвольного сервиса | Что записать |
|---|---|---|
| 1 | `reverse:list-forward` | ответ целиком и число байт; отказ — тоже ответ |
| 2 | `reverse:forward:tcp:7777;tcp:8888` | ответ целиком; появился ли `inbound_stream_refused` в журнале |
| 3 | `reverse:list-forward` повторно | изменился ли ответ после шага 2 |
| 4 | `reverse:killforward-all` | ответ; и снова шаг 1, чтобы увидеть пустой список |

**Как читать результат.**

- шаг 1 дал осмысленный ответ или пустой успех → имя сервиса угадано, и формат
  дальше строится от него;
- шаг 1 дал `REJECTED` → имени такого нет, и гипотезы придётся менять; что
  именно пробовать дальше, решается по тому, **что** ответило устройство, а не
  по следующей догадке из памяти;
- шаг 2 изменил ответ шага 3 → запрос принят, и формат подтверждён
  наблюдением;
- в журнале появился `inbound_stream_refused` → устройство завело к нам поток,
  то есть шаг 6 плана заработал на железе; отказ сейчас правильный — принимать
  ещё некому.

**Побочно проверяется шаг 6.** Запись `inbound_stream_refused` добавлена
специально к этому прогону: без неё нельзя отличить «устройство завело поток, и
мы корректно отказали» от «устройство ничего не заводило». Это тот же урок, что
§6.52, §6.55 и §6.57 — и на этот раз запись готова заранее.

**Мера предосторожности.** Шаг 2 заставляет устройство слушать порт. Это
обратимо и снимается шагом 4; оставлять слушатель на подопытном после прогона
незачем. Если шаг 4 не сработает, слушатель уйдёт с перезагрузкой устройства.

**Чего этот прогон не делает.** Он ничего не реализует. Код `reverse` пишется
**после** него и по его результату — это шаг 7.

## 6.61. Формат обратного проброса наблюдён — 2026-09-11, три ответа устройства

Прогон §6.60. Три вызова, все приняты, ни одного `REJECTED`. Гипотезы из плана
оказались верными, но **важно не это**: важно, что ответы записаны дословно и
дальше код пишется по ним, а не по памяти.

| Запрос | Байт | Ответ дословно |
|---|---|---|
| `reverse:list-forward` | 4 | `0000` |
| `reverse:forward:tcp:7777;tcp:8888` | 12 | `OKAY00047777` |
| `reverse:killforward-all` | 4 | `OKAY` |

**Что из этого следует наблюдением.**

- Все три имени сервиса существуют: устройство приняло их и ответило, а не
  закрыло поток.
- `reverse:forward:<устройство>;<хост>` отвечает `OKAY`, затем **четыре
  шестнадцатеричные цифры длины**, затем тело. Здесь `0004` и `7777` — тело
  оказалось назначенным портом на устройстве, тем самым, который просили.
- `reverse:list-forward` ответил `0000` и **без** `OKAY`: четыре цифры длины и
  пустое тело. Пустой список — это не отказ.
- `reverse:killforward-all` ответил `OKAY` и без длины вовсе.

**Расхождение, которое надо назвать, а не сгладить.** У одного ответа есть
префикс `OKAY`, у другого нет, у третьего нет длины. Объяснять это догадкой
сейчас нельзя: наблюдений три, и по трём точкам правило не выводится. Разбор
ответа в коде будет **терпимым** — искать `OKAY` и длину там, где они есть, и
не требовать их там, где их не наблюдали.

**Чего прогон не дал.** Шаг 3 плана — повторный `list-forward` **после**
`forward` — не выполнен, и непустой список остался ненаблюдённым. Для самой
возможности это не блокер: чтобы принять обратный проброс, довольно запроса и
входящего потока. Но показать оператору список того, что слушает устройство,
без этого наблюдения нельзя, и выдумывать его формат я не буду.

**Входящих потоков не было, и это правильно.** `inbound_stream_refused` в
журнале ноль: устройство начало слушать 7777, но к этому порту никто не
подключался — подключаться было нечем и незачем. Шаг 6 на железе этим прогоном
не проверен, и проверится он вместе с самим `reverse`.

**Убрано за собой.** `reverse:killforward-all` ответил `OKAY`; слушателя на
подопытном не осталось.

## 6.62. Непустой список и перевод строки — 2026-09-11, наблюдение спасло от дефекта

Дополнение к §6.61: тот же прогон, но `list-forward` спрошен **после**
`forward`, чего в прошлый раз не сделали.

    19:45:48  reverse:forward:tcp:7777;tcp:8888 → 12 байт: OKAY00047777
    19:46:09  reverse:list-forward              → 29 байт: 0019UsbFfs tcp:7777 tcp:8888
    19:46:29  reverse:killforward-all           →  4 байта: OKAY

**Формат строки списка.** `UsbFfs tcp:7777 tcp:8888` — сначала транспорт, потом
сторона устройства, потом сторона хоста, через пробел. Порядок сторон тот же,
что в запросе, и это второе независимое подтверждение §6.61.

**Главное здесь — арифметика, а не содержимое.** Объявлено `0019`, то есть
двадцать пять символов. Видимых — двадцать четыре. Всего получено 29 байт:
четыре на длину и двадцать пять на тело. Двадцать пятый символ есть
**завершающий перевод строки**, и на экране его не видно потому, что
`AdbServiceOutcome.Completed.text()` срезает концевые переводы строк.

**Отсюда требование, которого без наблюдения не было бы.** Разбирать ответ надо
по сырому выводу, а не по `text()`. Иначе длина перестаёт сходиться, и верный
ответ устройства приходит как `Unreadable` — то есть код объявляет непонятным
то, что понял бы, не обрезав.

Это был бы настоящий дефект, и нашёлся бы он не сразу: пустой список
(`0000`) разбирался бы правильно, а ломалось бы только на непустом — то есть
ровно тогда, когда возможность начинает работать. Оба случая теперь закреплены
проверками: со строкой конца и без неё.

**Чего по-прежнему не видели.** Отказа. Все пять запросов за два прогона
приняты, и форма `FAIL` остаётся догадкой — так и записана в коде.

## 6.63. Аппаратный гейт обратного проброса — план; закрыт прогонами §6.65 и §6.66

Раздел написан **до** прогона. Шаг 7 плана
`docs/adr/0005_LOCAL_SOCKET_FORWARDING_RU.md`, и он же последний пункт Phase 4,
не запертый в Phase 8.

**Чем это отличается от §6.51.** Там слушали мы, и клиента приводил оператор.
Здесь слушает **устройство**, а соединение приходит к нам входящим потоком, и
навстречу ему идём мы — к адресу на хосте. Значит нужен тот, кто на хосте
ответит, и им будет наш же собственный проброс: `forward` уже доказан (§6.59),
и опираться на доказанное правильнее, чем заводить ради гейта ещё одну
неизвестную.

**Схема прогона.** Проброс `forward` слушает на хосте порт **P** и ведёт на
`shell:cat` устройства. Обратный проброс просит устройство слушать `tcp:7777` и
приводить соединения к `tcp:P` на хосте. Тогда соединение, начатое **на
устройстве**, доходит до нашего слушателя, а оттуда — обратно на устройство в
`shell:cat`. Путь замкнут, и по счётчикам обеих секций видно каждое звено.

Начать соединение на устройстве нечем, кроме самого устройства: для этого
пригодится поле произвольного сервиса — `shell:` с командой, которая сходит на
`127.0.0.1:7777` у себя.

**Чем именно — спрошено у устройства, а не предположено.** `shell:which nc`
ответил `/system/bin/nc`, пятнадцать байт. Значит `nc` вызывается по имени, без
`toybox` впереди.

| Шаг | Что сделать | Что обязано получиться |
|---|---|---|
| 1 | Завести `forward`: порт `0`, адрес `shell:cat`; запомнить назначенный порт **P** | слушатель поднялся, как в §6.59 |
| 2 | В обратном пробросе: на устройстве `tcp:7777`, на этом телефоне `tcp:P` | в списке появился обратный проброс, устройство ответило `7777` |
| 3 | Нажать «Что оно слушает» | ответ содержит `tcp:7777` и `tcp:P` |
| 4 | Вызвать сервис `shell:echo hello \| nc 127.0.0.1 7777` | ответ `hello`: путь замкнулся; у обратного «приведено 1», у `forward` «принято» выросло |
| 5 | Отключить кабель | обратные пробросы исчезли, как и прямые |

**Как читать результат.**

- шаг 2 дал отказ → смотреть, что именно ответило устройство: форма `FAIL` нам
  до сих пор не встречалась (`07` §6.61), и её первый живой пример сам по себе
  ценен;
- шаг 4 вернул `hello` → путь замкнулся целиком: через обратный проброс к
  нашему слушателю и обратно на устройство в `shell:cat`. Слово латиницей
  намеренно — кодировка не должна вмешиваться в доказательство;
- шаг 4 не тронул счётчики → соединение не дошло; различить где, поможет
  журнал: `inbound_stream_accepted` означает, что устройство поток завело,
  `reverse_unreachable` — что мы не дошли до адреса на хосте,
  `reverse_unroutable` — что адрес нам непонятен;
- счётчик у обратного вырос, а у `forward` нет → мы приняли поток, но до своего
  же слушателя не дошли, и это наша ошибка целиком;
- шаг 5 оставил обратный проброс в списке → ожидание пережило транспорт, а
  поток по нему идти уже некуда.

**Чего гейт не проверяет.** Адрес на хосте вида `localabstract:` — мы не умеем
до него дойти и говорим об этом прямо (`reverse_unroutable`), потому что не
наблюдали, как это делается. И форму отказа устройства: за два прогона нам
отказали ноль раз.

**Мера предосторожности.** Шаг 2 заставляет устройство слушать порт. Снимается
кнопкой «Снять все»; если не сработает — уйдёт с перезагрузкой устройства.

## 6.64. Цепочка построена, данные не прошли — 2026-09-11, шаг 6 доказан

Прогон гейта §6.63. Шаги 1–3 прошли, шаг 4 построил весь путь и не перенёс ни
одного байта.

    20:15:50.185  forward_listening address=shell:cat bindAddress=127.0.0.1 localPort=45687
    20:17:51.580  reverse_listening assigned=7777 onDevice=tcp:7777 onHost=tcp:45687
    20:18:22.302  service_completed bytes=30 service=reverse:list-forward
    20:19:19.602  inbound_stream_accepted service=tcp:45687 stream=5
    20:19:19.604  forward_adopted stream=5
    20:19:19.605  forward_closed end=DEVICE_CLOSED fromClient=0 fromDevice=0 stream=5
    20:19:19.612  forward_accepted live=0 localPort=45687
    20:19:19.613  forward_open service=shell:cat stream=6
    20:19:19.632  forward_closed end=CLIENT_CLOSED fromClient=0 fromDevice=0 stream=6

**Шаг 6 плана доказан на железе, и это главный результат.** Строка
`inbound_stream_accepted service=tcp:45687` означает, что устройство завело
поток **к нам**, маршрутизатор его разобрал, приёмник опознал адрес как свой,
диспетчер подтвердил и отдал ящик. До этого прогона входящий `OPEN` на железе не
наблюдался ни разу — §6.61 его не вызвал, потому что к порту никто не
подключался.

**Построилась и вся остальная цепочка.** За тридцать миллисекунд: устройство
завело поток, мы его приняли, дошли до своего слушателя (`forward_accepted` на
том же порту 45687), тот открыл `shell:cat`. Пять звеньев собрались сами, без
единой ошибки маршрутизации.

**И ни одного байта.** Поток 5 кончился через 0,5 мс после принятия —
`DEVICE_CLOSED`, ноль в обе стороны. Устройство прислало `CLSE`, не прислав
`WRTE`. Поток 6 закрылся следом и по той же причине: закрылся наш канал, за ним
закрылось всё остальное. Вызов `shell:echo hello | nc 127.0.0.1 7777` ответил
нулём байт — `nc` отработал молча, то есть подключился и вышел, ничего не
получив.

**Чего сказать нельзя.** Почему устройство закрыло поток, не прислав данных.
Версий две, и журнал их не различает:

1. `nc` закрыл соединение сразу после отправки — `echo` закрывает stdin, и
   `adbd`, увидев конец, послал `CLSE` вместо `WRTE`, потеряв то, что успело
   прийти;
2. мы чего-то не сделали, и `adbd` закрыл поток по своей причине.

Разрешается это наблюдением, а не рассуждением: если держать соединение
открытым — `shell:(echo hello; sleep 3) | nc 127.0.0.1 7777` — и байты пойдут,
верна первая версия, и дефекта у нас нет вовсе. Если и тогда ноль, причина
наша, и искать её надо в том, что мы отвечаем устройству после подтверждения.

**Чего этот прогон стоил гейту.** Шаг 4 в §6.63 записан одной командой, и
оказалось, что такая команда проверяет не только проброс, но и поведение `nc`
с закрытым stdin. Это не ошибка гейта — это то, что выясняется только на
устройстве; но следующий заход должен развести два вопроса, а не смешивать их.

## 6.65. Обратный проброс работает — 2026-09-11, шесть байт кругом

Повтор §6.64 с одним изменением: соединение держится открытым —
`shell:(echo hello; sleep 3) | nc 127.0.0.1 7777`. Вызов ответил `hello`,
шесть байт.

    20:26:56.097  inbound_stream_accepted service=tcp:35121 stream=5
    20:26:56.099  forward_adopted stream=5
    20:26:56.099  forward_accepted live=0 localPort=35121

**Доказательством служат счётчики, а не факт соединения.** `6/6` на **обоих**
звеньях: шесть байт пришло от устройства и шесть ушло обратно на каждом. `hello`

**Путь, который прошли эти шесть байт.** Команда на устройстве постучалась в

механизма — прямой проброс и обратный, — и обе стороны транспорта заняты
одновременно.

**Версия 1 из §6.64 подтверждена, дефекта у нас не было.** Разница между
прогонами ровно одна: `sleep 3` держит stdin открытым. С `echo` `nc` закрывал
соединение раньше, чем `adbd` успевал передать данные, и мы получали `CLSE`
вместо `WRTE`. Код не менялся между прогонами вовсе — значит причина была не в
нём, и хорошо, что я не пошёл её «чинить» после §6.64.

**Снятие проверено.** `reverse_removed_all outcome=OK`, затем
`forward_removed`; оба списка опустели.

**Шаг 5 гейта остался непроверенным, и это надо сказать прямо.** Кабель
отключался в 20:24:43, но к тому моменту обратных пробросов уже не было — их
сняли кнопкой в 20:20:35. Поэтому `reverse_forgotten` в журнале нет, и увидеть,
что смерть транспорта уносит ожидание, не удалось. Путь покрыт проверкой
`aDeadTransportForgetsEveryExpectation` и повторяет прямой проброс, где то же
самое доказано на железе (§6.59, шаг 7), — но сам по себе он не наблюдался.

Закрывается это двадцатью секундами: завести обратный проброс и выдернуть
кабель, не снимая его кнопкой.

## 6.67. Аудит документации перед Phase 5 — 2026-09-11, семь расхождений

Software/doc changeset без нового поведения. Сверены 20 документов, 5 ADR, пять
гейтов `scripts/ci/`, ссылки между документами, числовые утверждения и раскладка
кода по модулям. Аппаратного прогона нет и не требуется: поведение не менялось,
ни одного `.kt` в changeset'е.

**Главное, что показал аудит, — не сами расхождения, а их форма.** Все семь
одного рода: текст рос припиской, а устаревшее утверждение рядом никто не
снимал. Не «забыли написать», а «забыли зачеркнуть».

**1. Единственный источник истины сам себе противоречил.** В чеклисте `09`
строка `forward/reverse` стояла **готово** и заканчивалась словами «`reverse`
не начат». Там же ADR-0005 назван `PROPOSED`, хотя он `ACCEPTED` с того же дня,

Строка `reboot` содержала «**Готовым не считается**: на железе не проверялось»
прямо перед «Доказано на железе прогоном §6.46». Читающий ячейку сверху вниз
получал неправду из документа, который `CLAUDE.md` называет единственным
источником истины о готовности.

Причина видна по размеру: ячейка `forward/reverse` выросла до 9032 символов
против 300–600 у соседей. Она пересказывала §6.51–§6.66 целиком, то есть делала
ровно то, что `CLAUDE.md` запрещает — дублировала прозу о сделанном. Обе ячейки
сжаты до статуса, решений и указателей на прогоны; ни один факт не потерян,
все они есть в `07` и ADR-0005 подробнее.

**2. Прошлый аудит нашёл эту же болезнь и вылечил половину.** §6.35 пункт 2
назвал четыре файла с дублирующейся прозой о статусе — `README.md`,
`docs/README.md`, `00` §7 и `99` — и убрал её в двух. Три дня спустя устарели
ровно те два, которые оставили: оба всё ещё писали, что `SEND` не имеет
аппаратного прогона, а `install`, `reboot`, raw services и concurrent dispatcher
не закрыты. К тому моменту все четыре были доказаны на железе. Теперь пересказ
убран и там: оба файла называют фазу и указывают на чеклист.

**3. Фаза была закрыта в журнале, но нигде больше.** §6.66 кончается словами
«Дорога к Phase 5 свободна», а четыре документа продолжали называть текущей
работой Phase 4. Заголовок фазы в `09` не имел отметки, хотя Phase 0–3 её
имеют. Отметка проставлена, текущей названа Phase 5.

**4. Слово «готово» просочилось в документ, который не о готовности.**
В `04` строка `concurrent multi-stream router` несла «**готово** (ADR-0004)» —
и не в своей колонке, а в «Источнике опыта», в таблице, чья первая строка
говорит, что это целевой контракт, а не обещание milestone. Соседняя строка
`forward/reverse` при этом осталась «Планируется», хотя сделана тем же днём:

готовности здесь нет и быть не должно.

22 217), а вместе с ним и соотношение: сейчас 3880 против 701, то есть в пять с
половиной раз. Сам снимок помечен как снимок и честно просил себя сверять —
а выведенная из него цифра такой пометки не имела. Обновлено; доля тестов,

одного класса. Разбирать сейчас нечего, но к Phase 9 он подойдёт вплотную к

## 6.68. Gradle заработал из чата — 2026-09-11, открыт `dl.google.com`

Изменение среды, не кода. Ни одного `.kt` в changeset'е; аппаратного прогона нет
и не требуется — поведение устройства здесь ни при чём.

**Что было.** `docs/16` §5.1 утверждал как факт: Gradle из чата не запускается,
Google Maven закрыт, Android-модули и Compose проверяет только CI. Это было
правдой и стоило дорого: две красные сборки подряд ломались на Compose, который
нечем было проверить, кроме разбора текста, и ради этого пришлось завести
отдельный гейт `check_compose_wiring.py` (`07` §6.35, §6.49).

**Что изменено.** В политике сети окружения уровень `Trusted` заменён на
`Custom` с одним добавленным доменом `dl.google.com` и сохранённым списком по
умолчанию. Домен один, потому что он отдаёт и Google Maven
(`/dl/android/maven2/`), и репозиторий SDK (`/android/repository/`).

Обход искали до того, как просить изменение: `maven.google.com` отвечает `301`
и редиректит ровно на `dl.google.com`, то есть зеркалом не является. Справка
прокси при этом прямо велит отказы политики не обходить, а называть хост.

**Чего одного домена не хватило.** Две вещи, которых нет в базовом образе:

| Чего не было | Как проявилось |
|---|---|
| Android SDK | `ANDROID_HOME` не задан, каталогов SDK нет вовсе |
| JDK 17 | образ несёт 21; сборка встала на `Cannot find a Java installation ... languageVersion=17` — toolchain закреплён на 17, и Gradle его не скачивает |

Обе ставит `scripts/dev/provision_android_toolchain.sh`. Попутно выяснилось, что
API 37 публикуется как `platforms;android-37.0`, а не `android-37`: запрос по
второму имени отвечает `Package not found`. И что индекс `apt` в образе бывает
устаревшим — без `apt-get update` установка JDK падает на `404` по настоящему
пакету, а не по отсутствующему.

**Измерено.** Прогнана ровно команда CI —
`./gradlew test lint assembleDebug --no-daemon --stacktrace`:

| Что | Результат |
|---|---|
| Тесты | 537, падений 0, ошибок 0 |
| Разбивка | `protocol:adb` 341, `usb:api` 127, `app` 44, `core:diagnostics` 16, `core:model` 3, `core:operation` 3, `usb:android` 3 |
| Lint | `0 errors` (11 замечаний ниже уровня ошибки в `:app`, 1 в `usb:android`) |
| APK | `app-debug.apk`, 14 МБ |
| Время | около 3 минут вхолодную, 8 секунд повторно |

537 сходится с числом `@Test` в дереве и с тем, что гоняет CI.

**Что это закрыло.** Три границы из §5.1 перестали существовать: сборка Gradle
со слиянием манифестов и Compose проверяется по-настоящему; `NewApi` и
`MissingPermission` проверяются тоже, потому что Lint выполняется локально той
же задачей, что в CI; заглушки библиотек не нужны вовсе.

**Что осталось и стало важнее.** Ни одна сборка не подтверждает поведение USB,
ADB, Fastboot и Recovery. Когда всё остальное стало проверяемым, эту границу
особенно легко начать размывать — поэтому она записана отдельной строкой и в
`16` §5.1, и в `CLAUDE.md`.

Отдельно записано расхождение с CI, которое остаётся: запускающая JVM здесь 21,
в CI 17. Toolchain в обоих случаях 17, поэтому выход компилятора совпадает, но
Gradle с AGP крутятся на разных JDK. Локальный зелёный — сильный признак, а не
тождество.

**Где это живёт, и почему не в репозитории.** Открытый домен и Setup script —
настройки окружения, дерева они не касаются. Контейнер сессии эфемерный, поэтому
установка руками умирает вместе с сессией; постоянное место скрипта — Setup
script окружения, который выполняется один раз, после чего файловая система
снимается снапшотом и достаётся следующим сессиям уже готовой. В репозитории
скрипт лежит затем, чтобы его можно было прочитать, поправить и прогнать как
обычный код, а не хранить копию в поле ввода.

Из этого следует граница, которую стоит помнить: **сессия в среде без этих
настроек вернётся к прежним ограничениям.** Тогда чинить надо среду, а не
подгонять код под неё.

**Setup script отчитывается успехом, ничего не сделав, и это проверено.**
Очевидный текст для его поля — `bash scripts/dev/provision_android_toolchain.sh`.
Он опирается на два необещанных условия: что репозиторий к тому моменту
склонирован и что рабочий каталог — его корень. Документация не говорит ни
того, ни другого; её собственный пример (`apt install shellcheck`) файлов
репозитория не трогает вовсе.

Проверено запуском из `/`: `No such file or directory` **и код возврата 0**.
То есть при несовпавшем каталоге среда сообщит об успешной подготовке, а
следующая сессия начнёт со сломанным инструментарием и без единого признака,
почему.

Поэтому надёжное место — не Setup script, а хук `SessionStart` в самом
репозитории (`.claude/hooks/session-start.sh`): он выполняется заведомо при
готовом дереве и получает его путь в `CLAUDE_PROJECT_DIR`. Setup script оставлен
как быстрый путь — он делает установку один раз до снапшота, — а хук закрывает
случай, когда тот промолчал. Чтобы страховка ничего не стоила, проверка наличия
вынесена в скрипт до вызова `sdkmanager`: на готовой машине он отрабатывает за
6 мс вместо секунд.

Хук намеренно ничего не делает вне облака: он ставит пакеты от root и пишет в
`/opt`, и на локальной машине — в Termux на телефоне, например — это была бы не
страховка, а порча рабочей среды. Условие `CLAUDE_CODE_REMOTE != true` стоит
первой строкой и проверено обоими прогонами.

## 6.69. Аппаратный гейт различения bootloader/fastbootd — план; закрыт прогоном §6.70

Раздел написан **до** прогона и до того, как результат виден. Первый пункт
Phase 5, и первый обмен по Fastboot в этом проекте вообще: до сих пор Fastboot
существовал только как класс интерфейса в дескрипторе.

**Что проверяется.** Что устройство отвечает по Fastboot, что роль читается по
`getvar:is-userspace`, и что неустановленная роль остаётся неустановленной, а не
подменяется догадкой.

**Почему это не проверить иначе.** Дескриптор различить роли не может: и
загрузчик, и `fastbootd` перечисляются одинаковым интерфейсом Fastboot-класса.
Устанавливает роль только протокольный обмен, а он на устройстве не выполнялся
ни разу — весь разбор до сих пор шёл по архивам.

### Шаги

1. **Загрузчик отвечает.** Из системы: `reboot bootloader` на экране ADB.
   Устройство поднимается интерфейсом FASTBOOT (это уже наблюдалось, §6.46).
   В секции Fastboot нажать «Спросить устройство, кто оно».
   Ожидается: `fastboot_probe_finished` с `lane=IDLE`. **Что именно в `mode` —
   гейт не предрешает:** на этом устройстве загрузчик может и не знать
   `is-userspace`, и тогда верный ответ — `UNKNOWN` с причиной. Требуется
   другое: чтобы `detail` называл основание, а не молчал.

2. **`fastbootd` отвечает иначе, чем загрузчик.** Из загрузчика перейти в
   `fastbootd` и повторить опрос. Ожидается `mode=FASTBOOTD`,
   `detail=is-userspace=yes`.
   **Это главный шаг гейта:** он единственный доказывает, что различение
   вообще работает, а не что мы всегда отвечаем одно и то же.

3. **Роль не выдумывается.** Сравнить `mode` из шагов 1 и 2. Если они совпали —
   различения нет, и гейт не пройден, каким бы «правильным» ни выглядел ответ.

4. **Рамка переживает отказ.** Наблюдать `FAIL` на шаге 1 или на любой
   переменной, которой у загрузчика нет. Ожидается: `lane=IDLE` после отказа.
   `FAIL` — ответ устройства, и рамку он не портит; если после него полоса
   окажется `STALLED`, это дефект.

5. **Молчание отличается от отказа.** Отсоединить кабель и нажать опрос.
   Ожидается `fastboot_claim_failed` либо `mode=UNKNOWN` с `lane=STALLED` и
   названной причиной. Требуется, чтобы в журнале было видно **какой** из двух
   случаев произошёл: неотличимость этих двух уже стоила прогона в §6.55.

### Что считается провалом заранее

- роль в шагах 1 и 2 совпала;
- `UNKNOWN` пришёл без причины в `detail`;
- после `FAIL` полоса осталась `STALLED`;
- отказ захвата и молчание устройства в журнале неразличимы.

### Что прогон не проверяет, и это записано заранее

Фазу данных, запись, разделы и что угодно мутирующее: в этом changeset'е их нет
вовсе. Опрос ничего не меняет на устройстве — единственная команда, которую он
шлёт, это `getvar:is-userspace`.

Отдельно: ветка слишком длинной команды и ветка команды не в ASCII на железе не
проверяются — их нечем вызвать из секции опроса, где команда одна и задана
кодом. Они закрыты тестами и ждут раздела произвольной команды Fastboot.

## 6.70. Роли различаются на железе — 2026-09-12, первый обмен по Fastboot

Пациент `vayu` (POCO X3 Pro), `serial:eff4927c`. Первая команда, отправленная
этим проектом по Fastboot: до сегодня Fastboot существовал только как класс
интерфейса в дескрипторе. Журнал полный — `droppedEvents=0`.

**Главный шаг гейта пройден: роли различаются.**

| Роль | Generation | `productName` | Ответ | Полоса |
|---|---|---|---|---|
| Загрузчик | 2 | `Android` | `is-userspace=no` → `BOOTLOADER` | `IDLE` |
| `fastbootd` | 4 | `vayu_global` | `is-userspace=yes` → `FASTBOOTD` | `IDLE` |

Шаг 3 требовал именно этого: совпадение ролей было объявлено провалом заранее.
Они не совпали.

**Предпосылка пункта подтверждена прямо, а не по аналогии.** Подпись
дескриптора в обеих ролях **одна и та же** — `6353:53261:FASTBOOT:255:66:3:129:1`,
включая `interfaceClass/Subclass/Protocol` = `255/66/3` и оба эндпоинта. То есть
дескриптор действительно не различает загрузчик и `fastbootd`, и различить их
мог только обмен. Это ровно то, на чём стоял весь пункт, и до сегодня оно было
взято из `02` §11, а не наблюдено.

**Наблюдение, которого не было в плане: `productName` в ролях разный.** Загрузчик
назвался `Android`, `fastbootd` — `vayu_global`. Заменой опросу это **не
является и заменой не станет**: `Android` — родовое имя, его носит множество
устройств, никакого контракта за строкой нет, и построить на ней различение
значило бы вернуться к догадке по дескриптору, от которой пункт и уводит.
Записано как факт, а не как способ.

**Переход в `fastbootd` сделан нашим же кодом.** `reboot:fastboot` через секцию
перезагрузки: `reboot_requested` → `reboot_accepted evidence=dispatch loop
stopped` за 2,56 с, дальше generation 4 с интерфейсом FASTBOOT. Прогон
§6.50 закрывал эту ветку на целях `bootloader` и `recovery`; цель `fastboot`
встретилась впервые и повела себя так же.

**Времена.** Опрос занял 12,0 мс в загрузчике и 1,2 мс в `fastbootd`. Разница
десятикратная и ни на что не влияет, но записана: первый обмен полезно иметь
с числом.

**Расхождение с архивом, которое сработало в нашу пользу.** A2 держит
`HANDSHAKE_SETTLE_MS = 350` — паузу после захвата интерфейса перед первой
командой. Мы её не делаем: между `interface_claimed` и `fastboot_probe_started`
прошло 10,2 мс в загрузчике и **0,3 мс** в `fastbootd`, и обе команды получили
ответ. На этом устройстве пауза не нужна. Утверждать, что она не нужна вообще,
по одному устройству нельзя — если где-то первая команда останется без ответа,
проверять надо это в первую очередь, и место в архиве известно.

### Чего прогон не проверил, и это названо, а не умолчано

**Шаг 4 не вызван.** Отказа не было ни одного: устройство знает `is-userspace` в
обеих ролях, поэтому `FAIL` на железе так и не пришёл. Значит ветка «отказ рамку
не портит» подтверждена только тестами. Закрывается она обращением к переменной,
которой у загрузчика нет, — то есть разделом произвольного `getvar`, которого
пока нет.

**Шаг 5 не вызван.** Кабель выдернут (`session_closed_detached` generation 4 в
16:55:44), но опрос после этого не нажимали, и `fastboot_claim_failed` в журнале
нет. Различимость «отказ захвата» и «устройство молчит» на железе не проверена.
Это тот самый дефект наблюдаемости, который стоил прогона в §6.55, поэтому
пункт остаётся открытым и закрывается отдельным коротким прогоном, а не
задним числом.

Ни то, ни другое главного вывода не касается: различение ролей доказано, и
доказано на обеих ролях сразу.

### Правило из §6.67 пропустило первый же настоящий случай

Закрывая гейт, я проверил подсадкой дефекта, поймает ли его машинная проверка,
добавленная аудитом §6.67, — и **она не поймала**. Заголовок §6.69 объявлен
непрогнанным, ячейка чеклиста при этом стоит «готово», а гейт молчит.

Причина в том, как правило было написано: оно искало слова «закрыт», «выполнен»
или «пройден» рядом с номером гейта. И §6.70, и ячейка называют гейт пройденным
**другими** словами — «главный шаг гейта пройден» без номера рядом, «это был
главный шаг гейта §6.69» без глагола рядом. Совпадения не нашлось, и правило
отчиталось об успехе.

Это тот же износ, от которого правило и ставилось, только на уровень выше:
проверка выглядела верной, потому что проверялась на той формулировке, под
которую писалась. Аудит §6.67 заметил, что правило без машинной проверки
бесполезно; здесь выяснилось, что и машинная проверка бывает привязана к
формулировке.

Добавлено второе правило, **не зависящее от слов**: гейт, чей заголовок говорит
«прогон не проведён», не может быть упомянут в строке чеклиста с отметкой
«готово». Сопоставляются только номера. Проверено подсадкой того же дефекта —
падает с названием гейта.

## 6.71. Аппаратный гейт произвольного обмена Fastboot — план; закрыт прогоном §6.72

Раздел написан **до** прогона. Закрывает пункты `raw command`, `getvar
explorer`, `INFO/TEXT/OKAY/FAIL` и `one transaction engine`, а заодно — две
ветки, которые §6.70 оставил открытыми и назвал прямо.

**Почему один гейт на четыре пункта.** Они проверяются одним и тем же: через
полосу проходят обмены **разной формы**. `one transaction engine` иначе и не
закрыть — «движок один» подтверждается не существованием класса, а тем, что
через него прошло непохожее. Разбивать это на четыре прогона значило бы четыре
раза гонять оператора за тем же.

### Шаги

1. **Произвольная команда доходит как набрана.** В поле команды —
   `getvar:product`. Ожидается `OKAY` со значением, `lane=IDLE`, и в журнале
   `fastboot_command` с ровно набранной строкой.

2. **Отказ устройства не портит рамку.** Спросить переменную, которой у
   загрузчика нет: в поле имени — `no-such-variable-here`.
   Ожидается: `устройство отказало`, **`lane=IDLE`**, и следом шаг 1 работает
   снова.
   **Это главный шаг.** §6.70 оставил ветку неподтверждённой на железе, потому
   что `is-userspace` знают обе роли и `FAIL` не пришёл ни разу. Если после
   отказа полоса окажется `STALLED` — это дефект, и гейт не пройден.

3. **`getvar:all` разбирается.** Кнопка «Прочитать всё».
   Ожидается: список переменных с числом больше одной, `complete=true`,
   `lane=IDLE`. Сколько именно — гейт не предрешает: это свойство устройства.
   Требуется другое: чтобы **имена не слились**. Если в списке есть
   `partition-size:<что-то>` хотя бы для двух разных разделов — двухсоставные
   имена разобраны верно. Если вместо этого видно одну переменную
   `partition-size` со значением вида `boot: …` — разбор сломан, и гейт не
   пройден, каким бы длинным список ни выглядел.

4. **Строки `INFO` видны оператору.** На любом из шагов, где устройство их
   шлёт, они должны появиться на экране отдельными строками, а не пропасть.
   `getvar:all` их шлёт заведомо.

5. **Разные по форме обмены прошли одну полосу.** После шагов 1–3 в журнале
   должны стоять `fastboot_command_finished`, `fastboot_getvar_finished` и
   `fastboot_getvar_all_finished` — три обмена разной формы, и все с
   `lane=IDLE` на конце. Это и есть закрытие `one transaction engine`.

6. **Отказ захвата отличается от молчания устройства.** Выдернуть кабель и
   нажать опрос роли.
   Ожидается: `fastboot_claim_failed` **либо** `mode=UNKNOWN` с `lane=STALLED`,
   и в журнале видно, какой именно из двух случаев. Вторая ветка, оставленная
   §6.70 открытой; неотличимость этих двух стоила прогона в §6.55.

### Что считается провалом заранее

- после `FAIL` полоса осталась `STALLED`;
- `getvar:all` дал одну переменную `partition-size` вместо имён с разделами;
- строки `INFO` на экране не появились;
- в журнале нет всех трёх `*_finished`;
- отказ захвата и молчание устройства в журнале неразличимы.

### Чего прогон не проверяет, и это записано заранее

Фазу данных и что-либо мутирующее. Команда `download:` фазу откроет, и полоса
честно скажет, что передавать нечем, — но специально её здесь не трогаем: это
пункт `DATA OUT`, который не начат, и вызывать его ради «посмотреть» значило бы
оставить устройство ждать байты без нужды.

Оператору: команды вроде `erase:` и `flash:` в это поле **не набирать**. Они
мутирующие, их граница мутации не разобрана, и в этой фазе их нет. Поле
ограничений не имеет намеренно (`01` §3) — ответственность за набранное здесь
на операторе.

## 6.72. Отказ не портит рамку, 222 переменные — 2026-09-12

Пациент `vayu`, `serial:eff4927c`, загрузчик. Журнал полный, `droppedEvents=0`.

**Главный шаг гейта пройден, и пройден с запасом.** Требовалось, чтобы после
`FAIL` полоса осталась `IDLE`. Оператор прогнал отказ и согласие **вперемешку**:

| Время | Обмен | Ответ | Полоса |
|---|---|---|---|
| 17:48:49 | `getvar:product` | `OKAY payload=vayu` | `IDLE` |
| 17:49:13 | `getvar:no-such-variable-here` | `FAIL GetVar Variable Not found` | `IDLE` |
| 17:49:39 | `getvar:product` | `OKAY payload=vayu` | `IDLE` |
| 17:49:45 | `getvar:no-such-variable-here` | `FAIL` | `IDLE` |
| 17:49:47 | `getvar:product` | `OKAY payload=vayu` | `IDLE` |

Это закрывает ветку, которую §6.70 оставил открытой и назвал прямо: там
`is-userspace` знают обе роли, отказа не пришло ни разу, и «`FAIL` — ответ, а не
поломка» держалось на тестах. Теперь оно наблюдено, и наблюдено трижды подряд.
Отказ занял 6,4 мс.

**Имена в `getvar:all` не слились — второй существенный шаг.** Устройство
назвало **222** переменные за 283 мс, `complete=true`, `lane=IDLE`. На экране
видны `partition-type:persistbak`, `partition-size:persistbak`,
`partition-type:persist`, `partition-size:persist`, `partition-type:modemst2`,
`partition-size:modemst2`, `partition-type:bk52`, `partition-size:bk52` — то
есть двухсоставные имена разобраны порознь. Провалом заранее объявлялось
обратное: одна переменная `partition-size` со значением вида `boot: …`. Этого не
случилось.

**Один движок принял три разные формы обмена.** В журнале стоят
`fastboot_command_finished`, `fastboot_getvar_finished` и
`fastboot_getvar_all_finished`, все с `lane=IDLE`. Пункт `one transaction
engine` закрывается именно этим: «движок один» подтверждается не существованием
класса, а тем, что через него прошло непохожее.

### Шестой шаг гейта был поставлен неверно, и это моя ошибка

Шаг требовал выдернуть кабель и нажать опрос роли. Оператор ответил, что при
выдернутом кабеле интерфейса нет вовсе — только «Пересканировать USB» и
«Выгрузить диагностику». Это **верно**: без сессии нет и секции Fastboot, а
значит и кнопки, которую я просил нажать. Шаг просил сделать невозможное.

Записывается не как «не сделан», а как **негодный**: критерий, который нельзя
выполнить, критерием не является — так же, как придуманный после результата.

Правильно эти два случая проверяются иначе, и это записано здесь для будущего
гейта:

- **устройство молчит** — выдернуть кабель **во время** долгого обмена, то есть
  на `getvar:all`. Полоса должна уйти в `STALLED` с названной причиной;
- **захват не удался** — надёжного способа вызвать на железе нет: отказ выдаёт
  платформа, и подстроить его по требованию нечем. Остаётся под тестами, и это
  честнее, чем держать открытым шаг, который никто не выполнит.

Различимость самих событий при этом структурная, а не словесная:
`fastboot_claim_failed` пишется **до** всякого обмена, а `lane=STALLED` — только
после. Спутать их нечем.

### Ветка, которую прогон не вызвал

Строки `INFO` от **обычной** команды на экране не появились: `infoLines=0` во
всех трёх обменах — это устройство на `getvar` их не шлёт. Через `getvar:all`
они прошли заведомо (222 переменные пришли именно ими), но там показываются
разобранным списком, а не сырыми строками. Значит путь «сырая `INFO` на экране»
подтверждён не полностью, и `TEXT` не наблюдался ни разу.

Вызовется это само, когда появится команда, которая говорит по ходу дела, —
`erase:` или `flash:`. Специально гонять её сейчас нельзя: они мутирующие, и их
граница мутации не разобрана.

### Пробел наблюдаемости, найденный прогоном и закрытый тем же changeset'ом

Журнал написал `duplicates=2 ignored=2` — оба не нули, на живом устройстве. А
**какие именно**, по журналу узнать было нельзя: видно, что что-то есть, и не
видно что. Тот же дефект стоил прогона в §6.55.

Добавлены `duplicateNames`, `conflicting` и `ignoredLines`. Значения переменных
при этом **не** записываются, и это намеренно: среди 222 переменных есть `token`
разблокировки Xiaomi. Проверено — в выгруженном архиве его нет ни в одном
разделе, журнал хранил только числа. Имя расхождения и неразобранная строка для
разбора достаточны, а выгружать весь ответ устройства в отчёт незачем. Это
свойство стоит помнить к `diagnostics privacy review` из Phase 11.

### Наблюдения, которые пригодятся позже

`unlocked = no` — загрузчик заперт. Для нас это **advisory** и ничего не
запрещает (ADR-0002, D031): предупреждение и typed confirmation, а не запрет.
Пригодится, когда появится запись образа.

`token` — тот самый токен разблокировки, который понадобится Mi Unlock в
Phase 10. Устройство отдаёт его обычным `getvar`, и отдельного пути к нему не
нужно.

Ещё: `reboot_accepted evidence=transport closed`. §6.70 наблюдал другую дорогу к
тому же исходу — `dispatch loop stopped`. Обе верны и обе предусмотрены §6.50;
теперь встречены оба варианта на одной и той же цели `reboot:bootloader`.
